# 데몬 하네스 실행 방식: 자료의 전제와 실제 적용 검사

## 문제와 판정 단위

외부 입력을 읽는 `Entry`를 찾았다는 사실만으로 `LLVMFuzzerTestOneInput`에서 그 입력을 정상적인 순서로 재생할 수 있는 것은 아니다. 실제 데몬은 연결 설정, 여러 메시지, 작업자 스레드, 공유 상태와 종료 절차를 거칠 수 있다. 소스의 `if`나 `case`는 그 흐름을 읽을 위치를 알려 줄 수 있지만 외부 주체가 요청 가능한 동작의 개수나 완료 여부를 정하지 않는다.

이 저장소의 기본 Action 탐색은 분기마다 작업을 만들지 않는다. 열린 함수에서 입력 형태·소비·효과를 별도로 확인하고, 미열람 호출 대상과 불확실한 값 전달을 미해결로 남긴다. 단일 입력의 정상 응답, GDB의 같은 스레드 중단점 순서, `if/case` 위치만으로 요청별 실행과 취약점을 증명하지 않는다.

## 공개 연구를 옮길 수 있는 범위

| 자료와 원래 전제 | 이 프로젝트에서 확인할 수 있는 것 | 그대로 옮기면 생기는 문제 | 적용 결정 |

| [StateAFL 공개 구현](https://github.com/stateafl/stateafl): StateAFL 컴파일러로 계측한 네트워크 서버와 재생 가능한 메시지열이 필요하다 | 별도 서버 프로세스를 실제 통로로 실행하고 요청열의 경로·상태를 탐색할 수 있다 | 상태 해시나 경로 증가는 특정 요청의 성공, C 하네스 생성, 크래시의 취약성 증명이 아니다 | 별도 `network-fuzz` 연구 캠페인으로만 사용하며 C 하네스 판정과 분리한다 |
| [RESTler 논문](https://patricegodefroid.github.io/public_psfiles/icse2019.pdf): OpenAPI의 요청 종류와 응답 경계가 먼저 있다 | 생산자·소비자 순서와 실제 거절 응답을 검토할 수 있다 | 임의 데몬의 소스 분기를 OpenAPI 요청 종류로 치환하거나, 프로토콜 프레임 없이 응답을 요청에 귀속하면 잘못된 순서를 승인한다 | 소스 기반 요청 형식은 가설로 보관하고 원본 실행의 요청별 증거가 없으면 미확정으로 둔다 |
| [AFLNet 공개 구현](https://github.com/aflnet/aflnet): 실제 메시지열과 서버 응답을 이용한다 | 단일 메시지보다 요청열이 필요한 네트워크 기능을 시험할 수 있다 | 임의 바이트 가설을 실제 클라이언트 기록처럼 취급하거나 TCP 방식을 파일·환경 입력에 적용할 수 없다 | 실제 원본에서 관찰한 바이트와 소스 기반 가설의 출처를 구분한다 |

숫자 `16`개 함수나 `8`개 시드가 이해의 완료 기준이라는 근거는 이 자료들에 없다. 현재 기본 함수 원문 탐색 상한과 초기 입력 사례 상한은 `0`이며, 명시적인 작업 예산에 걸리면 미해결 작업으로 기록한다. 반면 시나리오의 후보·상태 탐색에는 자원 예산이 남아 있다. 이 예산은 완전성이나 정상 흐름의 증거가 아니며 소진된 후보를 결과에서 구별해야 한다.

하네스 검증용 입력 생성에도 `14~24`개를 모델에 강제하던 규칙이 있었다. [LLVM libFuzzer 문서](https://llvm.org/docs/LibFuzzer.html)는 시드 코퍼스의 유용성과 반복 실행 계약을 설명하지만 특정 개수를 정상성 조건으로 정하지 않는다. 따라서 검증 Agent의 스키마에서 개수 하한·상한을 제거하고, 원본 실행에서 관찰한 요청 하나는 실행기가 항상 추가하도록 유지했다. 모델은 열린 소스나 관찰한 입력 형식으로 설명할 수 있는 변형만 제안한다. 이 변경은 불필요한 변형을 채우는 비용을 줄일 수 있지만, 더 적은 시드로 동일한 버그를 찾는다는 성능 증거는 아니다. 원본 요청과 변형 요청의 도달률·고유 경로 수를 비교해야 한다.

## LightFTP 실제 적용 실험, 2026-10-31

StateAFL의 공개 소스 `/mnt/c/harness/research-repos/StateAFL`의 `d923e22f7b2688db45b08f3fa3a29a566e7ff3a4`를 사용했다. 실제 LightFTP 원본의 기준 리비전은 `5980ea1a0ee0e5c3015275f93445626f8c25c83a`다. 격리된 사본에서 공개 컴파일러 `afl-clang-fast`를 빌드하고, LightFTP의 기존 Makefile에서 컴파일러 경로만 그 컴파일러로 바꿔 계측 서버를 만들었다. 이 Makefile 수정은 **LightFTP 실험용**이며 일반 데몬 빌드 규칙으로 제품에 넣지 않았다.

앞선 LightFTP 원본 실행에서 얻은 `NOOP`와 `USER` 요청을 StateAFL의 길이 접두 메시지 형식으로 재생했다. 격리된 컨테이너에서 45초 실행한 `fuzzer_stats`는 `execs_done=1669`, `paths_total=23`, `stability=92.61%`, `bitmap_cvg=0.31%`, `unique_crashes=0`을 기록했다. 원자료는 `/tmp/harnesscreator-lightftp-stateafl/campaign/out/fuzzer_stats`와 `/tmp/harnesscreator-lightftp-stateafl/campaign/afl.log`에 있다. 통계 파일의 SHA-256은 `59b247c98c0c0d6762274a9852db18403a101a70007f2dbde10c14248ce0f822`다. 따라서 **해당 계측 LightFTP에서 네트워크 퍼징이 실제로 시작됐다는 좁은 결론**만 지지한다. `stability`가 100%가 아니므로 반복 실행의 완전한 결정성도 확인되지 않았다.

첫 실행은 StateAFL 소스의 [`check_aslr()`](https://github.com/stateafl/stateafl/blob/d923e22f7b2688db45b08f3fa3a29a566e7ff3a4/afl-fuzz.c#L9611-L9642)에서 ASLR 때문에 즉시 중단됐다. 공개 구현의 [`check_crash_handling()`](https://github.com/stateafl/stateafl/blob/d923e22f7b2688db45b08f3fa3a29a566e7ff3a4/afl-fuzz.c#L9547-L9609)은 Linux `core_pattern`이 파이프로 시작하면 중단하며, 환경 변수로 건너뛰면 크래시를 시간 초과로 잘못 해석할 수 있다고 경고한다. 재실험은 격리된 컨테이너 내부에서만 ASLR을 0으로 바인드하고 크래시 검사 생략 변수를 명시해 수행했다. 호스트 ASLR은 2로 유지됐다. 제품의 `network-fuzz` 실행기는 이제 두 조건을 실행 전에 검사하며 시스템 설정을 자동 변경하거나 크래시 검사 생략을 자동 허용하지 않는다.

## memcached 비교 실험, 2026-10-31

한 데몬에서의 실행 결과를 일반화하지 않기 위해, 별도의 `/tmp/harnesscreator-memcached-stateafl/source`에 원본 memcached `2d51e364799bc9698bd4b11728ea978cea12da6e`를 복사해 같은 StateAFL 컴파일러로 빌드했다. 실제 소켓 원본 실행에서 `version`에 `VERSION UNKNOWN`, `set foo 0 0 3`에 `STORED`, 이어지는 `get foo`에 저장된 값과 `END`가 반환되는 것을 확인했다. 이 요청들을 길이 접두 메시지열로 만든 뒤 45초 캠페인을 실행했다. 원자료는 `/tmp/harnesscreator-memcached-stateafl/{build.log,server-smoke.log,afl.log,out/fuzzer_stats}`에 있다.

**처음 판정은 잘못됐다.** 45초 실험의 `fuzzer_stats`에는 `execs_done=37`, `bitmap_cvg=0.00%`가 있었고 초기 통계에는 `Bitmap range : 0 to 0 bits`가 표시됐다. 당시 이를 계측 경로가 없다는 결과로 해석했다. 그러나 [StateAFL의 `calibrate_case()`](https://github.com/stateafl/stateafl/blob/d923e22f7b2688db45b08f3fa3a29a566e7ff3a4/afl-fuzz.c#L4235-L4335)는 첫 시드를 여러 번 실행한 뒤에야 `bitmap_size`와 실행 시간을 기록한다. [dry run](https://github.com/stateafl/stateafl/blob/d923e22f7b2688db45b08f3fa3a29a566e7ff3a4/afl-fuzz.c#L4383-L4465)이 그 전에 중단되면 이 값은 0으로 남아도 실제 계측 비트가 0이었다는 뜻이 아니다. 통계 원본의 SHA-256은 `15cafee0bd7fc77d4c65ac4eb031b3b3180868981a1f11a9241f253777065659`다.

[후속 memcached 재시험 원자료](../research-evidence/stateafl-memcached/README.md)는 계측 서버의 응답 직후 약 1,200비트, 실행 반환 직후 1,324비트를 관찰했다. `AFL_FAST_CAL=1`을 명시한 별도 연구 실행은 보정을 완료해 1,324비트와 새 경로 2개를 기록했고, 제품의 `network-fuzz` 명령 재시험도 `bitmap_cvg=2.02%`, 새 경로 2개를 기록했다. 따라서 원래 45초 실험은 **보정 도중 중단돼 커버리지 여부를 판정할 수 없었던 사례**다. `AFL_FAST_CAL`은 보정 정밀도를 바꾸고 ASLR 사전 검사도 격리된 시험 복사본에서만 건너뛰었으므로, 후속 결과는 계측과 요청 전달의 작동 확인에 한정된다. 크래시 0건을 안전성 결과로 인용하거나 특정 handler 귀속 및 C 하네스 적격성을 주장하지 않는다.

실행기의 판정도 수정했다. `0.00%`와 초기 통계의 0비트만으로 계측 부재를 선언하지 않는다. StateAFL은 파일로 리다이렉트한 로그에도 ANSI 색상 코드를 넣어 `Bitmap range :`와 숫자 사이에 제어 문자가 낄 수 있으므로, 판정 전에 이를 제거한다. 실제 두 로그를 다시 파싱해 첫 실행은 **보정 완료 없음·0비트 초기 통계**, 후속 실행은 **보정 완료·1,324비트**로 구분했다. 시간 제한으로 첫 시드 보정이 끊기고 보정 완료 줄이 없으면 `CALIBRATION_INTERRUPTED_COVERAGE_UNKNOWN`을 기록한다. 완료 여부가 불명확한 0비트 결과는 `EXECUTIONS_OBSERVED_COVERAGE_UNKNOWN`으로 둔다. StateAFL이 명시적으로 `No instrumentation detected`를 보고한 경우만 계측 부재로 분류한다.

## Dropbear 원본 퍼저 비교, 2026-10-31

격리된 Dropbear 원본 복사본을 `./configure --disable-zlib --enable-fuzz`와 `make -j2 fuzz/fuzz-harness.o fuzzer-preauth FUZZLIB=fuzz/fuzz-harness.o`로 빌드했다. 실제 `fuzzer-preauth` 실행 파일에 SSH 식별 문자열 시드를 재생하면 종료 코드 0이 나왔다. GDB에서 `svr_session` 중단점은 한 프로세스에서 두 번 잡혔다. 이는 이 원본 퍼저의 `fuzz_run_server`가 입력을 `fuzz_set_input`으로 공급하고 세션 구조체를 다시 설정해 서버 세션에 진입한다는 소스 관찰과 일치한다. 같은 시드가 두 번 실행된 사실은 원본 퍼저의 독립 재생 특성이며, 생성기에서 만든 C 하네스가 정상이라는 증거는 아니다.

별도 일반 서버 빌드의 전체 컴파일 기록에는 `src/svr-session.c`가 있었지만 `fuzz/fuzz-common.c`는 없었다. 반면 소스 인덱서는 두 파일의 함수를 모두 검색할 수 있었다. 따라서 생성기의 함수 원문에 `recorded_compilation`을 표시한다. `RECORDED`는 해당 번역 단위의 컴파일 명령이 **제공된 기록에 있었다**는 뜻이고, `NOT_RECORDED`는 **그 기록에는 없었다**는 뜻이다. 컴파일 데이터베이스는 링크 목록이 아니고 증분 빌드 기록일 수도 있으므로 둘 다 대상 실행 파일의 링크 여부를 확정하지 않는다. 원본 퍼저의 초기화 함수를 일반 서버 빌드에 그대로 호출할 수 있다고 가정하지 않도록 모델에 이 경계를 전달한다. 실제 사용 가능 여부는 선택한 하네스 빌드에서 확인해야 한다.


## 적용 후에도 남는 장애

1. `instrument-server`는 호출자가 지정한 빌드 명령과 실행 파일 경로를 사용해 격리 사본을 빌드한다. `CC/CXX`를 설정하고, Makefile이 `gcc`/`g++`를 직접 호출하는 경우에는 PATH의 컴파일러 shim으로 StateAFL 컴파일러를 사용한다. 이 방식이 임의 C/C++ 데몬의 빌드 시스템을 자동으로 이해한다는 증거는 없다. 절대 경로 컴파일러, 별도 빌드 디렉터리, 생성 소스, 라이브러리 빌드는 각각 추가 확인이 필요하다.
2. StateAFL의 경로·상태 피드백만으로 특정 요청의 `Entry → handler → 결과`를 귀속할 수 없다. 기존의 엄격한 원본 실행 증명과 C 하네스 적격 판정을 대신하지 않는다.
3. 네트워크 서버에 유효한 방법을 모든 파일, stdin, 환경, IPC 입력에 적용할 수 없다. 각 통로의 실행·재설정 근거를 별도로 확보해야 한다.
4. 원본 재현 크래시도 모두 취약점이라고 단정할 수 없다. 정상적으로 거절해야 할 잘못된 입력에서의 의도된 중단, 환경 문제, 알려진 제약 위반을 구분해야 한다.

따라서 LightFTP와 후속 memcached 연구 실행에서는 네트워크 계측과 입력 전달을 관찰했다. 어느 실행도 일반 하네스 자동 생성률이나 거짓 양성 0%를 입증하지 않는다. 다음 비교 실험은 서로 다른 빌드 시스템의 데몬 둘 이상에서 **입력 도달률, 실제 handler 귀속률, 빌드 성공률, 반복 실행 안정성, 적격 C 하네스 수**를 각각 기록해야 한다. 그 전에는 공개 연구의 성능을 이 워크플로우의 성능으로 인용하지 않는다.

## 명시적 서버 빌드 어댑터 시험, 2026-10-31

LightFTP의 기존 Release Makefile은 `gcc`를 직접 호출하므로 `CC=afl-clang-fast`만으로는 계측 빌드가 되지 않는다. 새 `instrument-server` 경로에서 원본 소스를 복사하고 컴파일러 shim으로 컴파일했다. 첫 시험은 `make -C Release -B`가 기본 대상 하나만 빌드한 뒤 복사된 오래된 실행 파일을 새 결과로 오인했다. 이제 복사된 대상 실행 파일을 빌드 전에 제거한다. 두 번째 시험의 `make -C Release -B all`은 [빌드 로그](../../evidence-runs/lightftp-20261031-instrumented-build-v2/build.log)에서 StateAFL 런타임 객체와 PIE 기본 링크가 충돌했다. StateAFL 소스를 임의로 변경하지 않고, 사용자가 지정한 `--linker-flag=-no-pie`를 최종 링크에만 전달했다.

그러나 [세 번째 빌드](../../evidence-runs/lightftp-20261031-instrumented-build-v3/build.json)는 AFL 런타임 심볼만 있었고 `ftpserv.o`에는 coverage 참조가 없었다. `afl-showmap`은 연결만 한 경우와 `NOOP`을 보낸 경우 모두 `000000:1` 한 항목만 기록했다. 원인은 StateAFL LLVM 패스가 Clang 10 환경에서 만들어졌는데 호스트의 Clang 14로 컴파일한 것: LLVM 패스가 실제 함수에 적용되지 않은 채 링크만 성공했다. 따라서 런타임 심볼을 계측 성공의 충분조건으로 사용하지 않는다.

같은 StateAFL 컴파일러·LLVM 패스를 호환되는 Clang 10 컨테이너에 넣고, **사용자가 명시한** 이미지와 빌드 명령으로 다시 빌드했다. [네 번째 빌드 결과](../../evidence-runs/lightftp-20261031-instrumented-build-v4/build.json)에는 새 실행 파일 지문과 새로 컴파일한 객체 파일의 AFL coverage 참조가 모두 있다. 실제 서버에 `NOOP\r\n`을 보냈을 때 `200 Command okay.`를 받았다. [coverage 비교](../../evidence-runs/lightftp-20261031-instrumented-build-v4/coverage-smoke.json)에서 `afl-showmap`은 연결만 한 경우 169개, `NOOP`을 보낸 경우 203개 항목을 기록했다. 이는 **이 LightFTP 빌드에서 요청에 따른 계측 경로가 실제로 달라진다**는 국소 증거다. 당시 빌드 도구는 새 객체에서 coverage 참조를 관찰하지 못하면 `BUILT_COVERAGE_NOT_OBSERVED`를 반환하고 CLI 종료 코드 2로 표시했다. 후속 직접 컴파일·링크 검사는 아래에 기록했다. 런타임 심볼만으로 계측 성공을 보고하지 않는 원칙은 같다.

동일한 빌드 어댑터를 이미 설정 스크립트가 있는 별도 memcached 사본에도 사용했다. 호출자가 `./configure CC=gcc` → `make clean` → `make -j2 CC=gcc memcached` 세 단계를 명시했다. [빌드 결과](../../evidence-runs/memcached-20261031-instrumented-build-v2/build.json)는 새 실행 파일과 coverage가 들어간 새 객체를 기록한다. [원본 요청 시험](../../evidence-runs/memcached-20261031-instrumented-build-v2/original-request.json)은 같은 실행 파일에서 `SET` 뒤 `GET`이 성공했음을 기록한다. [coverage 비교](../../evidence-runs/memcached-20261031-instrumented-build-v2/coverage-smoke.json)에서 연결만 할 때 772개, `SET`·`GET`을 보낼 때 1,313개 항목이 기록됐다. `afl-showmap`의 종료 코드 1은 장기 실행 서버가 설정한 2초 제한에 걸려 종료됐기 때문이며, 요청 응답과 지도는 그 전에 기록됐다.

두 프로젝트의 빌드 방식은 달랐지만 빌드 명령과 이미지·링크 플래그는 사람이 지정했다. 이 결과는 **명시한 두 데몬에서 계측 빌드와 요청별 coverage 차이가 재현됐다**는 뜻이다. 임의 C/C++ 데몬의 빌드 자동화, StateAFL 캠페인의 상태 탐색, C 하네스 생성이나 반복 실행 가능성은 아직 증명하지 않는다. 제품의 `network-fuzz`와 `instrument-server`는 별도 명령이며 자동 하네스 생성 파이프라인으로 연결되지 않았다.

추가로 C++용 `g++` shim과 StateAFL의 `afl-clang-fast++` 경로는 [작은 C++ 빌드](../../evidence-runs/stateafl-cpp-20261031-build/build.json)에서 새 객체의 coverage 참조까지 확인했다. 이것은 C++ 컴파일러 연결의 검사이며 C++ **데몬**의 네트워크 실행 검사는 아니다.

## 실행 결과와 패키지 연결, 2026-10-31

기존 LightFTP Action 실행의 요청 시드 3개를 새 계측 바이너리와 연결해 [네트워크 퍼징 패키지](../../evidence-runs/lightftp-20261031-network-package-bound-v2/campaign.json)를 만들었다. 패키지 준비는 빌드 기록의 coverage 객체 확인 값과 실행 파일 SHA-256을 다시 검증한다. 빌드 이후 실행 파일이 바뀌거나 객체 계측이 관찰되지 않은 기록은 거절하는 회귀 검사도 추가했다. 이 연결은 그 실행 파일이 특정 handler를 수행한다는 증명은 아니다.

첫 짧은 StateAFL 실행은 [초기 시드의 dry run이 1초 제한에서 timeout](../../evidence-runs/lightftp-20261031-network-package-bound/logs/afl-fuzz.log)되어 퍼징을 시작하지 못했다. [StateAFL의 LightFTP 공개 튜토리얼](https://github.com/stateafl/stateafl/blob/d923e22f7b2688db45b08f3fa3a29a566e7ff3a4/tutorials/lightftp/README.md)은 대상 시작 대기와 종료 옵션을 사용한다. 이 자료와 실패 로그를 대조한 뒤 LightFTP 실험에서 `-D 10000`, `-K`, `-t 5000`, `-m none`을 **명시적으로** 설정했다. 다른 데몬에도 같은 값을 기본값으로 넣지 않는다. 실행기는 이런 dry run timeout을 `SEED_DRY_RUN_TIMEOUT`으로 분류해 coverage 부재와 구분한다.

두 번째 [25초 실행](../../evidence-runs/lightftp-20261031-network-package-bound-v2/results/fuzzer_stats)은 `execs_done=711`, `paths_total=10`, `bitmap_cvg=0.31%`, `stability=100.00%`를 기록했다. 이 결과는 **새 빌드와 기존 요청 시드가 StateAFL에서 실제 실행됐다**는 증거다. 크래시 검사를 건너뛰는 환경 변수를 격리 실험에서 명시했고 호스트 ASLR은 2로 유지됐다. 따라서 크래시 0건이나 안정성 100%를 취약점 부재, 장시간 결정성, C 하네스 자격으로 해석하지 않는다. 여전히 이 결과는 별도 네트워크 퍼징 경로이며 `LLVMFuzzerTestOneInput` C 하네스를 생성한 결과가 아니다. 관련 회귀 검사 25건이 통과했다.

## Action 실행과 별도 네트워크 하네스 연결

Action 워크플로우의 활성 생성기는 여전히 한 프로세스 안의 libFuzzer 반복 실행을 요구한다. LightFTP의 [실제 Action 실행](../../evidence-runs/lightftp-20261031-gdb-draft-fixed/20261031-174019-ede13aff/summary.json)에서는 원본 `NOOP`·`QUIT` 요청을 관찰했지만 C 코드 초안 둘 다 비었다. 모델은 서버의 요청별 완료·상태 정리를 증명하지 못했다. 이를 C 하네스 성공으로 재분류하지 않고, StateAFL의 **원본 서버 프로세스 실행 방식**을 별도 결과로 연결했다.

`run --network-harness-config /path/network.json`은 원본 실행에서 기록한 네트워크 시드만 사용한다. 설정 예시는 아래와 같다. 경로와 빌드 옵션은 대상 프로젝트에 맞게 직접 지정하며 LightFTP의 숫자를 공통 기본값으로 사용하지 않는다.

```json
{
  "afl_fuzz": "/path/to/stateafl/afl-fuzz",
  "server_build_manifest": "/path/to/instrumented/build.json",
  "server_command": ["/path/to/instrumented/server", "/path/to/config"],
  "transport": "tcp",
  "host": "127.0.0.1",
  "port": 40827,
  "seconds": 25,
  "seed_tier": "exploratory",
  "research_only": true,
  "replay_server_command": ["/path/to/uninstrumented/server", "/path/to/config"],
  "replay_timeout_ms": 5000,
  "startup_delay_us": 10000,
  "execution_timeout_ms": 5000,
  "memory_limit_unlimited": true,
  "graceful_sigterm": true,
  "execute": false
}
```

`replay_server_command`와 `replay_timeout_ms`는 함께 지정하는 선택 항목이다. 실제 퍼징에서 크래시 입력 파일이 생성된 경우 기존 StateAFL 재생 실행기에 원본 서버 명령을 전달한다. 재생 명령의 실행 파일은 워크플로우 시작 전에 확인하며, 계측 서버와 바이트가 동일하면 원본 재생으로 인정하지 않는다. 재생 중 원본 서버의 크래시가 관찰돼도 결과는 `ORIGINAL_REPLAY_CRASH_OBSERVED`이며, 요청이 원인인지 또는 취약점인지 자동으로 단정하지 않는다.

준비 전에 `build.json`의 원본 소스 경로가 이번 분석 대상과 같은지, 새 객체에 계측 흔적이 기록됐는지, 실행 파일 SHA-256이 빌드 당시와 같은지 확인한다. 원본 실행이 끝나면 시드 파일의 해시와 StateAFL 메시지 형식을 검사해 별도 패키지를 만든다. 실제 실행은 `execute: true`에서만 시도하며 호스트 실행 조건은 기존 StateAFL 사전 검사를 따른다. 호스트 조건 때문에 실행을 시작할 수 없으면 패키지는 보존하고 `PREPARED_EXECUTION_BLOCKED`로 기록한다. 결과는 `network_harness_status`와 `research/stateafl/network-harness-result.json`에 기록하고 C 하네스의 `QUALIFIED` 수에는 포함하지 않는다. 기존 LightFTP 시드 3개를 사용한 [연결 확인 결과](../../evidence-runs/lightftp-20261031-network-harness-integrated-check-v3/research/stateafl/network-harness/campaign.json)는 `PREPARED_UNQUALIFIED`였다. 이 검사는 **기존 실행 기록에 대한 패키지 연결 시험**이며 새 코드로 Action 전체 실행을 다시 완료한 결과는 아니다.

이 경로는 TCP/UDP 서버와 이미 준비된 계측 빌드 또는 대상별 빌드 명령이 있을 때만 사용할 수 있다. 파일·stdin·IPC 입력, 대상별 빌드 명령 자동 추론, 요청별 목표 handler 귀속, 원본과의 크래시 동등성, 일반 C++ 데몬의 빌드 성공률은 여전히 미검증이다.

## C++ 서버와 빌드 단계 연결 검사

[ProFuzzBench의 Live555 StateAFL 빌드 절차](../../research-repos/ProFuzzBench/subjects/RTSP/Live555/Dockerfile-stateafl)는 Live555의 `ceeb4f4` 리비전을 대상으로 `genMakefiles linux`와 `make`를 사용한다. 이 자료가 **모든 C++ 데몬에 같은 명령을 적용해도 된다**는 근거는 아니다. 그 리비전을 별도 체크아웃하고, 같은 두 명령을 명시적으로 전달해 현재 `instrument-server` 어댑터로 빌드했다. [빌드 기록](../../evidence-runs/live555-20261031-build-v1/build.json)은 `afl-clang-fast++`로 컴파일한 새 객체의 coverage 참조와 새 서버 실행 파일 해시를 기록한다.

[실행 기록](../../evidence-runs/live555-20261031-build-v1/original-request.json)에서 계측된 C++ RTSP 서버는 `OPTIONS` 요청에 `RTSP/1.0 200 OK`를 반환했다. 같은 실행 파일의 [coverage 비교](../../evidence-runs/live555-20261031-build-v1/coverage-smoke.json)는 연결만 했을 때 지도 항목 654개, `OPTIONS` 요청을 보냈을 때 791개로 추가 항목 137개를 관찰했다. 이는 **해당 C++ 서버의 입력이 계측 실행 경로를 바꾸는 것**을 확인한 결과다. 다른 RTSP 동작, 장시간 반복 실행, 크래시 판정은 확인하지 않았다.

이후 `network.json`의 `server_build_manifest` 대신 아래의 `build` 블록을 사용하도록 연결했다. `server_command`의 첫 항목은 정확히 `{server_binary}`이며, 빌드 결과의 실행 파일 경로로 치환된다. 빌드 명령·컴파일러·이미지·링크 플래그는 해당 프로젝트의 명시적 설정이다.

```json
{
  "afl_fuzz": "/path/to/stateafl/afl-fuzz",
  "server_command": ["{server_binary}"],
  "transport": "tcp",
  "host": "127.0.0.1",
  "port": 554,
  "seconds": 25,
  "seed_tier": "exploratory",
  "research_only": true,
  "execute": false,
  "build": {
    "compiler": "/path/to/stateafl/afl-clang-fast",
    "cxx_compiler": "/path/to/stateafl/afl-clang-fast++",
    "command": ["./genMakefiles", "linux"],
    "steps": [["make", "-j2"]],
    "server_relative_path": "mediaServer/live555MediaServer",
    "timeout_seconds": 1200,
    "linker_flags": ["-no-pie"],
    "container_image": "harnesscreator/stateafl-daemon-test:latest"
  }
}
```

기존 원본 소켓 관찰에서 나온 `OPTIONS` 한 건을 시드로 만든 [자동 빌드·패키지 결과](../../evidence-runs/live555-20261031-auto-network-v1/network-harness-result.json)는 `PREPARED_UNQUALIFIED`, 시드 1개, 새 객체 계측 관찰을 기록한다. [자동 빌드 서버 재시험](../../evidence-runs/live555-20261031-auto-network-v1/auto-build-runtime-smoke.json)도 `200 OK`였다. 이 테스트는 **설정에서 빌드와 패키징으로 이어지는 경로**를 확인한 것이고, Action Agent가 Live555의 Entry·Action을 발견해 전체 워크플로우를 완료한 증거는 아니다. 여전히 C/libFuzzer 적격 하네스와 C++ 데몬 전반의 생성률은 미검증이다.

## C++ 소스 분석의 컴파일 명령 누락과 복원

Live555를 빌드할 수 있어도 처음 [소스 분석 기록](../../evidence-runs/live555-20261031-build-v1/source-analysis.json)은 C++ AST 1개 파일만 파싱하고 220개 파일에서 실패했다. 첫 오류는 프로젝트 헤더를 찾지 못한 것이었다. `handleCmd_DESCRIBE`, `handleCmd_SET_PARAMETER`처럼 `::`가 다음 줄에 놓인 메서드 정의도 정규식 기반 보조 인덱스에서 빠졌다. 따라서 빌드 성공이나 함수 2,790개라는 총량으로 분석 완결성을 주장할 수 없었다.

[Clang의 컴파일 데이터베이스 명세](https://clang.llvm.org/docs/JSONCompilationDatabase.html)는 C++ AST 도구에 번역 단위별 실제 작업 디렉터리와 컴파일 인자가 필요하며, `directory`·`file`·`arguments`를 기록하도록 설명한다. 이에 따라 명시적 StateAFL 빌드에서 호출된 컴파일 명령을 기록하고, 컨테이너 경로를 복사된 소스 경로로 대응시킨 `compile_commands.json`을 만든다. AST 실행에는 기존의 허용된 전처리·언어 옵션 추출기를 사용하며 StateAFL LLVM 플러그인을 호스트 Clang에서 다시 실행하지 않는다. 이 기록은 대상별 빌드 절차를 추측하지 않는다.

[Live555 재분석 결과](../../evidence-runs/live555-20261031-compile-db-v1/with-compile-db-analysis.json)에서 빌드 명령 218개가 기록됐고, 기록된 C++ 파일 216개 모두 AST 파싱에 성공했다. 원래 빠졌던 두 RTSP 메서드 정의도 추가됐다. 추가로 Clang AST의 `parentDeclContextId`를 사용해 소스 줄이 갈라진 외부 정의의 클래스 소유자를 복원했다. [해당 파일 직접 검사](../../evidence-runs/live555-20261031-compile-db-v1/owner-resolution.json)에서 `RTSPServer::RTSPClientConnection::handleCmd_DESCRIBE`와 서로 다른 두 클래스의 `handleCmd_SET_PARAMETER`가 구분됨을 확인했다. 관련 회귀 검사 40건이 통과했다.

이 결과는 **Live555의 소스 인덱스 누락 한 종류를 해결한 실측**이다. 전체 AST 분석에는 약 211초가 걸렸고, 빌드 기록에 없는 C++ 파일 5개는 여전히 AST 근거가 없다. 또한 빌드 결과에서 생성한 데이터베이스는 현재 별도 네트워크 빌드 결과에 저장된다. Action 워크플로우가 이를 자동으로 선행 사용하거나 RTSP Action·정상 요청 순서·적격 하네스를 생성했다는 증거는 아직 없다.

후속 [세 파일 경로 검사](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-entry-path-probe.json)는 추가 누락을 드러냈다. `readSocket`의 `recvfrom` 후보와 RTSP 명령 handler가 각각 존재했지만, 다른 번역 단위의 `incomingRequestHandler → readSocket` 호출과 기반 클래스의 가상 `handleRequestBytes` 호출이 그래프에서 연결되지 않았다. 동일한 컴파일러 링커 심볼·함수 타입의 정의가 하나일 때 파일 간 호출을 **탐색 후보**로 연결하고, AST에 기록된 상속 관계와 가상 메서드 시그니처가 일치하는 구현체도 **탐색 후보**로 연결했다. 어느 쪽도 빌드 대상 연결이나 실행 시 실제 객체 타입을 증명하지 않으므로 직접 호출 증명으로 바꾸지 않는다. 회귀 검사는 이 후보들이 탐색 경로에는 나타나면서 정적 인과 증명에는 나타나지 않음을 확인한다.

[수정 후 경로](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-entry-action-navigation.json)는 `readSocket → GenericMediaServer::ClientConnection::incomingRequestHandler → RTSPServer::RTSPClientConnection::handleRequestBytes → handleCmd_OPTIONS/DESCRIBE/SET_PARAMETER`를 소스 탐색용으로 복원했다. 또한 [후보 재검사](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-entry-candidate-cleanup.json)에서는 주석·문자열의 `recvfrom(`을 제외하여 이 함수의 실제 획득 지점 한 곳만 남았다. 이것은 Action Agent가 읽을 수 있는 경로가 생겼다는 증거이며, RTSP 명령이 원본 실행에서 정상 처리되거나 하네스가 생성됐다는 증거는 아니다.

[전체 빌드 기록 재분석](../../evidence-runs/live555-20261031-compile-db-v1/full-after-virtual-analysis.json)은 213.78초에 C++ 파일 216개를 파싱하고 실패 0개, 기록 없는 파일 5개를 보고했다. `readSocket::recvfrom` 후보는 실제 호출 한 곳이며 `handleCmd_DESCRIBE`까지의 4함수 탐색 경로가 전체 인덱스에서도 유지됐다. 호출 관계는 10,346개로 늘었지만 여기에는 증명이 아닌 `source_candidate`도 포함되므로 이 수치를 실행 도달률로 해석할 수 없다. 현재의 명시적 빌드 명령 기록과 전체 AST 분석 비용 또한 대형 데몬에 그대로 적용할 때 따로 측정해야 한다.

Action Agent의 별도 [1턴](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-action-first-turn-probe.json)·[2턴](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-action-two-turn-probe.json) 결정론적 검사에서는 `readSocket`을 연 뒤 `incomingRequestHandler`가, 그것을 연 뒤 `RTSPClientConnection::handleRequestBytes`가 차례로 다음 함수 후보에 나타났다. 이는 LLM 응답을 가짜로 주어 **후보 전달만** 확인한 검사다. [3턴 검사](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-action-three-turn-probe.json)에서 현재 함수 원문은 명령 분기를 포함하지만 `handleCmd_OPTIONS`와 `handleCmd_DESCRIBE`는 자동 frontier에 없었다. 모델은 원문에 있는 이름으로 다음 함수를 요청할 수 있으나, 실제 모델이 올바르게 선택하는지와 정상 요청 바이트를 복원하는지는 아직 시험하지 않았다.

후속 [Live555 3턴 재검사](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-action-three-turn-after-direct-nav.json)에서는 Clang이 현재 함수의 정확한 호출 위치를 기록한 직접 피호출자를 Action Agent의 **열람 선택지**에 남기도록 수정했다. `handleRequestBytes`를 연 턴에 `handleCmd_OPTIONS`(745행), `handleCmd_DESCRIBE`(757행), `handleCmd_SET_PARAMETER`(752행)가 각각 선택지로 나타났다. 이는 여러 `if` 분기를 각각 Action이나 새 작업으로 생성한 것이 아니며, 모델에 주어진 세 번째 응답은 빈 Action 목록이었다. 이 결정론적 검사 자체가 입증하는 것은 선택지 전달뿐이다. 실제 모델의 함수 선택과 원본 실행 결과는 아래 별도 실험에서 확인했다.

실제 `gpt-6-sol` 모델을 사용한 [5턴 제한 Action 시험](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-action-real-model-5turn-details.json)에서는 `readSocket → incomingRequestHandler → handleRequestBytes → parseRTSPRequestString → handleCmd_OPTIONS`를 차례로 열었다. 마지막 턴에 `RTSP OPTIONS` 후보 하나가 나왔지만 검증 상태는 `POSSIBLE`이고 완전한 요청 바이트 예시는 **0개**였다. 가상 호출의 실제 대상과 입력 값 전달이 증명되지 않았으며, 다른 명령도 아직 검사되지 않았다. 이 시험은 Action Agent만 보기 위해 `recvfrom` Entry를 수동으로 넣었고, 원본 실행·하네스 생성은 수행하지 않았다. 앞선 3파일 시험에서 파서가 선택지에 없던 이유는 시험용 컴파일 데이터베이스에서 `RTSPCommon.cpp`를 제외했기 때문이다. 5턴 시험에는 해당 파일을 포함했다.

[Input Surface Agent의 실제 모델 시험](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-input-surface-real-model-7turn.json)은 `readSocket → incomingRequestHandler → handleRequestBytes → parseRTSPRequestString`을 열고 파서 79·103·116·156행과 요청 종료 검사 675행을 근거로 `OPTIONS rtsp://127.0.0.1/test RTSP/1.0\r\nCSeq: 1\r\n\r\n` 바이트 후보 하나를 만들었다. 그 바이트를 [계측 원본 Live555에서 소켓으로 전송한 시험](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-input-surface-original-response.json)은 `RTSP/1.0 200 OK`를 받았다. 이 시험은 요청별 함수 실행 경로를 기록하지 않았으므로 응답만으로 특정 handler 실행을 증명하지 않는다.

같은 Input Surface 후보와 원본 응답을 Action Agent 첫 턴에 공급한 [연결 시험](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-action-with-surface-real-model-5turn.json)에서는 실제 모델이 파서와 `handleCmd_OPTIONS`를 열고 `RTSP OPTIONS` Action에 원본 요청 바이트 예시 하나를 붙였다. 최종 상태는 여전히 `POSSIBLE`이다. 기반 클래스의 가상 호출 대상, 입력 버퍼의 값 전달, 나머지 RTSP/HTTP 동작의 범위가 미확정이다. 이 독립 시험은 사용자가 요청한 전체 워크플로우 실행이나 `QUALIFIED` 하네스를 대체하지 않는다.

같은 실행 파일 해시와 요청 바이트로 별도의 [단일 연결 GDB 실행 검사](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-input-surface-gdb.json)를 수행했다. `RTSPServer::RTSPClientConnection::handleCmd_OPTIONS()` 중단점이 실제로 걸렸고, 호출 스택에 `handleRequestBytes`의 745행, `GenericMediaServer::ClientConnection::incomingRequestHandler`의 246행이 기록됐다. 따라서 이 **실험 입력 한 건**에서는 가상 호출이 실제 RTSP 구현으로 이어졌다는 실행 증거가 있다. 현재 Action 구조체의 `POSSIBLE`은 여전히 올바르다. 이 수동 진단을 일반 워크플로우의 요청별 귀속 증명으로 자동 연결하지 않았고, 다른 입력·데몬·반복 실행이나 생성 하네스의 적격성까지 증명하지 않기 때문이다.

[대상 실행 파일의 정의 심볼](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-binary-symbols.json)에서도 위 경로의 함수들이 확인됐다. 이는 이번 빌드에 함수가 포함됐다는 추가 근거지만, 수신된 특정 요청이 각 함수를 실행했거나 가상 호출이 그 구현체를 택했다는 증거는 아니다.

## StateAFL 직접 컴파일·링크 검사, 2026-10-31

[StateAFL의 LLVM 모드 문서](../../research-repos/StateAFL/llvm_mode/README.llvm)는 기존 LLVM 패스와 `trace-pc-guard` 두 계측 방식을 설명한다. 제품의 빌드 검사는 전자의 객체 파일 `__afl_area_ptr` 참조만 인정해, 후자의 Clang `__sancov_guards`와 콜백 참조를 놓쳤다. 후자는 StateAFL 런타임에도 구현되어 있다. 이제 새 객체에서 콜백 두 개와 guard 구간을 함께 확인한다. 한 명령으로 소스를 컴파일하고 링크해 중간 `.o`가 남지 않는 빌드는 최종 실행 파일의 guard 구간을 검사한다. 어느 경우에도 StateAFL 런타임 심볼이 함께 확인되어야 계측 증거로 인정한다. 이는 실행 전 검사일 뿐 실제 입력 커버리지의 대체 증거가 아니다.

진단용 C 서버의 [직접 빌드 기록](../../evidence-runs/stateafl-direct-link-20261031/build.json)은 새 객체 파일 없이 런타임 심볼과 최종 실행 파일의 guard 구간을 확인했다. `afl-showmap`에서 `HELLO`는 `OK`, `NOPE`는 `ERR` 응답을 받았고, [HELLO 지도](../../evidence-runs/stateafl-direct-link-20261031/hello.map)와 [NOPE 지도](../../evidence-runs/stateafl-direct-link-20261031/nope.map)는 모두 14개 항목이지만 내용이 달랐다. 같은 빌드와 원본 실행에서 확보한 TCP 시드로 만든 [캠페인 준비 기록](../../evidence-runs/stateafl-direct-link-20261031/campaign.json)은 `PREPARED_UNQUALIFIED`였다. 현재 호스트의 StateAFL 실행 전 검사 조건 때문에 이 캠페인의 퍼징 실행 결과는 없다.

이 진단에서는 원본 StateAFL의 `trace-pc-guard` 컴파일러 사본에서 현재 Clang이 거절하는 오래된 LLVM 옵션 하나를 **임시 실험 사본에서만** 제거했다. 제품이 StateAFL 컴파일러를 자동으로 설치하거나 임의 Clang 버전에 맞게 수정한다는 뜻은 아니다. 직접 컴파일·링크와 분리 컴파일 양쪽의 계측 검사, 무계측 콜백 오인 방지, 기존 캠페인 연결에 대한 회귀 검사 33건이 통과했다. 입력별 coverage 차이는 이 작은 서버에서만 확인했으며, 일반 C/C++ 데몬의 자동 빌드·요청 귀속·적격 C 하네스 생성률은 여전히 미검증이다.

## 원본 시나리오에서 C 하네스까지의 UDP 진단, 2026-10-31

작은 진단용 데몬에서 UDP 요청 `HELLO\n`을 원본 실행으로 확인한 뒤 전체 Action 워크플로우를 실행했다. [실행 요약](../../evidence-runs/daemon-matrix-udp-20261031/summary.json)은 `PROVEN_RUNTIME` 시나리오 1건, C 하네스 초안 1건, 정적 통과 0건, 적격 하네스 0건이다. [첫 초안](../../evidence-runs/daemon-matrix-udp-20261031/fuzz_target.c)은 원본 `main`을 재사용하고 별도 스레드에서 퍼징 바이트를 UDP 소켓으로 보냈다. 별도로 빌드해 `HELLO\n` 고정 입력을 1,000회 반복했을 때 종료됐고, [짧은 퍼징 기록](../../evidence-runs/daemon-matrix-udp-20261031/fuzz-1000.log)의 1,000회에서는 libFuzzer의 `cov`가 46에서 55로 증가했다. 이는 이 진단 입력에서 코드가 실행됐다는 근거이며 하네스의 전체 입력 공간 안전성이나 적격성을 증명하지 않는다.

[첫 정적 검사](../../evidence-runs/daemon-matrix-udp-20261031/static-audit-1.json)는 입력 함수가 처리 함수의 직접 호출자 경로에 없다는 이유로 `HC08/HC10`을 실패시켰다. 실제 원본의 `process_one`은 `input_read`를 호출해 버퍼에 저장한 뒤 같은 함수에서 `target_handler`를 호출한다. 두 함수가 호출 그래프상 형제인 일반적인 수신 형태이므로, 이 그래프만으로는 입력 전달을 증명할 수 없지만 곧바로 우회라고 단정하는 것도 틀리다. 정적 검사의 설명을 ‘형제 호출이며 바이트 전달 미증명’으로 고쳤고 직접 handler를 호출해 Entry를 우회하는 경우는 계속 실패하도록 회귀 검사했다. 이는 정적 통과 조건을 완화한 수정이 아니다.

별도로, 자체 네이티브 빌더는 원본 `main`을 `hc_native_original_main`으로 바꿔 링크하지만 정적 호출 검사는 이 별칭을 인식하지 못했다. 이제 그 빌더 명령이 실제로 선택된 경우에만 별칭을 원본 `main` 호출로 해석한다. 별칭이 없는 임의 빌드 명령에서는 같은 이름을 신뢰하지 않는다. 이 수정은 호출 경로가 실제로 Entry를 통과하는 경우의 오탐을 줄이지만, 위 UDP 예제처럼 Entry와 handler가 형제 호출인 경우를 성공으로 바꾸지 않는다.

초안 모델 자체도 반복 실행의 상태 분리, 서버 준비 시점, 응답 처리, 실패 시 정리 절차를 `WARN`으로 남겼다. [두 번째 시도](../../evidence-runs/daemon-matrix-udp-20261031/static-audit-2.json)는 바인드 준비 신호와 막힌 `recvfrom`을 종료할 방법을 소스에서 확인하지 못해 C 코드를 생성하지 않았다. 이는 임의의 데몬 `main`을 libFuzzer의 반복 콜백 안에 넣을 수 있다는 일반 가정이 성립하지 않음을 보여 준다. 반복 실행 [제품 trace 집계](../../evidence-runs/daemon-matrix-udp-20261031/trace-counts.json)에는 매 반복에 동일한 `request-1` 식별자가 나와 요청별 의미 비교에 사용할 수 없었다. 따라서 이 진단의 짧은 정상 실행을 `QUALIFIED`로 승격하지 않았다.

동일한 원본 증거에서 얻은 요청 하나와 이미 계측한 서버를 사용해 [StateAFL 프로세스 실행 패키지](../../evidence-runs/daemon-matrix-udp-20261031/network-campaign.json)는 `PREPARED_UNQUALIFIED`로 생성됐다. 이 대안은 C 하네스 성공으로 계산하지 않는다. 일반 데몬으로 확장하려면 입력별 완료·정리 증거를 어떤 실행 방식에서 얻을 수 있는지와 요청별 귀속을 별도로 입증해야 한다.

이번 정적 검사 관련 직접 회귀 검사 3건과 데몬 실행·네이티브 빌드 관련 검사 6건은 통과했다. 별칭 수정 전 실행한 `test_scenario_workflow.py` 전체에서는 87건 중 41건이 실패했다. 실패는 주로 현재 폐기된 `if/case`별 Action 생성 호출을 기대하거나, 요청별 trace가 없는 응답만으로 `PROVEN_RUNTIME`을 기대하는 과거 테스트에 집중돼 있다. 이 실패들을 통과로 간주하지 않았고, 현재 워크플로우의 전체 회귀 성공 주장에도 사용하지 않는다.

### SVF 값 흐름 출력으로 형제 호출을 재검사

SVF의 기존 호출 그래프만으로 `input_read`와 `target_handler` 사이의 바이트 전달을 판단할 수 없어, 같은 UDP 진단 소스를 LLVM bitcode로 컴파일한 뒤 공개 SVF의 `wpa -ander -svfg -dump-vfg`를 실행했다. [실험 기록](../../evidence-runs/daemon-matrix-udp-20261031/svfg-sibling-flow-probe.json)은 소스·그래프의 SHA-256과 분석한 818개 간선을 보존한다. SVFG에는 `process_one`의 버퍼 포인터가 `input_read` 인자를 거쳐 `recvfrom` 버퍼 인자에 이르는 경로가 있다. 그러나 `recvfrom` 버퍼 인자에서 형제 호출 `target_handler`의 버퍼 인자로 가는 경로는 없었다. 두 호출의 버퍼 주소가 같은 지역 배열에서 나온다는 사실도 수신된 **내용**이 처리 함수로 갔다는 증거는 아니다.

따라서 현재 SVF 출력으로 `HC08/HC10`을 통과시키지 않는다. 이 결과는 SVF 일반의 능력 부재를 증명하는 것이 아니라 **현재 분석 설정과 이 외부 수신 함수 모델에서 필요한 바이트 흐름 증거가 나오지 않았다**는 국소 결과다. 다음 구현은 외부 수신 함수의 메모리 쓰기 효과와 요청별 handler 귀속을 별도로 확인해야 한다. 그 전에는 형제 호출을 `UNPROVEN`으로 유지한다.

이 원인을 분리하기 위해 동일한 형제 호출 형태에서 입력 함수가 `getchar()`의 반환값을 버퍼에 **명시적으로 쓰는** [대조 소스](../../evidence-runs/daemon-matrix-udp-20261031/svfg-explicit-write-control.json)를 분석했다. 수정하지 않은 SVF는 반환값 → 버퍼 쓰기 → 함수 반환 메모리 → 처리 함수의 버퍼 읽기까지 11개 노드의 경로를 출력했다. 원본 수신 예제에서는 이 경로가 나오지 않았다. 고정한 SVF 원본의 [MRGenerator](../../research-repos/SVF/svf/lib/MSSA/MemRegion.cpp)는 외부 호출의 메모리 변경 집합을 해당 호출에 붙은 `StoreStmt`로부터 계산한다. 이 체크아웃에서 `recvfrom` 이름의 별도 모델도 찾지 못했다. 따라서 **외부 수신 호출의 버퍼 쓰기 효과가 현재 분석에 표현되지 않은 것**이 이 두 실험과 일치하는 설명이다. 이를 해결하지 않고 단순히 공유 포인터나 같은 호출자라는 이유로 정적 검사를 통과시키지 않는다.

SVF가 이미 제공하는 `-extapi` 주석 방식을 **실험용 복사본**에서 시험했다. `recvfrom`의 출력 인자에 `STORE_TOP:Arg1+`를 붙이면 [최소 예제](../../evidence-runs/daemon-matrix-udp-20261031/svfg-recv-minimal-model-probe.json)에서는 수신 호출의 쓰기 노드부터 처리 함수의 직접 버퍼 읽기까지 6개 노드 경로가 나온다. 그러나 같은 모델을 [원래 UDP 예제](../../evidence-runs/daemon-matrix-udp-20261031/svfg-recv-original-model-probe.json)에 적용하면 수신 호출의 쓰기 노드 3개는 생겨도 `target_handler`의 메모리 입력까지 경로는 0개다. 그 처리 함수는 `memcmp` 같은 다른 외부 함수로 버퍼를 읽으므로 해당 함수의 읽기 효과도 별도로 모델링해야 한다. 이 주석은 가능한 메모리 변경을 나타내는 **탐색용 과대근사**이며, 실제 요청 바이트가 처리됐다는 실행 증명으로 승격할 수 없다. 실험 복사본은 제품의 고정 SVF 체크아웃이나 하네스 적격 판정을 변경하지 않았다.

### AST로 직접 버퍼 전달 후보만 기록

별도로 제품의 [값 흐름 탐색기](../src/harnesscreator/analysis/value_flow.py)는 Clang AST가 확인한 **선언 ID**로 한 호출자가 `Entry(buf)` 뒤 `handler(buf)`를 호출하는 형태를 찾는다. Entry의 직접 출력 인자도 같은 선언 ID의 함수 매개변수여야 하며, 그 매개변수가 `read`·`recv`·`recvfrom`·`SSL_read`·`SSL_read_ex`의 문서화된 버퍼 인자로 전달돼야 한다. 버퍼 인자 위치의 근거는 [Linux `read(2)`](https://man7.org/linux/man-pages/man2/read.2.html), [Linux `recv(2)`](https://man7.org/linux/man-pages/man2/recv.2.html), [OpenSSL `SSL_read(3)`](https://docs.openssl.org/3.3/man3/SSL_read/)이다. 이는 API의 **가능한 출력 위치**만 나타낸다. 반환값, 실행 분기, 중간 덮어쓰기, 실제 요청과 handler의 귀속은 이 AST 검사로 알 수 없다.

이 후보를 하네스 정적 검사의 `HC08/HC10` 실패 설명에 함수·행 번호와 함께 붙였다. 검사 결과를 PASS로 바꾸지 않았다. 진단용 UDP 소스에서는 `process_one`의 동일한 `buf` 선언이 `input_read`와 `target_handler`에 전달되는 후보 두 개(`recv`, `recvfrom`)가 기록됐다. 이름이 같은 다른 버퍼, 중첩 범위에서 가려진 버퍼, AST 호출 근거가 없는 경우에는 후보를 만들지 않는 회귀 검사 4건을 추가했다. 관련 하네스 검사까지 합쳐 108건이 통과했다. 이 방법은 직접 버퍼 인자 형태에 한정되며, C++ 객체 필드·비동기 큐·변환된 데이터까지 분석했다는 뜻은 아니다.

### UDP 실행 산출물의 목표 함수 선택 오류 정정

위 첫 정적 검사 기록을 재검토하면서, Action에서 dispatcher와 handler가 같은 함수일 때 함수 목록의 중복 제거가 마지막 handler를 제거한다는 오류를 확인했다. 실제 UDP Action의 handler는 `target_handler`(`fn-01ecf043aa8a76b397b8`)인데, 당시 하네스 계획의 마지막 필수 함수는 진단용 `record`(`fn-f28f7d35d356970abd4f`)였다. 정적 검사와 생성기가 마지막 필수 함수를 목표로 사용하므로 **위 HC08/HC10 실패는 실제 목표 handler에 대한 판정으로 해석할 수 없다**. SVF 수동 실험은 `target_handler`를 직접 지정했으므로 이 계획 오류와 별개다.

Action의 입력 Entry와 목표 handler는 중간 함수의 중복 제거 대상에서 제외하고, handler를 항상 마지막에 두도록 수정했다. 계획 생성 시 Action 스키마의 handler와 마지막 목표 함수가 다르면 즉시 오류를 내도록 했다. 이전 UDP Action과 witness를 저장 산출물에서 다시 읽어 계획을 만들면 마지막 함수가 `target_handler`로 확인된다. 관련 회귀 검사 111건과 계획 관련 추가 검사 35건이 통과했다.

[수정된 목표 함수로 기존 초안을 재검사한 기록](../../evidence-runs/daemon-matrix-udp-20261031/corrected-target-static-audit.json)에서도 HC08/HC10은 실패한다. `process_one`이 입력 함수와 목표 함수를 형제로 호출한다는 사실과 동일 버퍼 후보는 기록됐지만, 정적 검사는 수신 바이트가 목표 함수로 전달됐다는 증거를 아직 확보하지 못했다. HC09·HC12·HC13도 실패한다. **HC14는 통과했고, 아래에서 설명하는 자체 점검 수정 후 HC20도 실패 목록에서 빠졌다**. 첫 재구성에서는 열린 함수 목록과 모델의 자체 점검을 초안에 복원하지 않아 HC14까지 실패했는데, 저장된 원본 실행 trace의 열린 함수 목록과 원래 모델 점검을 넣어 재검사하고 기록을 정정했다. 이 재검사는 **기존 초안의 목표만 정정한 진단**이며 LLM 재생성, 빌드, 반복 실행까지 통과했다는 뜻이 아니다. 적격 하네스는 여전히 0건이다.

### 생성 하네스의 송신 스레드 전달 경로

첫 C 초안은 `LLVMFuzzerTestOneInput`에서 `sender.data = hc_fuzz_request`를 설정하고 `pthread_create`로 `hc_send_request`를 시작한다. 실제 `send()` 호출은 콜백 함수 안에 있다. 현 HC10 검사는 콜백 본문까지 값을 따라가지 않고 퍼저 함수 본문 안의 직접 송신만 찾는다. 따라서 HC10의 실패 메시지인 “바이트 전달이 명시되지 않았다”는 **이 초안의 실제 코드 구조를 정확히 설명하지 못한다**. 별도 실행에서 `HELLO` 입력이 도달한 사실과 모든 변이 입력의 안전한 전달은 구분해야 한다.

고정한 SVF 이미지로 **생성된 하네스 자체**를 LLVM bitcode로 컴파일하고 `-ander -enable-tcg -svfg -dump-vfg`를 실행했다. [SVFG 진단](../../evidence-runs/daemon-matrix-udp-20261031/svfg-harness-delivery-probe.json)에서 퍼저의 `Data` 인자 노드(358)는 `sender.data` 저장 노드(228)에 도달했지만, `send()`의 버퍼 인자 노드(262)에는 경로가 없었다. 그래프는 480개 노드와 581개 간선이며 `Data`에서 도달한 노드는 16개다. `-enable-tcg` 옵션을 넣은 실험에서도 이 결과다. 이는 **해당 분석 설정에서 pthread 콜백 경계의 값 흐름을 입증하지 못한 것**이며, 실제 실행에서 값이 전달되지 않는다는 주장이 아니다. 정적 게이트를 단순 완화하거나 SVF의 이 출력을 전달 증명으로 사용할 근거는 아직 없다.

수정된 목표 계획으로 기존 빌드 초안의 원본 대비 차등 검사도 직접 실행했다. 고정 `HELLO\n` 시드를 넣으면 하네스가 실제 Entry에서 동일 바이트의 SHA-256을 두 번 기록하고 두 번 모두 목표 handler와 `OK` 결과를 기록한다. 그러나 원본 진단 데몬은 매 요청에 고정 문자열 `request-1`을 사용하므로 libFuzzer의 반복 호출 두 건을 구분할 수 없다. 차등 검증기는 `INSUFFICIENT_EVIDENCE: harness request 0 differs from the witnessed byte/Entry sequence`를 반환했다. [검사 요약](../../evidence-runs/daemon-matrix-udp-20261031/differential-recheck.json)과 [반복 실행 trace](</tmp/hc-e2e-matrix-20261031/diagnose-draft1/manual-diff-trace-2.jsonl>)가 이 사실을 보여 준다. 이 실패는 특정 진단 데몬의 trace 식별자 문제이며, 다른 데몬에서도 항상 같은 문제가 생긴다는 근거는 아니다. 식별자를 임의로 보정해 적격 판정을 통과시키지 않는다.

### 생성기 자체 점검의 불확실성 처리

실제 첫 초안의 생성기 자체 점검은 HC01..HC16을 **모두 기록**했지만, 반복 격리·서버 준비·응답·정리·빌드는 아직 검증되지 않았다고 몇 항목을 `WARN`으로 남겼다. 종전 HC20은 이 정직한 `WARN`을 “점검 항목 누락”과 같은 실패로 처리해 원인 하나를 중복 보고했다. [QuartetFuzz 공개 구현](../../QuartetFuzz/QuartetFuzz/README.md)은 소스 점검 뒤 실제 빌드·sanitizer 실행·도달 검사로 품질을 확인한다. 이 단계 구분을 현재 구조에 적용할 수 있는지 확인하고, HC20은 항목별 근거의 존재와 `FAIL` 여부만 검사하도록 수정했다. `WARN`을 `PASS`로 승격하지 않으며, 개별 HC 검사와 원본 대비 실행 검증은 여전히 미해결 항목을 막는다. 누락·중복·빈 근거·명시적 `FAIL`을 막는 [회귀 검사](../tests/test_scenario_self_audit.py)와 관련 검사 103건이 통과했다. 이번 수정만으로 UDP 초안의 HC08/09/10/12/13 실패나 적격 하네스 0건이 바뀌지는 않는다.

### 직접 버퍼 전달의 증명 보류 경로

소스 AST에서 동일 버퍼가 입력 함수와 목표 처리 함수에 차례로 전달되고, **원본 실행의 같은 요청 ID**로 Entry·목표 함수·응답이 확인된 경우에만 HC08을 `WARN`으로 기록한다. 생성 코드에 퍼저 `Data/Size`의 요청 별칭과 실제 송신 호출이 보일 때 HC10도 `WARN`으로 기록할 수 있다. 함수 선언만 있는 경우는 송신 호출로 인정하지 않는다. 이것은 원본 경로의 근거와 생성 코드의 **후보**를 구별하기 위한 것이며, 생성 하네스에서 바이트가 실제 Entry에 도달했다는 판정은 아니다.

이 두 항목만 `WARN`이고 다른 정적 항목이 모두 통과했으며, 독립 검토에서 추가 실패가 없을 때만 빌드·실행 단계로 넘긴다. 이 경로는 요청별 trace를 제공하는 `command` 검증 백엔드에서 동적 검증을 켠 경우에 한정된다. 최종 적격 판정은 생성된 바이너리와 원본 프로그램의 **요청별 차등 검증 통과**를 계속 요구한다. 정적 통과 건수와 보류 건수를 별도로 기록한다. 이 단계화는 [QuartetFuzz의 소스 점검→실행 검증 순서](../../QuartetFuzz/QuartetFuzz/README.md)를 데몬의 요청 귀속 문제에 맞춰 **별도로 적용한 설계**다. QuartetFuzz가 이 형제 호출 패턴을 입증했다는 뜻은 아니다.

원본 성공 시드 하나만 비교하면, 생성 하네스가 그 바이트를 고정 전송하고 `Data`를 무시해도 우연히 일치한다. 따라서 보류 경로의 차등 검증은 빌드된 하네스에 **원본 시드와 다른 동일 길이의 입력**을 별도 실행으로 공급한다. 생성 하네스가 원본 Entry에서 정확히 그 바이트를 수신했다는 요청별 trace를 남겨야 한다. 원본 시드를 계속 전송하거나, 요청 ID가 중복되거나, 추가 입력이 섞이면 적격 판정을 거절한다. 이 검사는 잘못된 입력의 정상 성공을 요구하지 않고 **입력 전달만** 본다. 입력을 구조적으로 제한하는 정당한 하네스도 이 보류 경로에서는 통과하지 못할 수 있으므로, 적용 범위는 원시 최종 요청을 그대로 전달한다는 현재 계획 계약에 한정된다. [차등 검증 회귀 검사](../tests/test_differential_validation.py)는 고정 시드 하네스를 거절하고 실제 입력 전달을 받아들이는 것을 확인한다.

[회귀 검사](../tests/test_scenario_sibling_defer.py)는 일치하는 원본 요청 trace에서만 HC08/HC10이 보류되고, 요청 바이트가 다르거나 송신 호출이 없으면 실패하며, 다른 정적 실패·GDB 관찰만 있는 설정에서는 다음 단계로 가지 않음을 확인한다. [기존 UDP 초안의 재검사](../../evidence-runs/daemon-matrix-udp-20261031/corrected-target-static-audit-deferred.json)에서도 HC08/HC10만 `WARN`으로 바뀌고 HC09·HC12·HC13은 `FAIL`로 남았다. 따라서 이 변경만으로 빌드나 적격 판정에 도달하지 않는다. 앞서 기록한 차등 검증의 요청 ID 중복도 해결되지 않았다.

요청 ID 중복이 차등 검증을 막는지 분리해서 보기 위해, 원본 진단 소스를 **별도 임시 복사본**으로 만들고 요청마다 ID만 증가하도록 바꿔 같은 하네스를 다시 빌드했다. [이 복사본의 검사](../../evidence-runs/daemon-matrix-udp-20261031/unique-id-differential-challenge.json)에서는 원본 시드의 두 libFuzzer 호출과 별도 입력 전달 도전이 `MATCH`였다. 따라서 첫 초안의 실제 송신 경로는 이 진단 환경에서 동작한다. 이 결과는 원본 진단 소스와 생성 하네스에 대한 정적 HC09/12/13 실패를 해소하지 않으며, 일반 데몬에서의 적격 하네스 생성 증거도 아니다.

같은 임시 복사본에 대한 [5초 동적 진단](../../evidence-runs/daemon-matrix-udp-20261031/unique-id-short-dynamic-verification.json)은 빌드, 9개 시드 반복 실행, 5개 시드 목표 함수 도달, 짧은 퍼징과 coverage 증가를 보고했다. 이 결과에서 백엔드의 `qualified=true`는 **정적 게이트 전체 통과나 최종 워크플로우 `QUALIFIED`와 다르다**. 특히 HC09/12/13의 생성기 자체 점검이 `WARN`인 이유를 해결하지 않았고, 원본 소스의 bind 실패 경로에는 닫히지 않는 descriptor가 존재한다. 짧은 동적 실행이 그 실패 경로의 안전성을 증명하지도 않는다.

## 종료 경로가 없는 UDP 서버의 생성 차단

[UDP 진단 실행](../../evidence-runs/daemon-matrix-udp-20261031/summary.json)은 원본의 요청 경로를 한 건 증명했지만, 생성한 libFuzzer 초안 2건은 정적 검사를 통과하지 못했다. 두 번째 [생성기 점검](</tmp/hc-e2e-matrix-20261031/results-udp-auto/20261031-200233-e9b006f3/harnesses/harness-807e1cae79887c0efe66/attempt-2/generator-audit.json>)은 `main`이 `recvfrom`에서 기다릴 때 매 입력의 완료와 종료·join을 보장할 근거가 없다고 `SCENARIO_STEP_BLOCKED`를 보고했다. 따라서 원본 요청이 처리됐다는 증거와 같은 프로세스에서 libFuzzer 콜백을 안전하게 반복할 수 있다는 증거를 분리해야 한다. 이는 [LLVM libFuzzer의 반복 호출 계약](https://llvm.org/docs/LibFuzzer.html)에 직접 관련된다.

기존 정적 검사는 이 명시적 생성 장애를 HC17 실패로 기록한 뒤, 생성기가 추가한 `generation_blockers` 진단 행을 HC01~HC16의 잘못된 자체 점검으로 다시 계산해 HC20도 실패시켰다. 지금은 HC17에 장애를 보존하고 정상 형식의 16개 점검 행은 별도로 검사한다. 생성기가 어떤 `generation_blockers`라도 반환하면 동일한 실행 계획의 코드 재작성으로는 그 장애가 해소되지 않으므로 반복 생성을 멈춘다. [관련 회귀 검사](../tests/test_scenario_self_audit.py)와 시나리오 생성·오케스트레이터 검사 **24건이 통과**했다. 이 수정은 실패 보고와 불필요한 재시도를 고친 것이며, UDP의 in-process 실행 경계를 해결하거나 적격 하네스를 생성한 결과는 아니다.

같은 실행에서 원본 요청열의 `PROVEN_RUNTIME` 시드는 [StateAFL 네트워크 패키지](</tmp/hc-e2e-matrix-20261031/results-udp-auto/20261031-200233-e9b006f3/research/stateafl/network-harness/campaign.json>)로 별도 준비돼 있다. 패키지는 계측 서버·입력열·명령을 묶은 실행 산출물이며, 그 상태는 `PREPARED_UNQUALIFIED`다. 실제 퍼징·원본 크래시 재현·취약성 판정은 이 준비 단계에 포함되지 않는다.

## 독립 하네스 검증의 소스 열람

하네스 생성기는 함수 원문을 열어 판단했지만, 독립 검증기의 최종 요청에는 하네스 코드·계획·원본 실행 기록·정적 검사 결과만 있었다. 따라서 독립 검증기는 원본 함수의 초기화·결과·정리 순서를 직접 확인할 수 없었다. 이제 검증기는 계획의 Entry와 필요한 처리 함수를 먼저 열고, 추가 확인이 필요하면 생성기가 열었던 함수나 호출 관계로 연결된 함수 중 하나를 요청한다. 함수 원문은 같은 검증 세션에 한 번에 하나씩 전달한다. 원문 열람이 미완료이거나 요청한 함수가 소스에 연결되지 않으면 HC14 실패로 멈춘다. 최종 검증 요청에는 열린 함수의 참조만 넣고, 앞선 세션의 원문을 사용한다.

이는 **독립 검증의 근거를 제공하는 수정**이다. 원본에 요청별 trace가 없는 일반 데몬에서 `PROVEN_RUNTIME`을 만드는 방법이나 HC09·HC12·HC13의 실패 원인을 자동으로 해결하지는 않는다. 검증 호출이 늘어날 수 있으므로 실제 실행 시간과 최종 통과율은 별도로 측정해야 한다. [회귀 검사](../tests/test_scenario_independent_source_review.py)는 순차 원문 열람, 동일 세션, 미완료·연결되지 않은 함수 요청의 차단을 확인한다.

## 관찰된 요청의 하네스 실행 진단

원본의 요청·응답과 순서 있는 함수 진입을 관찰했지만 요청별 귀속이 없는 `OBSERVED_RUNTIME`/`REPLAYED_RUNTIME` 초안은 기존에 빌드만 수행했다. 따라서 코드가 컴파일되더라도 관찰된 요청을 실제로 처리하는지 확인할 방법이 없었다. `--scenario-exploratory-drafts`와 동적 검증을 함께 켜면, HC11/HC16을 제외한 정적 검사를 통과한 초안에 **원본에서 관찰한 최종 요청 바이트 한 건**을 넣어 반복 재생한다. command 백엔드는 기존 GDB 목표 함수 도달 검사까지 시도하고, OSS-Fuzz 백엔드는 `check_build`와 `reproduce`만 수행한다. 이 진단에서는 추가 LLM 시드를 만들거나 장시간 퍼징하지 않는다. 결과는 각 시도의 `exploratory-replay.json`에 저장한다. 동적 검증을 끈 경우에는 종전과 같이 `exploratory-build.json`에 빌드 결과만 저장한다.

이 경로는 생성 하네스의 실행 가능성을 **진단**한다. 원본 요청이 특정 handler와 결과를 유발했다는 요청별 증명은 여전히 없으므로 `qualified=false`를 유지하고 최종 적격 건수에도 더하지 않는다. command 백엔드에서 GDB가 없거나 목표 도달에 실패하면 그 실패를 기록한다. OSS-Fuzz의 성공적인 `reproduce`도 목표 함수 도달을 뜻하지 않는다. 실제 Clang/ASan 재생 시험의 Linux/WSL PIE 빌드는 시작 전 간헐적으로 `-11`로 종료되어, 회귀용 작은 테스트 바이너리만 `-no-pie`로 빌드했다. 임의 대상의 빌드 플래그를 변경하지 않는다. 관련 [검증기 회귀 검사](../tests/test_exploratory_replay.py)와 [OSS-Fuzz 백엔드 회귀 검사](../tests/test_oss_fuzz_backend.py)가 동작 범위와 적격 미승격을 확인한다. 일반 데몬의 적격 하네스 생성은 아직 입증되지 않았다.

명령 백엔드의 기존 반복 검증은 같은 시드 경로를 세 번 나열하면서 `-runs=3`도 전달했다. 실제 작은 libFuzzer 바이너리에 콜백 출력 한 줄을 넣어 실행하니 이 조합은 콜백 9회, 파일 경로 한 번과 `-runs=3`의 조합은 콜백 3회였다. 반복 실행과 크래시 GDB 재생 명령에서 파일 경로를 한 번만 전달하도록 고쳤다. 이는 각 시드의 의도한 동일 프로세스 3회 검사를 유지하며 중복 실행 6회를 제거한다. 전체 워크플로우의 총 실행 시간이 얼마나 줄어드는지는 측정하지 않았다.

## Live555 C++ 네트워크 실행과 크래시 원본 재생, 2026-10-31

고정한 Live555 소스 리비전 `ceeb4f462709695b145852de309d8cd25e2dca01`의 계측 서버와, 같은 리비전을 별도로 빌드한 비계측 원본 서버를 사용했다. 실행 파일 SHA-256은 각각 `965daed32eee73032ab9901226c871023b3f0df9c00a862431bbf135a416787b`와 `6da1dc04ba96b999626acc83deb069c4718d318c7f0889f529e1cb19529129f2`로 다르다. 기존 원본 실행에서 `RTSP/1.0 200 OK`를 받은 OPTIONS 요청을 StateAFL 메시지열 형식으로 입력했다. [35초 실행 기록](../../evidence-runs/live555-20261031-stateafl-run/run-graceful.log)과 [원본 통계](../../evidence-runs/live555-20261031-stateafl-run/results-graceful/fuzzer_stats)는 1,216회 실행, 새 경로 4개, `bitmap_cvg=1.09%`, `stability=100.00%`, `unique_crashes=27`을 기록했다. 이는 **이 C++ 네트워크 서버에서 계측 입력 탐색이 시작됐다**는 증거이며 C 하네스 생성 증거는 아니다.

이 실험은 격리 컨테이너 내부에서만 ASLR을 0으로 바인드하고, 파이프형 `core_pattern` 검사를 명시적으로 건너뛰었다. StateAFL의 경고대로 이 조건의 크래시 집계는 신뢰할 수 없다. 27개 크래시 파일은 모두 유효한 메시지열이었고 변이가 실제 RTSP 요청 바이트에 있었다. 각 파일을 별도 비계측 원본 서버 프로세스의 TCP 554번 포트로 다시 전송한 [전체 재생 기록](../../evidence-runs/live555-20261031-stateafl-run/original-replay-all.json)에서는 27개 모두 전송 성공, 연결 오류 0개, 관찰된 원본 크래시 0개였다. 각 원본 서버는 1.5초 관찰 시점에 계속 실행 중이어서 판정은 **27개 모두 `ORIGINAL_REPLAY_INCONCLUSIVE`**다. 이는 크래시가 없다는 증명도, 계측 빌드의 크래시가 거짓이라는 단정도 아니다. StateAFL의 `unique_crashes=27`을 취약점이나 재현된 원본 크래시로 보고해서는 안 된다는 직접적인 반례다.

이 결과가 현재 일반 데몬 목표에 주는 한계는 분명하다. C++ 빌드와 네트워크 입력 계측은 한 대상에서 관찰됐지만, 입력별 handler 귀속, 퍼징 시점의 서버 상태 재현, 비계측 원본에서의 크래시 재현, 최종 `QUALIFIED` C/C++ 하네스는 여전히 확인되지 않았다.

이 구분을 실행 결과에도 표시하도록 `reported_unique_crashes`, `crash_handling_check_bypassed`, `reported_crashes_verified` 필드를 추가했다. StateAFL의 원시 집계가 원본 재현이나 취약점 판정으로 읽히지 않도록 `reported_crashes_verified`는 현재 항상 `false`다. [캠페인 회귀 검사](../tests/test_stateafl_campaign.py) 22건이 통과했다.

## Action 함수 탐색 범위 회귀 검사, 2026-10-31

기본 의미 기반 Action 경로는 `if/case`마다 작업을 만들지 않지만, 현재 함수에서 Clang이 확인한 **모든 직접 피호출자**를 다음 함수 목록에 보여 주는 조건이 남아 있었다. [의미 기반 검사](../tests/test_semantic_action_workflow.py)는 입력을 사용하는 `handle_a`·`handle_b` 옆에 `if (config) tick()`이 있을 때 `tick`도 선택지에 들어가는 문제, 입력과 무관한 `unrelated()` 호출과 단순 결과 보조 함수가 같은 방식으로 제시되는 문제를 재현했다. 실제 기본 경로의 검사 90건 중 4건이 이 이유로 실패했다.

직접 호출이라는 사실만으로 그 호출이 획득된 입력과 관련 있다고 볼 수 없다. 다음 함수 목록은 입력값 전달, 입력 조건의 제어, 수신 필드·콜백 연결 등 **별도로 위치를 확인한 연결 후보**로 좁혔다. 필요한 보조 함수가 현재 원문에서 확인되면 모델이 그 정확한 함수 이름을 한 개씩 요청하는 기능은 유지한다. 이 변경은 Action 완료나 도달성 판정을 완화하지 않는다. 수정 뒤 의미 기반·일반 시나리오·작업 예산 검사 **90건과 하위 검사 23건이 통과**했다. 폐기된 분기 작업 방식이나 요청 귀속 없는 응답을 성공으로 기대하는 구 테스트 파일 `test_scenario_workflow.py`는 여전히 41건 실패하며, 이를 현 워크플로우의 통과로 계산하지 않는다.

실제 C++ Live555를 다시 분석하자 위 필터만 적용했을 때 `RTSPClientConnection::handleRequestBytes`의 다음 함수 후보가 9개로 줄면서 `handleCmd_OPTIONS`도 빠졌다. 이 함수는 `parseRTSPRequestString(fRequestBuffer, ..., cmdName, ...)`로 요청을 파싱하고, 파서가 `cmdName` 출력 인자에 쓴 값을 나중에 비교해 `handleCmd_OPTIONS`를 호출한다. 해당 파서의 소스에는 `resultCmdName[i1] = c` 쓰기가 있고, Clang이 확인한 출력 인자 위치는 2·4·6·8·10·12다. [누락 당시 후보](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-action-frontier-after-guard-filter.json)와 [Live555 소스](../../evidence-runs/live555-20261031-compile-db-v1/source/liveMedia/RTSPServer.cpp)를 대조했다.

그래서 현재 입력과 이미 연결된 **생산 함수의 출력 인자 쓰기 → 호출 위치의 동일 선언 → 이후 그 선언을 검사하는 조건 → 그 안의 호출**을 Clang AST 위치와 선언 ID로 연결했다. 또 `int cmd = decode(input)`처럼 지역 변수 초기화로 이어지는 선언도 후보를 찾는 데 사용한다. 출력 인자는 실제 좌변의 배열·포인터·참조 쓰기에서만 찾으며 `array[index]`의 인덱스 변수를 출력 인자로 잘못 표시하지 않도록 검사했다. [Clang AST 문서](https://clang.llvm.org/docs/LibASTMatchers.html)는 이런 선언·호출 위치 추출의 근거다. [Clang 데이터 흐름 문서](https://clang.llvm.org/docs/DataFlowAnalysisIntro.html)가 설명하는 제어 흐름 그래프와 경로별 사실 전파는 여기서 수행하지 않았으므로, 이 관계는 **다음에 열 함수 후보**이며 요청별 값 전달이나 조건 충족의 증명이 아니다.

[같은 Live555 재검사](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-action-frontier-after-output-link.json)에서는 `handleRequestBytes`의 후보가 20개가 되었고 `parseRTSPRequestString`과 `handleCmd_OPTIONS`가 모두 남았다. 후보는 원문 열람 대상으로 제시되며, 분기마다 Action 작업을 자동 생성하지 않는다. C·C++ 합성 검사에서는 입력 유래 지역 변수의 상수 덮어쓰기, 생산 함수의 출력 인자와 입력 전용 인자 구별, 설정값만 보는 조건의 제외를 확인했다. 이 재검사만으로 OPTIONS 요청이 실제 handler까지 도달하거나 생성 하네스가 적격하다는 결론은 낼 수 없다.

이 수정 뒤 의미 기반 Action·일반 시나리오·작업 예산·C++ AST·콜백·Entry 인계 관련 검사 6개 파일에서 **145건과 하위 검사 29건이 통과**했다. [전체 검사 기록](</tmp/harnesscreator-action-regression-20261031-final2.log>)은 실행 시점의 로컬 로그다.

같은 Live555 소스에 실제 `gpt-6-sol`을 5개 함수 열람 예산으로 다시 실행한 [별도 기록](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-action-real-model-after-output-link.json)에서도 모델은 `readSocket → incomingRequestHandler → handleRequestBytes → handleCmd_OPTIONS → parseRTSPRequestString` 순서로 원문을 열고 `RTSP OPTIONS` Action 초안을 기록했다. 다만 요청한 다음 함수가 예산에서 잘려 `action_context_complete=false`와 계속 분석할 작업이 남았다. 이 시험은 수동으로 지정한 `recvfrom` Entry를 사용하며, 전체 Entry 검증·원본 실행 귀속·하네스 빌드·적격 판정은 포함하지 않는다.

### `recvfrom` 호출 이름으로 TCP 경로를 버리던 오류

Action Agent의 통로 선별은 `recvfrom`과 `WSARecvFrom`을 무조건 UDP로 간주해 TCP 실행에서 제외했다. [Linux `recv(2)` 설명](https://man7.org/linux/man-pages/man2/recvfrom.2.html)은 `recvfrom`을 연결형과 비연결형 소켓 모두에 사용할 수 있다고 명시한다. Live555 `readSocket`의 `recvfrom` 호출은 `GenericMediaServer::ClientConnection::incomingRequestHandler`에서 연결의 요청 버퍼를 채우는 데 사용된다. 따라서 API 이름만으로 UDP라고 결론 내리는 규칙은 이 C++ 서버의 TCP 요청 경로를 놓친다.

기존 공통 통로 분류기 `source_transport`를 Action Agent에도 적용했다. 채널 근거가 TCP 또는 UDP를 특정하면 반대 실행에서 제외하고, `network socket`처럼 불명확하면 둘 중 하나로 **증명하지 않은 채** 원본 실행 귀속 대상으로 남긴다. [Live555 재검사](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-recvfrom-tcp-scope-after-fix.json)는 해당 `recvfrom` Entry가 더는 TCP 분석에서 제외되지 않음을 확인했다. 의미 기반 Action·C++ AST·경계 검사 128건과 하위 검사 29건이 통과했다. 이 수정은 **후보 누락을 막을 뿐**, 그 소켓의 실제 프로토콜·가상 호출 대상·요청별 값 흐름·libFuzzer 반복 실행 가능성을 증명하지 않는다. 이 항목들의 검증과 적격 하네스는 아직 남았다.

### 외부 수신 함수의 출력 버퍼가 C++ 객체 필드인 경우

Live555 `readSocket`은 `recvfrom`으로 자신의 `buffer` 매개변수에 쓴다. 호출자 `GenericMediaServer::ClientConnection::incomingRequestHandler`는 그 매개변수 자리에 `&fRequestBuffer[fRequestBytesAlreadySeen]`를 넘긴다. 종전 탐색기는 수신 함수 내부의 직접 인자 전달만 따라가고 이 **호출자의 실제 출력 인자**를 기록하지 않았다. 같은 이름의 함수나 다른 필드를 억지로 연결하지 않도록 Clang AST에서 호출 표현식의 인자와 `MemberExpr`의 필드 선언·`this` 수신자를 읽어 연결했다. 이 AST 표현은 [Clang의 `MemberExpr` 정의](https://clang.llvm.org/doxygen/classclang_1_1MemberExpr.html)를 따른다.

새 관계는 모델의 다음 함수 목록에 `source_output_parameter_field_handoff_candidate`로 나타난다. [실제 Live555 선택지 기록](../../evidence-runs/live555-20261031-compile-db-v1/rtsp-output-field-caller-frontier.json)은 `readSocket`의 `buffer` 인자 위치 2와 호출자의 `fRequestBuffer` 필드, 호출 위치 245행을 보존한다. 로컬 배열처럼 객체 필드가 아닌 인자는 이 관계를 만들지 않는 C++ 검사와, C 구조체 필드에도 같은 규칙이 적용되는 검사를 추가했다. 관련 의미 기반 Action·C++ AST·경계·정적 점검 검사 **134건과 하위 검사 29건이 통과**했다. 이는 **분석할 다음 함수의 출처**다. 수신 성공 여부, 가상 함수의 실제 대상, 해당 필드의 이후 읽기, 같은 요청의 런타임 귀속은 이 AST 관계만으로 증명하지 않는다. Live555의 이 시험에서는 Action 0개, 적격 하네스 0개다.

### 외부 수신 함수에 호출자의 지역 버퍼를 넘기는 경우

같은 출력 매개변수 연결에서 C/C++ 호출자가 객체 필드 대신 지역 배열이나 매개변수를 넘겨도 다음 함수 원문을 열어야 한다. 앞선 필드 전용 탐색에서는 이런 호출자를 누락했다. Clang의 [`CallExpr` 인자](https://clang.llvm.org/doxygen/classclang_1_1CallExpr.html)와 [`DeclRefExpr` 선언 참조](https://clang.llvm.org/doxygen/classclang_1_1DeclRefExpr.html)를 사용해 호출 위치의 정확한 인자 위치와 선언 ID를 확인하고, `source_output_parameter_local_handoff_candidate`로 **탐색 후보만** 남긴다. 같은 이름의 C++ 함수가 한 줄에서 각각 호출되면 링크 심볼과 함수 타입까지 일치하는 호출의 인자만 선택한다.

[C++ 회귀 검사](../tests/test_cpp_ast_semantics.py)에서는 객체 필드와 지역 배열을 모두 탐색 후보로 보존하고, 같은 줄의 서로 다른 이름공간 함수 호출을 혼동하지 않는 것을 확인했다. [C 회귀 검사](../tests/test_semantic_action_workflow.py)에서는 구조체 필드와 지역 배열을 구분하고 같은 줄의 동일 함수 호출 두 건을 모두 기록하는 것도 확인했다. 두 저장 방식이 한 호출자에 함께 나타나면 혼합 후보로 제시한다. 관련 5개 검사 파일 **135건과 하위 검사 29건이 통과**했다. 이 관계는 출력 매개변수의 실제 쓰기, 수신 성공, 이후 읽기, 요청별 처리 함수 도달을 증명하지 않으며 Action 완료나 `QUALIFIED`로 승격하지 않는다. 현재 일반 데몬의 더 큰 장애는 원본 프로그램이 요청별 귀속 trace를 자동으로 내지 않는다는 점이다.

## 네트워크 퍼징 전 계측 입력 검사, 2026-10-31

[StateAFL의 `afl-showmap.c`](../../research-repos/StateAFL/afl-showmap.c)는 계측 서버 실행 후 AFL 지도를 파일로 내보내며, 장기 실행 서버가 지정한 제한 시간에 끝나도 지도를 기록한다. 이를 이용해 선택된 실행 시드가 **연결만 한 실행과 다른 계측 경로를 만드는지** 확인하는 선택적 사전 진단을 추가했다. 설정에 `afl_showmap` 실행 파일, `coverage_probe_timeout_ms`, `coverage_probe_budget_seconds`를 **함께 명시**해야 실행한다. 전체 예산이 끝나면 새 검사를 시작하지 않고 이미 시작한 `afl-showmap`이 지도를 기록하도록 기다린다. 남은 시드는 미검사로 기록하며 결과는 `INCONCLUSIVE`다. 데몬마다 준비 시간이 달라 임의의 고정 제한을 기본값으로 정하지 않았다. UDP의 시작 지연도 `startup_delay_us`가 없으면 추측하지 않고 `INCONCLUSIVE`로 남긴다.

사전 진단은 새 서버 실행에서 연결만 한 경우 두 번과 각 선택 시드 두 번을 비교한다. 첫 시드가 효과가 없어도 다른 시드를 순서대로 확인한다. 모든 선택 시드에서 지도가 비고 실행 오류도 없을 때만 `SEED_COVERAGE_NOT_OBSERVED`로 퍼징 시작을 보류한다. 일부 지도가 같거나 실행이 불안정하면 계측 부재라고 단정하지 않고 캠페인을 계속할 수 있게 한다. 결과의 `qualified_harness_claim`, `target_reach_claim`, `vulnerability_claim`은 모두 `false`다.

[제한 시간을 포함한 재실행 원자료](../../evidence-runs/stateafl-seed-probe-budgeted-20261031/summary.json)에서 계측된 TCP 진단 서버는 연결 10개·`HELLO` 14개, UDP 진단 서버는 빈 데이터그램 8개·`HELLO` 12개, C++ Live555는 연결 651개·RTSP `OPTIONS` 790개 항목으로 두 번씩 일치했다. memcached는 연결 772/770개, `SET` 다음 `GET` 1,319/1,321개로 **반복 지도가 달라 `INCONCLUSIVE`**가 됐다. 앞선 [무제한 재실행](../../evidence-runs/stateafl-seed-probe-20261031/summary.json)에서는 memcached 지도도 일치했으므로, 이 결과는 네트워크 실행 시점의 변동을 실제로 드러낸다. 개별 디렉터리에는 AFL 지도, 요청 시드, 계측 서버와 `afl-showmap`의 SHA-256 지문을 저장했다. 이 검사는 **사전 진단이 TCP·UDP·C++에서 실행됨**을 보여 주지만, 해당 시드가 특정 handler에 귀속됐다는 증거, 모든 입력에서 정상 상태가 복구된다는 증거, C/libFuzzer 하네스 적격성은 아니다. 장기 실행 서버가 포그라운드로 실행되고 지정된 포트에서 요청을 받는다는 실행 계약도 여전히 필요하다.

### 원본 요청 시드와 계측 서버 준비의 실행 순서

기존 Action 실행기는 원본 데몬에 실제로 보낸 TCP/UDP 바이트를 Action 분석 전에 `research/stateafl/manifest.json`에 저장했지만, StateAFL 계측 서버의 준비·실행은 모든 Action, 상태, 시나리오, C 하네스 작업이 끝난 뒤에 시작했다. 이는 요청 바이트가 이미 있는 경우에도 긴 의미 분석 동안 프로세스 퍼저가 놀고 있게 만들었다. 현재 실행기는 선택된 증거 등급의 시드가 일찍 존재하면 그 바이트와 manifest를 별도 스냅샷으로 고정하고, 계측 서버 준비·예비 캠페인을 Action 분석과 겹쳐 시작한다. 나중에 원본 시나리오 증거가 갱신되어도 실행 중인 캠페인의 입력은 바뀌지 않는다. **뒤에서 새 요청열이 발견되면** 예비 결과를 따로 저장하고, 같은 계측 빌드를 검증해 재사용하면서 최종 시드 전체로 두 번째 캠페인을 실행한다. 첫 시드만 사용한 예비 결과로 최종 시드의 실행을 대신하지 않는다. 두 캠페인 모두 **연구용 프로세스 퍼징 결과**이며 C 하네스 `QUALIFIED` 판정에 포함되지 않는다.

원본 프로그램의 런타임 검증과 계측 서버가 같은 포트를 사용할 수 있거나 원본의 포트를 알 수 없으면 조기 실행을 보류한다. 서로 다른 포트가 명시되었거나 실제 퍼징을 하지 않는 준비 모드에서만 겹쳐 실행한다. 상위 분석이 예외로 끝나면 진행 중인 계측 빌드·퍼징에 중단 신호를 보내 자식 프로세스 그룹을 종료한다. 소스 폴더 안에 실행 결과 폴더가 있을 경우 계측 빌드의 소스 복사에서 그 결과 폴더를 제외한다. 그렇지 않으면 이전 퍼징 결과까지 빌드 입력으로 복사되어 시간과 저장 공간을 낭비한다. [시드 스냅샷](../src/harnesscreator/runtime/stateafl_seeds.py), [실행 순서](../src/harnesscreator/orchestrator.py), [계측 빌드](../src/harnesscreator/runtime/stateafl_build.py)에 이 계약을 구현했다. 짧은 테스트로 스냅샷 불변성, 새 시드가 생겼을 때의 계측 빌드 재사용, 중단 처리, 결과 폴더 제외를 검증했다. 두 번 실행되는 경우 총 CPU 사용량은 늘 수 있으며, 실제 대형 데몬에서 걸리는 시간이 줄어드는지는 아직 측정하지 않았다.

### 원본 요청 재생 시 서버 인사말과 응답 분리

선택적 `seed_replay_timeout_ms` 진단은 원본에서 관찰한 요청을 별도 계측 서버에 보내 성공 응답 표식을 비교한다. TCP 서버가 연결 직후에 보내는 인사말에 같은 표식이 있으면, 요청 처리 결과가 없어도 성공으로 기록될 수 있었다. 이는 기존 [원본 실행기](../src/harnesscreator/runtime/scenario.py)가 인사말을 요청 전 별도로 저장하는 경계와 맞지 않았다. 시드 manifest에 `connection_prelude_hex`를 보존하고, 재생에서도 그 정확한 바이트를 먼저 확인한 뒤 요청 응답만 표식과 비교하도록 수정했다. 인사말이 다르면 `INCONCLUSIVE`로 남긴다.

시드가 많을 때 `seed_replay_timeout_ms`만 적용하면 그 시간이 시드마다 다시 시작되어 전체 실행이 시드 수에 비례해 길어졌다. 이제 이 진단을 켜려면 `seed_replay_budget_seconds`도 함께 지정한다. 전체 예산이 만료되면 새 서버를 시작하지 않고 남은 시드를 `BUDGET_EXHAUSTED`로 기록한다. 예산이 실행 중 만료되면 그 시드의 남은 대기 시간도 잘린다. 이는 분석 완결성 기준이 아니라 운영자가 명시한 진단 작업 한도이며, 시드를 건너뛰었다면 결과는 `INCONCLUSIVE`다. 실제 응답을 주지 않는 TCP 서버와 시드 두 개로 검사했을 때 두 번째 서버를 시작하지 않았고, 관련 검사 46건이 통과했다.

[LightFTP 재검사](../../evidence-runs/lightftp-20261031-prelude-separated-probe/summary.json)는 원본에서 관찰한 `220 LightFTP server v2.0a ready`를 먼저 소비하고 `NOOP` 요청 뒤의 `200 Command okay.`만 응답으로 기록했다. TCP·UDP 응답 및 인사말만 보내는 음성 반례를 포함한 관련 검사 40건이 통과했다. 이 진단은 원본과 계측 서버의 **해당 요청 한 건에 대한 응답 표식**만 비교한다. 원본에 인사말 기록이 없는데 계측 서버가 먼저 데이터를 보내는 경우, 메시지 경계가 모호한 TCP 응답, 요청별 handler 귀속, 생성 C 하네스의 반복 실행 안정성은 여전히 증명하지 않는다. `qualified_harness_claim`과 `target_reach_claim`은 `false`다.

### 생성 초안의 서버 인사말 검사 회귀

현재 코드의 LightFTP Action 재실행에서 생성된 [C++ 초안](../../evidence-runs/lightftp-20261031-current-action-recheck/20261031-225543-534570d5/harnesses/preflight/harness-c0ce7bbf0eb920468352/fuzz_target.cc)은 서버의 정확한 `220 ...\r\n` 인사말을 `recv`로 읽고 길이와 `memcmp`로 비교한 뒤에야 퍼징 요청을 보낸다. 그런데 정적 HC09 검사는 `hc_response_contains` 호출만 찾았기 때문에 이 초안을 인사말 미검사로 오판했다. 정적 검사에 **계획의 정확한 인사말 바이트, 실제 수신, 길이 및 바이트 불일치 시 반환, 요청 전송보다 앞선 검사**를 함께 요구하는 좁은 `memcmp` 경로를 추가했다. 잘못된 표식, 수신 누락, 비교 방향 반전, 반환을 우회하는 논리곱, 요청 전송 뒤의 검사를 거부하는 회귀 검사를 통과했다. 이 수정은 HC09의 관찰 범위만 바로잡는다. 같은 초안의 HC08·HC10·HC11·HC13·HC16·HC17 실패와 원본 요청별 귀속 및 반복 실행 검증은 그대로 남는다.

동일한 초안을 현재 일반 네이티브 빌더에 독립적으로 전달하자 [실행 파일](../../evidence-runs/lightftp-20261031-current-action-recheck/native-build-probe/hc-native-fuzzer)이 생성됐다. `NOOP\r\n` 고정 입력 실행에서는 원본 서버의 `CMD: NOOP` 로그가 나타나고 정상 종료했다. 한 코퍼스에서 100회 변이 실행도 종료했으며 libFuzzer의 최종 수치는 `cov=129`, `ft=130`이었다. 그러나 서버 로그에 `CMD: NOOP`이 찍힌 실행은 시작 시드 포함 소수였고, 초안의 엄격한 `NOOP`/CRLF 선행 검사가 대부분의 변이를 반환시켰다. 따라서 **빌드 가능성과 이 요청 한 건의 실행 가능성만 확인**했다. 넓은 입력 공간의 목표 함수 도달률, 요청별 인과관계, 상태 격리, 원본과의 의미 동등성 및 `QUALIFIED`는 아직 입증되지 않았다.
