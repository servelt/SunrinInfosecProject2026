# 원본 흐름과 하네스 판정: 연구 근거와 현재 적용 범위

## 이번 코드 변경과 판정

1. `Entry`는 `recv` 자체가 아니라 그 호출을 통해 외부 바이트를 처음 얻는 **프로그램 함수의 획득 위치**이다. 입력 형식은 그 함수 안에 있다고 가정하지 않는다. 직접 전달, 반환, 구조체 필드, callback, 프로젝트의 실제 사용 예제를 각각 다음 원문을 열 후보로 유지한다. `if/case`는 Action의 단위가 아니다. 이 규칙은 기존 활성 경로에서 확인했으며 이번에 증명 수준을 높였다고 주장하지 않는다.
2. 소스 함수 16개와 초기 입력 8개의 기본 상한은 이미 제거돼 있다. Action 탐색도 한 함수씩 열고, 아직 열지 못한 경로를 continuation에 남긴다. 계획의 256개 후보와 4096개 상태는 **작업 자원 한도**로 남아 있으며 초과 시 미해결로 기록한다. 이 숫자들이 분석 완결성을 뜻하지 않는다.
3. 원본 실행을 지정하고도 기본 GDB 모드만 선택한 CLI 실행은 **시작 전에 중단**한다. GDB 순서로는 `QUALIFIED`의 요청별 귀속 증거를 만들 수 없기 때문이다. 사용자가 미검증 초안을 명시적으로 요청한 경우에는 탐색을 허용한다. 초안 생성 기본값은 꺼져 있다. 이것은 실패가 예상되는 긴 실행을 막는 조치이며, trace 생성기를 새로 구현한 것은 아니다.
4. `ORIGINAL_REPRODUCED`는 동일한 오류 종류와 첫 대상 프레임이 원본 프로세스에서 다시 관찰됐다는 뜻으로 유지한다. 추가 필드 `input_attributed`는 **그 퍼징 바이트가 동일 Entry에서 실제 획득됨을 요청별 trace가 확인했는지** 나타낸다. 후속 하네스 자격 판정에서 크래시 근거를 쓰려면 둘 다 필요하다. 실행 요약의 `original_crashes_reproduced`도 이제 두 조건을 모두 충족한 건만 센다. 같은 서명만 관찰된 건은 개별 `original-replay.json`에 남는다. 초기화 중 크래시나 다른 요청의 크래시가 같은 위치에서 나왔을 가능성을 배제하지 못하면 취약점으로 자동 승격하지 않는다. 단일 실행 파일의 file/argv/env 경로에서도 원본 오류 서명을 저장한다.
5. 범용 실행 통로 선택에서 `recvfrom → UDP`, `network socket → TCP`의 자동 변환을 제거했다. Entry Verifier는 소켓 생성·연결·리스너의 실제 소스 근거가 없으면 통로를 모호하게 기록한다. 자동 통로 선택은 이 경우 `UNPROVEN`으로 남긴다. 운영자가 `--scenario-channel tcp` 또는 `udp`로 원본 Internet endpoint를 **명시**하면 모호한 소켓 Entry에 한해 해당 실행을 가설로 시험할 수 있다. 실제 바이트 획득과 handler 귀속은 요청별 원본 trace가 확인해야만 증명으로 승격한다. Unix 도메인·TLS·IPC로 확인된 Entry는 이 예외로 인터넷 소켓에 보내지 않는다. 이는 잘못된 자동 재생을 줄이지만, 통로가 미확정인 프로젝트에서는 자동 실행 가능한 후보가 줄 수 있다. 따라서 다음 일반화 평가는 **후보 보존 수와 실제 통로 확인 수**를 함께 측정해야 한다.
6. [Linux `unix(7)`](https://man7.org/linux/man-pages/man7/unix.7.html)의 pathname 기반 `AF_UNIX/SOCK_STREAM`을 별도 원본 실행 통로로 추가했다. [Python `asyncio.open_unix_connection`](https://docs.python.org/3/library/asyncio-stream.html#asyncio.open_unix_connection)으로 원본 데몬에 연결하고, `{scenario_socket_path}`를 원본 명령에 넣으면 실행마다 임시 pathname을 사용한다. 기존 경로가 있으면 삭제하거나 다른 프로세스에 접속하지 않고 미실행으로 남긴다. 같은 C fixture에서 TCP 작업 스레드, UDP, Unix 스트림이 모두 요청별 trace로 `PROVEN_RUNTIME`을 얻는지 검사했다. **이 fixture는 범용 자동 계측이나 Unix 데이터그램·seqpacket 지원의 증거가 아니다.** 경로를 고정 설정하는 데몬은 `--scenario-socket-path`가 필요하고, 요청별 trace가 없는 데몬은 여전히 엄격한 증명을 얻지 못한다.

## 적용 검증과 남은 문제

- 반례 테스트는 GDB 중단점과 로컬 전송 완료가 있어도 요청별 획득 기록이 없으면 `input_attributed=False`임을 확인한다. 기존 원본 재현 통합 테스트는 실제 원본 프로세스의 동일 크래시를 `ORIGINAL_REPRODUCED`로 보존하면서 인과관계 미증명을 기록한다.
- 통로 판정은 실제 C 데몬 fixture의 TCP 작업 스레드·UDP·Unix 스트림 요청별 trace와, 모호한 소켓·지원하지 않는 Unix 데이터그램의 음성 반례로 검사했다. 활성 테스트 묶음(`tests/test_scenario_workflow.py`의 구형 분기 워크플로우 테스트 제외)은 **601건 통과, 4건 건너뜀, 하위 검사 72건 통과**였다. 이는 해당 fixture와 현재 구현의 회귀 결과이지 대부분의 데몬에서 성공했다는 통계가 아니다.
- 이 변경은 **하네스 생성 성공률을 입증하지 않는다**. 요청별 trace를 임의 C/C++ 데몬에 자동 생성하는 범용 계측기가 아직 없고, 원본 크래시와 동일 오류 서명만으로 보안 취약점을 논리적으로 보장할 수 없다. 엄격한 판정이 필요한 입력 통로·빌드에서는 획득한 정확한 바이트, 요청 ID, handler, 결과를 원본 실행에서 연결하거나 해당 범위의 판정을 미해결로 남겨야 한다.
- 이후 성능 판단은 memcached뿐 아니라 다른 빌드·프로토콜의 데몬에서 `Entry 후보 → 재생 가능한 요청 → Action → 원본 도달 → 하네스 빌드 → 커버리지 → 크래시 원본 재생`의 수와 시간으로 측정해야 한다. 위 논문들의 성능 수치를 이 구현의 성능으로 대입하지 않는다.
