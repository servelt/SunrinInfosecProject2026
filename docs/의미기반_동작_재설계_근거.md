# 외부 동작 단위 재설계: 근거, 전이 조건, 검증 범위

## 2026-10-31: 상태 생산자별 후속 확인 요청 누락 수정

**실패 재현:** `POST_FUZZ` 단계는 퍼저가 바꾼 요청 뒤에 그 결과를 읽는 요청을 놓아 상태 변화를 관찰한다. 기존 구현은 기본 32개, 실제 오케스트레이터는 숨은 `min(64, max_candidates/4)`개를 앞에서부터 생성하고 멈췄다. 서로 다른 상태 생산자 40개가 동일한 읽기 동작으로 확인 가능한 C 수준의 계약 반례에서, 기본 제한 때문에 뒤쪽 8개 생산자의 후속 확인 후보가 0개였다. 이 수치는 연구에서 얻은 의미적 경계가 아니라 작업 상한이었다.

**외부 자료를 옮기는 범위:** [RESTler 논문](https://www.microsoft.com/en-us/research/wp-content/uploads/2021/03/RESTler.pdf)은 생산자 요청의 결과가 소비자 요청의 인자·상태에 영향을 주는 순서를 검사하고, [AFLNet 구현](https://github.com/aflnet/aflnet)은 메시지열을 시험 단위로 사용한다. 두 자료는 상태를 만드는 입력과 이후 관찰 입력의 **순서가 분석 단위**일 수 있음을 뒷받침한다. 어느 자료도 “모든 상태 생산자에 정확히 한 후보를 먼저 예약하라”는 숫자 규칙을 증명하지 않는다. 그 규칙은 우리 시스템에서 숨은 작업 상한 때문에 특정 생산자가 **전혀 시험되지 않던 반례**를 막기 위한 스케줄링 불변 조건이다. 후보의 실제 도달·성공은 이후 원본 실행에서 별도로 확인해야 한다.

**적용과 위험:** 후속 확인 후보를 생산자별로 먼저 하나씩 보존한 뒤, 설정된 후보 예산 안에서 대체 요청열을 추가한다. 오케스트레이터의 숨은 64건 제한을 제거했다. 사용자가 명시적 `limit`을 지정한 경우는 그대로 자원 제한으로 적용하고, 누락된 생산자 수를 의무로 기록한다. 40개 생산자 반례와 기존 SET→GET 사례가 통과했다. 생산자가 많으면 원본 실행 건수와 비용도 늘어나며, 이 변경은 그 요청열이 정상 흐름이라는 증거를 만들지 않는다.

## 2026-10-31: 원본 응답을 현재 요청의 성공으로 잘못 귀속한 검증 규칙 수정

**실패 반례:** 원본 프로그램이 요청 바이트를 읽고 목표 handler에 도달한 기록은 남겼지만, 응답이 그 요청에서 생성됐다는 기록은 없었다. 기존 검증기는 `OK` 같은 성공 표시가 출력에 있으면 `PROVEN_RUNTIME`으로 승격했다. 상태가 있는 서버에서는 앞선 요청의 지연 응답이나 다른 작업의 출력이 현재 요청의 출력처럼 관찰될 수 있으므로 이 결과는 요청별 정상 흐름의 증명이 아니다. 같은 요청의 handler 기록과 성공 응답 문자열을 모두 가진 실제 C 테스트 프로그램으로 오판을 재현했다.

**외부 근거와 적용 경계:** [RESTler 논문](https://www.microsoft.com/en-us/research/wp-content/uploads/2021/03/RESTler.pdf)은 요청열의 의존성을 실제 서버 응답으로 검사하지만 OpenAPI 명세와 REST 요청 경계를 사용한다. [AFLNet 공개 구현](https://github.com/aflnet/aflnet)은 서버와 실제로 주고받은 메시지열을 사용하지만, 응답 코드로 상태를 구별하는 전제와 프로토콜별 메시지 분할이 필요하다. 두 자료 모두 임의 C/C++ 데몬의 출력 문자열 하나가 특정 요청의 처리 결과라는 주장을 허용하지 않는다. 여기서는 논문의 전체 알고리즘을 복사하지 않고, 원본 프로그램에서 **동일한 요청 ID로 입력 획득 → handler → 결과가 기록되고 결과의 응답 해시가 실제 캡처와 일치하는지**를 엄격한 검증 조건으로 삼았다. [LLVM DataFlowSanitizer 문서](https://clang.llvm.org/docs/DataFlowSanitizer.html)는 값 추적에 명시적 라벨링과 계측 경계 처리가 필요함을 보여 준다. 현재 JSONL 기록은 그 수준의 자동 계측기가 아니라 시험용 C 프로그램처럼 협조적으로 계측된 빌드가 제공해야 하는 기록이다.

**코드 변경과 검사:** `RequestTraceJournal`의 결과 이벤트가 실제 응답의 SHA-256과 일치했을 때만 `semantic-response` 기록을 만들고, 단일 요청·여러 요청 실행기와 하네스 계획 검사에서 그 기록을 요구한다. 주입된 테스트 observer나 GDB 호출 순서도 `PROVEN_RUNTIME`으로 승격하지 않는다. 응답은 출력하지만 결과 이벤트를 남기지 않는 두 C 반례는 `UNPROVEN`, 결과 이벤트를 남기는 단일 요청과 SET→GET 다중 요청 반례는 `PROVEN_RUNTIME`이다. 현재 모드 관련 회귀 검사는 107개와 하위 검사 9개가 통과했다. 이전 분기별 Action 모드를 전제로 한 오래된 테스트는 현재 모드에 적용되지 않아 별도 정리가 필요하다.

**남은 핵심 한계:** 임의 데몬에서 요청 ID, handler, 결과 이벤트를 자동으로 수집하는 계측은 아직 없다. 따라서 이 강화는 오판을 줄이지만 많은 실제 데몬에서 엄격한 원본 실행 증명이 `UNPROVEN`으로 남을 수 있다. 응답 프레임 분할과 동시 요청의 귀속도 프로토콜이나 계측 없이 일반적으로 증명할 수 없다. 이 단계의 통과를 모든 하네스 크래시가 취약점이라는 보장으로 표현해서는 안 된다.

준비된 C 원본 프로그램에 결과 이벤트를 추가한 통합 검사에서는 원본 실행 증명부터 생성된 하네스의 ASan/UBSan 빌드까지 통과했다. 현재 Action 워크플로우의 관련 검사 전체는 114개와 하위 검사 9개가 통과했다. 이 통합 결과는 임의 데몬을 자동 계측한 사례가 아니다.

추가로, 소켓을 사용하는 별도 C 데몬 픽스처에서 TCP의 작업자 스레드 경유 처리와 UDP datagram 처리에 동일한 요청별 결과 기록을 적용했다. 루프백에서 두 경로 모두 `PROVEN_RUNTIME` 검사를 통과했다. 이것은 **두 전송 방식의 준비된 계측 사례**를 검증한 것이며, 임의 프로토콜의 프레임 경계·동시 요청 귀속·자동 계측을 증명하지 않는다.

현재 Action 경로의 파일·argv·환경 입력 회귀에서는 주입된 테스트 observer가 원본 요청 귀속 증명으로 기대되어 있던 오류를 바로잡았다. 실제 C 원본은 세 통로 모두 입력을 받아 `OK`를 반환하지만 요청별 결과 계측이 없으므로 `REPLAYED_RUNTIME` 또는 `UNPROVEN`만 허용한다. 루프백 권한을 허용해 옛 분기별 모드 테스트 파일을 제외한 전체 회귀를 실행한 결과 **553개 통과, 4개 건너뜀, 하위 검사 51개 통과**였다. 이는 현재 코드의 회귀 상태이며, 대부분의 실제 데몬에서 하네스가 생성된다는 통계는 아니다.

**초기 stdin 시험의 대기 낭비:** 같은 통합 검사에서 입력 형식만 확인하는 한 번짜리 가설은 성공 응답 문법이 없어 실제로 출력된 `OK`를 읽지 못하고 10초를 기다렸다. [Linux `pipe(7)`](https://man7.org/linux/man-pages/man7/pipe.7.html)은 쓰기 끝을 모두 닫으면 읽는 쪽에 EOF가 전달된다는 조건을 설명하고, [Python asyncio subprocess 문서](https://docs.python.org/3/library/asyncio-subprocess.html)는 `Process.stdin`이 닫을 수 있는 `StreamWriter`임을 명시한다. 이 조건을 **후속 입력이 없고 성공 표시도 없는 단일 stdin 가설 시험**에만 적용해, 바이트 전송 직후 stdin을 닫았다. 테스트용 프로그램은 EOF를 받고 종료하여 실제 응답 `OK`가 기록됐으며, 통합 검사는 약 35초에서 5초로 줄었다. 이는 이 픽스처에서 관찰한 수치이며 다른 프로그램의 예상 시간은 아니다. EOF를 프로토콜 종료로 다르게 해석하는 프로그램에서는 시험 결과가 달라질 수 있으므로 이 관찰을 정상 처리 증명으로 승격하지 않는다. TCP/UDP나 여러 요청 단계에는 적용하지 않았다.

## 2026-10-31: 동작 탐색에서 직접 소비자 누락과 조건 분기 폭증을 함께 수정

**실패를 재현한 코드:** `read(fd, buf, ...)` 뒤에 `parse_a(buf); parse_b(buf);`가 있으면 Input Surface는 두 원문을 읽지만 Input Action은 직접 소비자가 둘이라는 이유만으로 어느 것도 자동으로 열지 않았다. 반대로 입력값에 따라 갈리는 `if (buf[0] == n) sink_n(buf);` 30개를 전부 읽으면 과거의 분기별 장시간 탐색이 다른 이름으로 재발한다. 전자는 동작 누락이고 후자는 분석 비용 폭증이다. 두 경우를 각각 실제 C 소스 인덱스로 테스트했다.

**자료의 전제와 적용 여부:** [CodeQL C/C++ 데이터 흐름 설명](https://codeql.github.com/docs/codeql-language-guides/analyzing-data-flow-in-cpp/)은 함수 인자를 통한 값 전달을 탐색할 수 있음을 보여 주지만, 이 프로젝트의 어휘 기반 탐색기가 CodeQL의 별칭 분석을 갖췄다는 뜻은 아니다. [프로그램 의존 그래프 연구](https://www.csa.iisc.ac.in/~raghavan/CleanedPav2011/horwitz-sdg-slicing-1990.pdf)는 자료 의존과 제어 의존을 구별한다. 따라서 같은 버퍼가 인자로 전달된 호출은 **읽을 후보**이며, `if` 안의 호출까지 자동으로 하나의 외부 동작이라고 선언할 근거는 없다. 연구 알고리즘을 이식한 것이 아니라, 현재 소스 탐색기의 과소 탐색과 과다 탐색을 이 구별로 검사했다.

**수정한 동작:** 입력값이 직접 인자로 전달되고 명백한 제어문 안에 있지 않은 함수들을 같은 Entry 세션에서 한 원문씩 읽는다. `if/switch/for/while/catch` 조건식·본문과 `else` 본문 안의 직접 전달은 모델이 명시적으로 선택할 수 있는 후보와 미해결 의무로 유지한다. 이 구분은 **자동 원문 열기 순서**에만 사용하며, 함수 실행 가능성이나 요청별 인과관계를 증명하지 않는다. C/C++ 매크로, 조건 연산자, 복잡한 제어 흐름과 간접 호출에서는 소스 수준의 제어문 검출이 불완전할 수 있다. 따라서 미열람 후보를 `동작이 없다`로 처리해서는 안 된다.

**검사와 남은 위험:** `receive → parse_a → parse_b` 세 원문을 확인했고, 조건문 30개의 반례에서는 30개 작업을 만들지 않았다. 여러 줄의 `if` 안에 있는 호출은 자동으로 열지 않되 미해결 후보로 기록하고, 같은 함수의 조건문 바깥 호출은 열었다. 관련 테스트는 107개 통과, 하위 검사 6개 통과였다. 실제 데몬에서 요청 바이트 복원, 원본 요청별 handler 귀속, 하네스 빌드와 크래시 재현은 이 테스트로 증명되지 않는다. 조건문 안에 있는 실제 외부 동작을 모델이 선택하지 않으면 미해결로 남을 수 있어, 이 방식만으로 대부분의 데몬에 대한 하네스 생성률을 보장하지 않는다.

## 2026-10-31: 제공된 NetLifter 문법의 숨은 접두어 절단 제거

[NetLifter 원논문](https://qingkaishi.github.io/public_pdfs/CCS23.pdf)은 주석을 단 네트워크 parser에서 바이트 범위와 제약을 포함하는 BNF 형식 명세를 출력한다. [공개 구현](https://github.com/qingkaishi/netlifter)은 LLVM bitcode와 입력 버퍼 주석 등 별도 전제를 요구한다. 따라서 이 시스템은 NetLifter를 임의 데몬의 범용 파서 자동 발견기로 취급하지 않고, 사용자가 **실제로 제공한 출력**만 외부 형식 근거로 받아들인다.

기존 어댑터는 그 출력의 앞 128개 production/assertion만 Action Agent에 보내고, 실행 기록에도 앞 256개만 저장했다. 규칙 129번 이후가 해당 요청의 유일한 형식 근거일 경우 모델은 그 내용을 볼 수 없어 탐색 누락이 발생한다. 두 숫자는 문법 의미나 NetLifter 연구에서 얻은 상한이 아니다. 기본 전달과 실행 기록에서 절단을 제거했다. 명시적 `limit`은 미리보기 호출에만 쓸 수 있고 생략 수를 표시한다. 130개 규칙 반례에서 마지막 규칙과 assertion이 기본 payload에 남는지 확인했다.

**전이 위험:** 큰 문법 전체를 모델 문맥에 넣으면 입력 비용과 문맥 초과 위험이 커진다. 이 변경은 문법의 적용 위치, 소스 함수와의 연결, 정상 요청 실행을 자동 증명하지 않는다. 큰 문법은 규칙 참조를 보존하는 페이지별 조회가 필요할 수 있지만, 근거 없는 앞부분 절단을 다시 넣어 해결했다고 주장하지 않는다.

## 2026-10-31: 직접 입력 전달의 형제 파서 누락 수정

**재현한 문제:** 외부 `read`가 채운 같은 버퍼를 `parse_a(buf)`와 `parse_b(buf)`에 각각 직접 넘기는 C 반례에서, Input Surface Agent는 첫 파서의 입력 바이트를 얻은 뒤 두 번째 파서 원문을 열지 않았다. 모델이 첫 함수에서 `context_complete=true`를 보고하면 더 빨리 멈출 수도 있었다. 따라서 최초 입력 함수와 한 파서만 보았다는 사실을 입력 형식 목록의 완료로 사용할 수 없었다.

**외부 자료의 적용 경계:** [CodeQL C/C++ 데이터 흐름 문서](https://codeql.github.com/docs/codeql-language-guides/advanced-dataflow-scenarios-cpp/)는 포인터가 가리키는 값과 필드 전달을 구별해야 한다고 설명한다. 현재 `source_dataflow_consumers`는 그 수준의 완전한 별칭 분석기가 아니라, 소스 줄이 있는 직접 인자 전달의 **탐색 후보**만 찾는다. 그러므로 자료에서 가져온 요구는 “찾은 모든 직접 입력 소비자를 확인해야 한다”는 탐색 의무이고, “그 함수가 실제 요청에서 실행됐다”는 증명은 아니다. [Fuzz Introspector 호출 트리 문서](https://github.com/ossf/fuzz-introspector/blob/main/doc/Calltree.md)의 간접 호출 근사 한계 때문에 보고 간선이나 필드 이름 일치만으로 이 직접 경로를 확장하지 않는다. [AFLNet 구현](https://github.com/aflnet/aflnet)의 실제 요청열 재생과 달리 이 단계의 바이트는 소스 기반 가설이므로 원본 실행 이전에 정상 입력으로 승격하지 않는다.

**코드 결정과 예상 영향:** 소스 위치가 있는 직접 호출에서 입력 버퍼가 인자로 전달된 소비자가 여러 개면 같은 Entry 세션에서 **원문 하나씩** 확인한다. 첫 번째 파서에서 시험 바이트가 나와도 다른 직접 소비자를 계속 확인해 별도 바이트 가설을 보존한다. 기존의 유일한 구조체 필드 전달 후보 탐색도 유지한다. 미열람 간접 호출·필드 별칭·큐 전달은 계속 미해결로 기록한다. 직접 소비자가 많은 프로그램에서는 LLM 호출과 분석 시간이 증가할 수 있으므로, 이는 하네스 수나 성능 개선의 증거가 아니다. `if/case` 개수만큼 Action 작업을 만드는 방식은 활성화하지 않았다.

**검사:** 서로 다른 두 직접 파서를 가진 반례에서 `receive → parse_a → parse_b` 순으로 세 함수 원문이 열리고 `A`와 `B` 입력 가설이 각각 보존된다. 소스 줄을 인용하지 않은 바이트 가설은 두 파서를 읽어도 원본 시험 자격을 얻지 않는다. 구조체 필드를 통한 기존 단일 체인 회귀도 통과한다. 이 결과는 소스 탐색 누락 한 종류를 줄였다는 검사이며, 요청별 실제 handler 도달이나 `QUALIFIED` 하네스 생성 결과가 아니다.

## 2026-10-31: 원본 입력 시험의 숨은 64 KiB 제한 제거

설정의 `max_input_trial_bytes=0`은 제한 없는 입력 시험을 뜻하고, Input Surface Agent도 70,000바이트 이상의 제공 입력을 자르지 않는다. 그러나 `BoundaryTrialRunner.run()`은 모든 채널에서 65,536바이트를 넘으면 원본 실행 전에 거절했다. 같은 프로젝트 안에서 입력 후보와 실제 시험 범위가 달라지는 재현 가능한 누락이었다. [LLVM libFuzzer 문서](https://llvm.org/docs/LibFuzzer.html)는 `-max_len`을 퍼저가 생성할 입력의 길이 설정으로 다룬다. 그 값은 **원본 프로그램 시험의 수용 가능한 길이를 증명하지 않으므로**, 여기의 고정 64 KiB 제한을 정당화하지 않는다.

원본 시험기는 이제 사용자가 `max_input_trial_bytes`에 양수를 지정한 경우에만 그 길이를 적용하고, 거절 상태에 실제 설정값을 기록한다. 기본값 0에서는 70,000바이트 stdin 입력이 원본 프로그램에 그대로 전달되는지 확인했다. 65,536을 명시하면 같은 입력이 실행 전 `INCOMPATIBLE_INPUT`으로 기록된다. 큰 입력은 메모리·실행시간 비용을 늘릴 수 있으므로 실행 시간 제한과 사용자가 지정한 크기 제한은 유지한다. 이 변경은 입력 형식의 정확성이나 목표 함수 도달을 증명하지 않는다.

## 2026-10-31: 읽기 뒤 여러 콜백이 있는 경우의 탐색 중단 수정

**재현한 실패:** `read(fd, c->buf, ...)`가 있는 함수에서 상태기계의 호출자로 돌아온 다음 `c->next(c)`를 호출하고, `next`에 두 parser가 등록된 C 데몬 반례를 만들었다. 기존 탐색기는 두 parser의 소스 위치와 `c->buf` 사용을 모두 찾았지만 모델이 어느 하나를 선택하지 않으면 둘 다 열지 않고 `continuations.json`에만 남겼다. memcached의 TCP 경로도 직접 인자 전달 분석은 소비 함수 0개였지만, `try_read_network → drive_machine` 이후 같은 수신 버퍼를 보는 콜백 후보가 여러 개 있는 형태다. 따라서 `if` 분기를 더 수집해도 이 단절은 해결되지 않는다.

**자료를 옮긴 범위:** [CodeQL C/C++ 데이터 흐름 문서](https://codeql.github.com/docs/codeql-language-guides/advanced-dataflow-scenarios-cpp/)는 포인터 값과 포인터가 가리키는 값을 구별해야 하며 필드 접근이 흐름 분석의 별도 대상임을 설명한다. [Fuzz Introspector의 호출 트리 문서](https://github.com/ossf/fuzz-introspector/blob/main/doc/Calltree.md)는 간접 호출이 근사치일 수 있음을 밝힌다. 이 자료는 콜백 후보를 **다음에 읽을 원문**으로 유지할 근거이지, 특정 요청이 그 콜백을 실행했다는 증거가 아니다. [AFLNet 공개 구현](https://github.com/aflnet/aflnet)의 원본 서버에 요청열을 보내고 응답을 관찰하는 방식도 실제 클라이언트 기록을 전제로 하므로, 여기서 찾은 parser 이름만으로 정상 요청을 만들거나 성공했다고 판정하는 데 쓰지 않았다.

**적용한 범위:** 읽기 함수의 직접 호출자에서, 읽기 이후 같은 수신 객체의 함수 포인터가 호출되고 콜백 본문이 수신 필드를 참조하는 경우에만 그 소스 위치가 있는 후보를 같은 Entry 세션에서 **하나씩** 연다. 입력 바이트 가설을 찾는 Input Surface Agent와 의미 동작을 찾는 Input Action Agent 양쪽에 적용했다. 첫 parser에서 시험 바이트를 얻어도 형식이 다른 형제 콜백을 계속 열어 각각의 바이트 가설을 보존한다. 후보가 둘 이상이라는 이유로 탐색을 멈추지 않는다. 일반적인 `if`의 모든 호출이나 모든 호출 그래프 간선을 자동 순회하지 않는다. 함수 원문을 열었다는 사실은 `POSSIBLE` 탐색 근거이며, 별칭·등록 조건·실제 요청의 콜백 선택은 원본 실행 계측 없이는 확정하지 않는다.

**예상되는 영향과 검증 한계:** 이 수정은 다중 콜백 때문에 누락되던 parser 원문을 볼 수 있게 하지만, 콜백 후보가 많으면 LLM 호출 시간도 늘어난다. 후보마다 요청 바이트, 의미 동작, 선행 상태가 자동으로 생기는 것은 아니다. 두 콜백 반례에서는 `A` 가설을 찾은 뒤에도 다른 콜백을 열어 `B` 가설을 추가했고, 분기별 검증 작업은 0건이었다. `if`에서 입력을 받은 함수 30개를 호출하는 반례는 여전히 30개 Action으로 자동 확장하지 않는다. 실제 memcached 소스에서는 `try_read_network`의 2472행 수신 뒤 `drive_machine`에서 호출될 수 있는 parser 콜백 **6개**를 탐색 후보로 찾았다. 이 숫자는 실제 요청에서 여섯 콜백이 실행됐다는 뜻이 아니다. 독립된 Dropbear 소스의 `read_packet_init::read` 및 `read_packet::read`에서는 대상 버퍼가 각각 `buf_getwriteptr`, `buf_getptr` 보조 함수 안에 있어 이번 콜백 규칙의 적용 대상이 아니었다. 실제 여러 데몬의 후보 유지율, 요청 성공률, 하네스 빌드·도달·커버리지는 별도 측정이 필요하다.

**별도 버퍼 보조 함수 경로:** Dropbear 대조에서 Input Action Agent는 중첩 읽기 대상 함수 `buf_getwriteptr`·`buf_getptr`을 탐색 후보로 보았지만 Input Surface Agent는 그러지 않았다. 이 보조 함수는 `read`의 대상 포인터를 계산하는 소스 호출이므로 입력 바이트의 **저장 위치를 이해하기 위한 원문**으로 한 턴씩 연다. 저장 위치가 확인돼도 입력 형식이나 정상 요청이 확인된 것은 아니다. 중첩 `read(fd, buffer_ptr(ctx), ...)` C 반례에서 보조 함수 원문을 열고도 바이트 가설을 만들지 않은 채 미해결로 남기는지 확인했다. 이 경로는 이번 콜백 후보 확장과 독립적이며, Dropbear 세션 전체 경로를 복원했다는 뜻이 아니다.

한 읽기 함수에 직접 호출자가 여러 개 있어도 각 호출자에 읽기 이후 같은 수신 객체의 콜백 호출이 소스로 확인되면, Input Surface Agent는 그 호출자와 해당 콜백을 한 함수씩 연다. 연결 근거가 없는 호출자 여러 개 중 하나를 이름순으로 선택하지 않는다. 두 호출자·두 parser C 반례에서 다섯 함수 원문을 열고 입력 형식을 추측하지 않은 채 미해결로 남기는지 확인했다. 이 역시 호출자나 콜백의 실제 실행 경로를 증명하지 않는다.

원본 memcached 소스 인덱스에 의미 주장을 전혀 하지 않는 대체 모델을 연결한 탐색 시험에서는 `try_read_network → drive_machine` 다음에 위 parser 콜백 6개의 원문을 각각 한 턴씩 열었다. Action은 0개였고 미해결 Entry 1개가 남았다. 이는 **경로 탐색 누락**에 대한 확인이며, 입력 형식 복원이나 하네스 생성 성공의 검사는 아니다.

## 2026-10-31: 정적 동작 확정의 전제 철회

추가 반례에서 `read(fd, data, ...) → handle(data, config)`가 **직접 인자 전달**로 확인되고 `handle`이 `data`를 읽더라도, 보고된 성공 결과는 별도의 `config` 분기만으로 결정될 수 있었다. 같은 함수 안의 `read → if (data[0]) ... → if (config) return 1`도 기존 검사에서는 `PROVEN_STATIC`이었다. 두 반례는 코드 수정 전에 실제 실패하는 검사로 재현했다. 따라서 앞 절의 “직접 값을 소비하는 handler와 인라인 처리는 일괄 차단하지 않았다”는 경계도 정적 확정에는 충분하지 않았다.

[Horwitz·Reps·Binkley의 프로그램 의존 그래프](https://www.csa.iisc.ac.in/~raghavan/CleanedPav2011/horwitz-sdg-slicing-1990.pdf)는 **입력에서 결과까지** 자료 의존 또는 제어 의존 경로를 요구한다. [CodeQL의 C/C++ 전역 데이터 흐름](https://codeql.github.com/docs/codeql-language-guides/analyzing-data-flow-in-cpp/)은 이 관계를 별도 계산한다. 이 개념을 현재 코드에 그대로 넣으면 안 되는 이유도 확인했다. 우리 소스 탐색기는 변수 이름과 직접 인자 전달만 찾고, 제품 빌드의 제어 의존 그래프는 만들지 않는다. 별도 CodeQL 실험에서는 읽기 전에 복사한 구조체 포인터를 통한 소비 경로가 누락되었다. 따라서 CodeQL의 존재도 이 제품에서 모든 입력 경로를 증명해 준다는 근거가 아니다.

**적용한 판정:** 활성 의미 동작 탐색의 source locator 결과는 다음 함수의 원문을 여는 단서와 원본 실행 가설로만 사용한다. 독립적인 입력→효과 의존 증명기가 아직 연결되지 않았으므로, 이 경로에서 후보를 `PROVEN_STATIC`으로 올리지 않는다. 그 후보는 `POSSIBLE`로 유지하고 원본 요청 시험 및 요청별 trace 검증 대상으로 계속 전달한다. `if/case` 구문은 여전히 Action 단위가 아니다. 개별 Action 후보가 있는 Entry를 “동작을 발견하지 못함”으로 기록하지 않도록 누락 진단도 바꿨다.

**전이 결과와 한계:** 이 수정은 허위 정적 확정을 줄이지만 적격 하네스 수를 늘린다는 증거는 없다. 현재 일반 GDB breakpoint 순서는 요청과 handler를 묶지 못한다. 요청별 입력·연결·handler·결과를 귀속하는 원본 계측이 없는 대상에서는 후보를 `PROVEN_RUNTIME`으로 승격할 수 없고, 따라서 자격 있는 하네스를 보장할 수 없다. 대부분의 C/C++ 데몬에 적용하려면 같은 빌드의 자료·제어 의존 분석과 요청별 원본 계측을 각각 구현한 뒤, 서로 다른 프로그램에서 후보 유지율, 오탐률, 도달률, 빌드 성공률을 측정해야 한다. 하나의 정적 도구 결과만으로 정상 흐름 전체를 증명할 수 있다는 주장은 하지 않는다.

## 2026-10-31: 분기 문법과 입력 의존성을 다시 분리한 판정 수정

기존 설명의 `if (data[0] == 'A') handler()` 정적 확정 예시는 **잘못된 일반화**였다. 입력 변수가 읽기 뒤에 언급된다는 사실과 handler 호출 간선은 그 호출이 입력에 의해 제어되거나 입력을 사용한다는 증명이 아니다. 실제 반례 `if (data[0]) log_input(); if (config) handler();`에서 모델이 첫 조건과 handler의 소스 위치를 인용하면 기존 검사는 `PROVEN_STATIC`을 반환했다. 같은 반례를 `read → dispatch(data, config) → handler`로 나눠도 직접 인자 전달과 dispatcher의 변수 언급 때문에 `PROVEN_STATIC`이 나왔다. 두 반례를 먼저 실패하는 회귀로 재현했다.

[Horwitz·Reps·Binkley의 함수 간 슬라이싱](https://www.csa.iisc.ac.in/~raghavan/CleanedPav2011/horwitz-sdg-slicing-1990.pdf)은 **자료 의존과 제어 의존**을 별개의 관계로 계산한다. [CodeQL C/C++ 데이터 흐름 문서](https://codeql.github.com/docs/codeql-language-guides/analyzing-data-flow-in-cpp/)도 함수 간 값 흐름을 별도 분석으로 다룬다. 두 자료를 이 워크플로우에 그대로 복사할 수는 없다. 현재 입력 소비 탐색은 어휘 검사이며, 기존 SVF 연결은 가능한 간접 호출만 가져온다. 위 연구가 요구하는 의존 그래프는 이 코드에 없다. 따라서 연구에서 가져온 결론은 새 분석기를 구현했다는 주장이 아니라 **어휘적 연결을 증명으로 승격하지 말아야 한다**는 판정 경계다.

활성 Action 검증에서 Entry 함수의 입력 언급과 별도 handler 호출을 잇는 경우, 또는 입력을 dispatcher에 넘겼지만 handler까지의 입력 의존이 확인되지 않은 경우를 `POSSIBLE`로 유지한다. 후보는 삭제하지 않으며 요청별 원본 trace가 있다면 실행으로 확인할 수 있다. `if/case` 수만큼 Action 작업을 만드는 과거 분기 경로는 여전히 비활성이다. 직접 값을 소비하는 handler와 함수 안에서 결과를 만드는 동작은 이번 반례만으로 일괄 차단하지 않았다.

**도입 영향과 남은 반례:** 올바른 `if (data[0] == 'A') handler()`도 현재 판정만으로는 `POSSIBLE`이 된다. 이는 발견 누락이 아니라 확정의 보류지만, 요청별 trace가 없는 기본 GDB 구성에서는 결국 적격 하네스로 가지 못한다. 반대로 직접 인자 전달이나 같은 함수의 인라인 처리도 효과와 입력 사이의 의존을 모두 증명한 것은 아니다. 따라서 이 수정으로 일반 데몬의 정적 확정 또는 하네스 생성률이 개선됐다고 주장할 수 없다. 다음 단계는 실제 빌드 문맥의 값·제어 의존 분석과 요청별 원본 실행 귀속을 각각 구현·측정하는 것이다. 둘 중 어느 하나만으로 정상 흐름의 완전성을 선언해서는 안 된다.

**초기 시험 수 제한의 적용 조건:** [AFLNet](https://github.com/aflnet/aflnet)은 실제 요청열의 변형을 서버에 재생하지만, 한 Action당 특정 개수의 소스 가설을 검사하면 충분하다는 근거는 제공하지 않는다. 현재 프로젝트의 `max_scenario_candidates`는 대안 요청열의 작업 예산이다. 그런데 원본 단발 시험 호출에서 이를 `limit`으로 다시 전달하면 뒤쪽 Action은 첫 시험조차 받지 못했다. 이제 원본 단발 시험에는 `limit=None`을 주고, `max_variants_per_action=1`로 **Action당 첫 가설 하나씩**만 우선 시험한다. 후보가 예산보다 많아도 첫 시험 자리는 유지하고 추가 대안은 미해결 의무로 남긴다. 이것은 AFLNet의 성능을 옮겨 왔다는 주장이 아니라 현재 실행기의 누락을 막는 일정 규칙이다. 첫 가설이 틀리면 다른 가설이 필요하고, Action 수가 많으면 원본 실행 비용이 커질 수 있다. 3개 Action·후보 예산 1의 반례에서 3개 모두 첫 시험 후보로 남는지 확인했다.

## 2026-10-30: 조건문을 동작으로 세지 않는 판정의 실제 경계

이번 변경은 `if`나 `case`를 기능 하나로 간주하는 방식을 **활성 경로에서 계속 사용하지 않는지**와, 남아 있던 정적 판정의 허점을 검토한 것이다. 활성 `InputActionAgent`는 `semantic_action_mode=True`로 실행된다. 이 모드에서 `OperationSeed` 분기 목록은 만들지 않으며, 분기별 LLM 작업도 예약하지 않는다. 외부에 보낼 수 있는 입력 형태, 그 입력의 소비, 처리 효과를 하나의 Action 주장으로 취급한다. 조건문은 그 주장의 소스 근거가 될 수 있지만 Action의 개수를 정하지 않는다. 입력 형식이 아직 없으면 원시 입력 가설과 미해결 의무를 유지한다.

**도입 부작용과 판단 기준:** 직접 호출만 확정으로 받으면 실제 C++ 가상 호출이나 C 함수 포인터 호출의 Action이 `POSSIBLE`로 남을 수 있다. 이는 미탐색이 아니라 별도 원본 요청별 계측을 요구하는 상태다. 반대로 단순한 변수 이름 검사는 정적 확정의 충분조건이 아니다. 실제 제품에서 `PROVEN_STATIC` 후보의 원본 도달률과 `POSSIBLE`로 내려간 후보의 정상 요청 재현률을 측정해야 정확도와 누락률을 평가할 수 있다. 이번 회귀 검사는 보고 간선의 탐색/확정 분리, 내부 `if` 반례, 입력을 검사하는 `if` 대조, 소스 위치 없는 인용을 검사한다. 이 결과를 일반 데몬 하네스 생성 성공의 증거로 사용하지 않는다.

수정본의 절대 `PYTHONPATH`를 지정하고 루프백 소켓 접근이 가능한 환경에서 전체 회귀 검사 **589건 통과, 4건 건너뜀, 하위 검사 51건 통과**를 확인했다. 과거 분기별 작업의 독립 검사는 `semantic_action_mode=False`를 명시하도록 고쳤다. 같은 검사를 기본 샌드박스에서 실행하면 UDP 소켓 생성이 권한 오류로 실패하므로 그 결과를 제품 코드 회귀로 해석하지 않는다.

## 2026-10-30: 간접 호출 후보를 원본 실행으로 확인하는 경로

활성 Action 탐색은 `if/case`를 작업 단위로 쓰지 않는다. 이번에는 그 다음 단계의 누락을 수정했다. 함수 포인터·콜백을 거쳐 도달하는 Action은 정적 호출 그래프에서 `POSSIBLE`로 남는 것이 타당하지만, 기존 스케줄러는 그 Action을 **요청별 trace가 설정되어 있어도** 원본 실행 후보에서 제외했다. 정적 불확실성을 실제 실행으로 확인할 기회가 없었던 것이다.

Dropbear 계측 빌드도 기본 SSH 입출력에 성공했다. 제품의 자격 판정에는 **도입하지 않았다**. | 두 데몬의 계측 조건이 서로 다르고, 요청별 자동 라벨·handler·완료 판정은 미구현이다. 콜백은 실행한 함수도 누락할 수 있다. |

코드에서는 `scenario_attribution=trace`와 원본 실행 명령이 있는 경우에 한해, 열린 소스에 **입력 예시·소비 함수·handler·성공 위치**가 근거로 기록되고 Entry 획득 위치도 확인된 `POSSIBLE` Action을 원본 실행과 상태 분석에 넘긴다. `UNCLASSIFIED_INPUT` 원시 바이트 가설이나 소스 근거 없는 예시 바이트는 이 경로에서 제외한다. 계획된 순서는 여전히 가설이며, 실제 원본의 요청별 trace가 Entry·handler·성공을 확인하지 않으면 하네스를 승인하지 않는다. 같은 단일 요청이 앞선 원본 시험에서 이미 입증됐으면 중복 실행을 줄인다. trace가 없는 기본 GDB 모드와 source-only 모드의 자격 판정은 바꾸지 않았다.

이 변경이 해결한 것은 **정적 간접 경로가 런타임 검증 전에 버려지는 문제**다. 일반 데몬에 자동 요청별 계측을 삽입하는 문제나, 모든 가능한 Action을 빠짐없이 찾는 문제는 해결하지 못했다. memcached의 수동 라벨 시험과 압축을 끈 Dropbear 기본 실행을 일반 데몬의 동작 증명으로 확대할 수 없다. 실제 서버 2종 이상에서 같은 설정으로 `POSSIBLE → 원본 도달 → 정상 완료 → 하네스 빌드·반복 실행` 전환 수를 측정하기 전에는 생성률 개선을 주장하지 않는다.

## 2026-10-30: 입력 탐색과 원본 완료 판정의 경계 재검토

사용자가 지적한 가정은 기본 실행 경로를 다시 대조했다. Entry는 recv 같은 라이브러리 함수가 아니라 **그 호출을 포함한 제품 함수의 입력 획득 위치**다. 입력 형식이 이 함수에 전부 들어 있다고 보지 않는다. InputSurfaceAgent는 연결된 소비 함수와 프로젝트 사용 예시를 한 항목씩 열고, 복원한 바이트를 시험 가설로만 저장한다. InputActionAgent의 기본 모드는 열린 소스에서 외부 입력 형식·소비·효과를 함께 설명할 수 있는 동작을 찾는다. if나 case 하나를 별도 동작으로 예약하는 경로는 기본 모드에서 실행되지 않는다. 기본 함수 턴 제한과 초기 원본 시험 개수는 0이다. 0은 충분한 이해를 보장하는 수가 아니며, 프로젝트 함수 수를 중복 탐색 방지용 실행 상한으로 사용한다. 사용자가 설정한 양의 제한이나 시나리오 탐색 예산에 닿으면 미확인 항목을 기록한다.

C 원본 fixture에서 성공·근거 누락·응답 해시 불일치·가짜 관찰자 반례를 검사했다.

**적용 한계:** 원본의 계측 코드를 사람이 잘못 넣거나 성공 위치의 의미를 잘못 읽으면 JSONL 결과도 잘못될 수 있다. 요청별 계측이 없는 일반 C/C++ 데몬의 무응답 동작은 계속 미확정이다. 따라서 이 변경을 일반적인 정상 흐름 복원이나 크래시 무오탐 증명으로 해석할 수 없다. 실제 제품별로 요청별 계측의 정확성, 선행 상태, 하네스와 원본의 동일 입력 실행, 크래시 원본 재현을 따로 확인해야 한다.

## 2026-10-30: 분기 문법 대신 외부 입력의 효과를 단위로 삼고, 후보 경로와 확정 경로 분리

앞서 `if/case`를 별도 Action으로 만드는 작업은 기본 경로에서 제거했지만, 정적 확정 판정에 또 다른 혼동이 남아 있었다. `causal_path_from_entry`는 SVF의 `indirect_possible` 간선과 Fuzz Introspector의 `reported` 간선을 탐색할 수 있고, Action 검증도 같은 경로를 사용했다. 따라서 소스 위치가 있는 **가능한 호출 대상**을 실제로 이어지는 호출 경로처럼 취급할 수 있었다. 함수 포인터가 여러 대상을 가질 때 이는 외부 입력의 효과를 잘못 귀속시킨다.

|---|---|---|---|
| [SVF Andersen 자료](https://svf-tools.github.io/SVF-doxygen/html/classSVF_1_1Andersen.html), [LLVM Alias Analysis](https://llvm.org/docs/AliasAnalysis.html) | 포인터 분석 결과는 호출 가능한 대상의 집합과 `MayAlias`를 포함한다. 가능성은 특정 실행의 대상 확정이 아니다. | `indirect_possible`은 다음에 열 함수의 후보로 유지하되, 정적 확정 경로에는 사용하지 않는다. | SVF의 가능한 대상 집합을 실제 요청의 호출 기록으로 바꾸지 않는다. 현재 가져오는 SVF 결과에는 값 흐름의 필수 동일성 증명도 없다. |

활성 `InputActionAgent`의 지시문에서도 명명된 dispatcher를 필수로 암시하지 않게 수정했다. 입력을 읽은 뒤 파서·명령 선택 함수가 없는 경우에는 실제 첫 소비 함수 또는 효과 함수의 ID를 기존 출력 필드에 담을 수 있다. 이것은 출력 구조의 호환 방식이며 가상의 dispatcher를 만들어내라는 뜻이 아니다. `if/case`는 여전히 해당 입력이 어떤 효과에 도달하는지 설명하는 **근거 위치**로만 쓴다.

정적 판정은 이제 열린 함수 사이에 **줄 번호가 있는 직접 호출 간선**이 있을 때만 경로 조건을 통과한다. 가능한 간접 호출 또는 보고서의 간선만 있으면 Action은 삭제하지 않고 `POSSIBLE`과 구체적인 미해결 이유로 남긴다. 탐색용 `causal_path_from_entry`는 그대로 가능한 경로를 반환한다. 즉, 발견률을 위해 후보를 보존하면서 증거 수준을 과장하지 않는다. 같은 세 함수에서 `direct` 간선일 때와 `indirect_possible` 간선일 때의 판정이 달라지는 회귀 검사를 추가했다.

**남은 한계:** 직접 호출 간선도 그 요청에서 조건 분기가 실행되거나 바이트가 실제 handler까지 이동했다는 증명이 아니다. 구조체 필드, 콜백 등록과 호출, 큐, 스레드 사이의 정확한 객체 동일성을 정적으로 복원하는 기능은 아직 없다. 그래서 실제 TCP 콜백 경로의 정당한 Action이 `POSSIBLE`로 남을 수 있다. 이 경우 원본 요청별 계측과 정상 응답을 함께 확인해야 하지만, 임의 데몬에 그 계측을 자동 삽입하는 엔진도 현재 없다. 이 수정만으로 하네스 생성률이나 취약점 판정의 완전성이 향상됐다고 주장하지 않는다. 여러 실제 데몬에서 후보 보존 수, 정적 확정 수, 원본 도달 수, 최종 하네스 수를 각각 다시 측정해야 한다.

원본을 시험했지만 응답이 없는 입력은 이전에 Action 탐색으로 전달되지 않았다. 이제 그 **시도한 바이트**와 무응답 사실을 함께 전달하며, 전달 성공·handler·정상 수락은 모두 미증명으로 명시한다. 이는 AFLNet의 요청열 단위에서 입력 자체와 서버 상태 관찰을 구별하는 원칙을 우리 입력 가설 경로에 한정해 적용한 것이다. 무응답 데몬에서 성공 여부를 알아내는 새 판정기는 아니며, 전송 실패와 정상 무응답을 구별하지 못하면 계속 미해결로 남는다.

## 2026-10-30: 함수 목록 겹침을 호출 그래프 완전성으로 오인한 문제

별도 Dropbear 소스 분석에서 Fuzz Introspector와 자체 인덱서의 함수 이름·파일 일치율은 83.2%였지만, Clang C AST는 5개 파일만 파싱하고 225개 파일에서 실패했으며 분석 예산도 끝났다. 이전 코드는 이름 일치율이 임의의 80%를 넘으면 `authoritative=true`, `callers/callees=reported`로 기록했다. 이 수치는 **함수 목록의 겹침**일 뿐, 누락된 호출이나 간접 호출이 없다는 측정이 아니었다.

[Fuzz Introspector 공식 호출 트리 문서](https://github.com/ossf/fuzz-introspector/blob/main/doc/Calltree.md)는 컴파일된 LLVM 기반 트리도 근사치이며 간접 호출을 놓칠 수 있다고 명시한다. [OSS-Fuzz 공식 사용법](https://github.com/google/oss-fuzz/blob/master/docs/advanced-topics/fuzz_introspector.md)은 C/C++의 일반 분석에 LLVM LTO와 Gold를 사용한다고 설명한다. 현재 자동 분석은 하네스가 없는 시점에 실행하는 **build-free 소스 프런트엔드**이므로, 공식 빌드 기반 호출 트리의 성질을 그대로 가져올 수 없다.

따라서 80% 판정선을 삭제하고, `--require-fuzz-introspector`는 **현재 프로젝트와 함수 기록이 하나 이상 일치하는 보고서**를 요구하게 바꿨다. 일치가 전혀 없으면 다른 프로젝트의 보고서일 수 있으므로 중단한다. 이 0건 검사는 보고서의 대상 확인일 뿐, 1건만 일치하면 충분한 그래프라는 뜻이 아니다. 보고서가 있어도 전체 호출 그래프는 `partial`, `graph_closure_proven=false`, `authoritative=false`로 기록한다. 함수 일치율은 진단 수치로 남긴다. 이 변경은 누락된 경로를 찾아 주는 기술이 아니라, 불완전한 그래프를 확정 근거로 사용하지 않게 하는 교정이다. 결과적으로 일부 Entry나 Action이 더 오래 `UNRESOLVED`로 남을 수 있다. 실제 누락률과 하네스 생성률은 서로 다른 C/C++ 데몬의 빌드·실행 결과로 따로 측정해야 한다.

Action 소스 탐색에서는 모델이 **현재 연 함수**에서 연결 근거가 있는 다음 함수를 직접 요청한 경우, 과거 Entry 검증이 남긴 자동 후보 목록보다 먼저 그 요청을 연다. 자동 후보를 삭제하거나 완결성으로 간주하지 않는다. [FuzzingBrain V2의 문맥 공학](https://arxiv.org/html/2605.21779)은 필요한 함수의 문맥을 단계적으로 제공할 근거이고, [FuzzGen](https://www.usenix.org/system/files/sec20-ispoglou.pdf)은 실제 사용 코드의 인자·상태 연결을 따라가야 하는 이유를 제공한다. 어느 연구도 **우리 후보의 우선순위**가 하네스 생성률을 높인다고 증명하지는 않는다. 이 순서는 앞서 관찰한 자동 후보가 모델이 요청한 소비 함수를 지연시키는 문제에 대한 국소적인 구현 선택이며, 잘못된 모델 요청은 여전히 시간 낭비를 일으킬 수 있다. 독립 C 픽스처에서 요청 함수가 먼저 열리고 나머지 자동 후보도 이후에 열리는지를 검사했다. 실제 데몬에서의 호출 수·누락률 개선은 아직 측정되지 않았다.

## 실제 오류

기존 구현은 `if`·`switch case`를 `OperationSeed`로 만들고, dispatcher로 판정한 함수의 각 분기를 별도 LLM 작업으로 예약했다. 그러나 분기는 제어 흐름 위치일 뿐 외부 사용자가 요청할 수 있는 동작의 수를 뜻하지 않는다. 연결 상태 검사와 오류 처리도 분기이며, 하나의 동작은 여러 분기에 걸칠 수 있다. 반대로 한 분기 안에서 여러 동작을 선택할 수도 있다. 이전 memcached 실행에서 잘못 포함된 backend 응답 Entry 한 개가 분기 작업 대부분을 만들었고, per-branch 탐색이 시간을 증폭했다.

## 적용한 규칙

1. **Action 후보의 단위**는 외부 주체가 입력으로 요청할 수 있는 처리 동작이다. 후보에는 입력 예시, 입력이 들어간 Entry, 입력 형식을 해석한 소스, 실제 효과를 구현한 handler, 성공·실패 관찰 근거를 요구한다. `if`·`case`·함수 호출 하나를 Action 하나로 자동 변환하지 않는다.
2. Entry별 같은 세션에서 함수 원문을 하나씩 열고 외부 입력부터 consumer와 handler로 이동한다. 기본 실행은 분기 위치 목록을 선행 탐색 단위로 만들지 않으며 분기별 LLM 작업 큐도 만들지 않는다. 이미 열린 함수의 `if/case`는 동작을 뒷받침할 수 있는 소스 근거일 뿐이다.
   과거 분기 작업 코드는 기존 회귀 시험을 비교하기 위한 내부 호환 경로로 남아 있지만, CLI 오케스트레이터는 이를 선택하지 않는다.
3. 모델이 제시한 입력 예시가 열린 소스의 위치로 뒷받침되지 않으면 정적 확정 상태를 주지 않는다. handler·경로·응답 근거가 없거나 문맥이 끝나지 않은 후보도 `POSSIBLE`로 남긴다. 원본 프로그램의 입력 전달 및 handler 도달은 이후 원본 실행에서 검증한다.
4. 분석 턴의 기본 0은 정해진 8·16·32회에서 완료로 간주한다는 뜻이 아니다. 그래프의 함수 수를 순환 방지 상한으로 사용한다. 사용자가 양의 작업 한도를 명시하면 그 값이 적용되지만, 한도 소진은 완결성의 근거가 아니다.

## 전이의 위험과 판정 기준

- **누락 위험:** 의미 동작을 모델이 빠뜨릴 수 있다. 기본 경로는 분기 목록으로 누락을 감사하지 않는다. 현재 구현은 모든 외부 입력 처리 동작을 발견했다는 완전성 증명을 만들지 못하므로 `0 Actions`를 `0 외부 동작`으로 해석하면 안 된다. 과거 `OperationSeed`는 별도 호환 경로에서만 확인된다.
- **과대 판정 위험:** 모델의 문장과 소스 위치가 일치해도 바이트 형식이나 실제 도달이 틀릴 수 있다. `PROVEN_STATIC`도 원본 실행 성공이 아니며, 최종 자격은 원본 요청 재생·하네스 빌드·계측 도달·반복 실행으로 판단한다.
- **시간 위험:** 분기별 중복 세션은 없어졌지만 하나의 Entry 탐색이 긴 dispatcher와 여러 handler를 열면 비용이 계속 발생한다. 이를 임의 횟수로 조용히 자르거나 완료 처리하지 않고, 추후 실제 소요 시간과 누락률을 별도로 측정한다.
- **일반화 검증:** memcached 또는 한 C 픽스처의 통과만으로 대부분의 C/C++ 데몬에 적용된다고 주장할 수 없다. 명령형 TCP/UDP, 콜백 기반, 파일·stdin, 바이너리 프레임, 상태 의존 요청을 가진 **서로 다른 프로젝트**에서 Action 발견률, 미해결 비율, 원본 도달, 하네스 빌드 및 커버리지를 각각 비교해야 한다. 분기별 작업 수 감소와 기능 누락 감소는 다른 지표다.

## 이번 검증

- 다수의 내부 `if`와 두 외부 요청 동작을 가진 픽스처에서 Action 두 개가 나오고 분기별 LLM 작업은 0개인지 확인한다.
- 분기 없는 C++ 입력 처리 픽스처도 Action 후보로 남는지 확인한다. 이는 명령문 구문을 필수 조건으로 두지 않는 회귀 검사일 뿐, 실제 C++ 데몬의 도달성 증명은 아니다.
- 기존 원본 실행 → 하네스 생성 → sanitizer 빌드 통합 픽스처를 새 Entry별 의미 동작 경로로 통과시킨다.
- 관련 단위·통합 테스트 통과는 위 전이 규칙의 회귀 검사다. 실제 memcached 전체 실행이나 다수 데몬의 성능 검증 결과는 아니다.

2026-10-29 재검사에서는 활성 Action 경로와 입력 표면·원본 실행 관련 테스트 **100건 통과, 5건 건너뜀**을 확인했다. 한 C 파일로 제한한 실제 memcached `try_read_udp` 정적 감사에서는 인덱싱된 함수 95개 중 분기 단서가 0개였다. UDP 입력이 `conn` 구조체의 버퍼와 상태 머신을 거쳐 이동하므로 현재 직접 인자 전달만 추적하는 감사가 모든 consumer를 열거하지 못한다는 한계가 드러났다. 이는 Action이 없다는 증거가 아니다. 실제 전체 memcached 실행, 독립 프로젝트 비교, 최종 하네스의 자격 판정은 아직 수행하지 않았다.

## 추가 전이 검토: 분기 없는 입력과 문맥 중단

| 재검사한 질문 | 현재 동작 | 남은 검증 경계 |
|---|---|---|
| Entry 함수에 입력 형식이 전부 있어야 하나? | 아니오. `InputSurfaceAgent`는 최초 입력 획득 호출을 포함하는 함수에서 시작하고, 열린 소스가 가리키는 다른 함수 원문을 요청해 한 함수씩 연다. | 모델이 필요한 소비 함수를 요청하지 않으면 누락할 수 있다. 원시 후보는 정답으로 승격하지 않는다. |
| 16함수나 8개 요청으로 끝나나? | 기본 작업 한도는 인덱스 함수 수이며 원시 입력 시도는 기본적으로 물질화된 후보 전부가 대상이다. 사용자가 명시한 양의 한도는 작업 제한으로만 기록한다. | 시나리오 후보 수 같은 별도의 자원 제한은 결과의 완결성을 증명하지 않는다. |
| 원본 실행에 GDB가 붙나? | 설정된 귀속 방식에 따라 GDB 또는 요청 추적 계측을 시도한다. GDB breakpoint 순서만으로 요청별 인과관계를 증명하지 않는다. | 도구가 없거나 요청 귀속이 불가능하면 `UNPROVEN`으로 남는다. |
| `if/case`가 기능 하나를 뜻하나? | 기본 경로에서는 아니다. 분기 목록을 만들고 작업으로 확장하는 선행 단계를 제거했다. | 모델의 의미 동작 발견에 누락 가능성이 있어 `0 Actions`는 부재 판정이 아니다. |

독립 프로젝트인 [Dropbear의 pre-auth 퍼저](/mnt/c/dropbear/fuzz/fuzzer-preauth.c)는 `Data/Size`를 [세션 퍼징 함수](/mnt/c/dropbear/fuzz/fuzz-common.c)에 넘기고, 그 함수는 가짜 입력 FD를 만든 뒤 실제 `svr_session`을 호출한다. 퍼저 입력은 세션에서 이어지는 여러 읽기에 사용된다. 여기에는 특정 `if`나 `case`를 하나의 동작으로 먼저 고르는 절차가 필수 조건으로 들어 있지 않다. [LLVM libFuzzer 문서](https://llvm.org/docs/LibFuzzer.html)도 퍼저 엔트리에서 바이트 배열을 실제 대상 API에 전달하고 반복 실행할 것을 요구하며, 외부 명령 분기 수집을 요구하지 않는다. 이 두 자료는 **분기 목록이 하네스 생성의 필수 선행조건이라는 가정이 틀렸다는 반례**다. Dropbear의 FD 래퍼, 종료 처리, 암호화 관련 수정은 프로젝트 고유 구현이므로 범용 데몬에 복사하지 않는다.

이에 따라 기본 Action 경로는 `OperationSeed` 추출을 실행하지 않는다. `OperationSeed`는 명시적으로 선택한 과거 분기 경로에서만 사용한다. 기본 경로는 Entry 함수에서 시작해 소스 연결이 확인된 함수와 모델이 직접 요청한 함수를 한 번에 하나씩 연다. 이는 분기 없는 입력도 탐색할 수 있게 하지만 **전체 스트림 퍼징 하네스가 현재 자동으로 합격한다는 뜻은 아니다**. 현 원본 실행 검증은 성공 응답 표식과 목표 handler 귀속을 요구하므로, Dropbear형 조용한 스트림 입력은 아직 `PROVEN_RUNTIME`으로 판정할 수 없다. 해당 검증 목표와 생성 계획을 별도로 다루기 전에는 `0 Action`을 `하네스 불필요`로 해석하면 안 된다.

이 비교에서 또 하나의 실제 구현 오류를 확인했다. 오케스트레이터는 한 Entry에서 이름 붙은 Action을 하나라도 찾으면 그 Entry의 원시 입력 후보 전부를 후속 계획에서 제거했다. 한 입력 지점에서 여러 명령이나 연속 입력을 처리할 수 있으므로 Action 하나의 발견은 나머지 입력을 대표하지 않는다. 따라서 원시 입력 후보와 의미 동작 후보를 모두 유지하고 각각의 원본 실행 결과를 따로 기록하도록 수정했다. 이것은 [Dropbear 세션 퍼저](/mnt/c/dropbear/fuzz/fuzz-common.c)의 스트림 단위와 [libFuzzer 입력 계약](https://llvm.org/docs/LibFuzzer.html)을 현재 `Entry` 단위에 비교해 확인한 누락 수정이다. 다만 원시 입력 후보가 후속 계획에 남는 것과 하네스가 적격 판정을 받는 것은 구분된다.

하네스 생성 문맥에도 모델이 `context_complete=true`와 다음 함수 요청을 함께 반환하면 요청을 버리는 오류가 있었다. 필수 함수들을 먼저 열면서 그 요청을 보존하고, 요청한 소스를 실제로 연 뒤에만 완료를 인정하도록 수정했다. 32턴 기본값과 4096턴 숨은 상한은 연구에서 나온 완결성 기준이 아니므로 제거했다. 기본은 인덱싱된 함수 수를 순환 방지 한도로 삼고, 명시적 작업 한도에 걸리거나 함수가 없으면 미완료로 기록한다. 이 수정은 모델의 다음 함수 요청을 이행하는 계약 수정이지 하네스의 올바름을 증명하는 새 기법이 아니다.

전체 소스 인덱스에서 메모리 필드 작성자 후보를 재본 결과 memcached의 `try_read_udp`는 9개, `read_into_chunked_item`은 26개, `drive_machine`은 39개였다. 기존 기본 Action 탐색은 이 후보를 앞 12개로 자르고 있었으며 26개·39개 사례에서 실제로 탐색 후보를 숨겼다. 기본 탐색에서 이 12개 절단을 제거했다. 다만 이는 이름과 타입의 어휘적 일치만으로 만든 **탐색 후보**이며, 데이터 흐름의 증명이나 누락 없는 전체 프로그램 분석이 아니다. [SVF](https://github.com/SVF-tools/SVF)의 현재 연결도 간접 호출 가능성만 제공하므로 구조체 필드의 실제 객체 동일성은 별도 근거가 필요하다.

이번 변경 후 Entry·입력 표면·Action·상태 의존성·시나리오·하네스 관련 테스트는 **189건 통과, 4건 건너뜀**이었다. 명령을 처리하는 C 통합 픽스처에서는 하네스 소스 생성과 sanitizer 빌드가 통과했다. 같은 입력 지점의 별도 원시 후보를 미검증으로 유지했기 때문에 전체 결과는 `BUILD_VERIFIED_DRAFT_PARTIAL`이다. 이는 실제 Dropbear 또는 memcached의 새 하네스가 적격 판정을 받았다는 증거가 아니다.

## 2026-10-30: 일반화 경로의 가정 재검사

이번 변경은 논문의 알고리즘을 통째로 이식한 결과가 아니다. 각 자료가 **어떤 문제를 확인하는지**와 우리 데몬 워크플로우에 **어디까지 옮길 수 있는지**를 분리했다.

| 자료와 확인 가능한 내용 | 현재 워크플로우에 적용한 판단 | 적용하면 생길 수 있는 문제와 검증 경계 |
|---|---|---|
| [FuzzGen](https://www.usenix.org/system/files/sec20-ispoglou.pdf): 라이브러리를 잘못된 호출 순서와 인자로 실행하면 가짜 크래시가 생길 수 있어 실제 사용 코드를 분석한다. | 외부 입력 처리에도 실행 순서와 준비 상태의 근거가 필요하다는 **문제 정의**로 사용한다. 입력 스트림에서 `if` 하나가 기능 하나라는 근거로 사용하지 않는다. | FuzzGen의 분석 단위는 라이브러리 API 호출이다. 데몬의 외부 세션과 바이트 전달을 자동 복원했다는 결론은 낼 수 없다. |
| [RESTler](https://www.microsoft.com/en-us/research/wp-content/uploads/2021/03/RESTler.pdf): 명세에 있는 요청의 생산자·소비자 관계를 실제 응답으로 시험한다. | 명령 요청이 확인된 경우에만 선행 상태를 계획하는 데 참고한다. 응답이 없거나 프로토콜 명세가 없는 입력은 원시 입력 후보로 별도 보존한다. | RESTler는 OpenAPI 명세가 전제다. 임의 C/C++ 데몬의 `if/case` 목록을 요청 명세로 간주하면 기존 분기 폭증이 재발한다. |
| [Dropbear 공개 preauth 퍼저](/mnt/c/dropbear/fuzz/fuzz-common.c): 전체 퍼저 바이트를 가짜 FD에 넣고 실제 세션 처리로 보낸다. | 외부 동작을 명령별로 분리하지 않아도 유효한 입력 경계가 존재한다는 **반례**로 사용한다. | FD 래퍼, 상태 재설정, 종료 복구는 Dropbear 고유 코드다. 다른 데몬에 복사해도 정상 실행이 된다는 증거가 없다. |
| [Google OSS-Fuzz-Gen의 오탐 완화 연구](https://research.google/pubs/lessons-from-mitigating-false-positives-in-googles-oss-fuzz-gen/): 유효한 인자 제약과 현실적인 프로그램 시작점에서의 재검증이 필요하다. | 모델의 `confidence` 숫자를 정적 증명 조건에서 제거하고, 원본 실행·하네스 실행의 독립 증거를 계속 요구한다. | 정상 시드 한 개와 빌드 통과만으로 모든 변이 입력의 크래시가 실제 취약점이라고 결론 낼 수 없다. 크래시별 원본 프로그램 재현이 남는다. |

이 대조에서 확인한 **구현 오류와 수정**은 다음과 같다.

1. 활성 Action 검증에 모델이 스스로 적은 `confidence >= 0.70` 조건이 남아 있었다. 이 수치는 소스나 실행 증거가 아니므로 제거했다. 소스 위치·Entry에서 handler까지의 경로·입력 예시·성공 근거는 별개로 검사한다.
2. Entry에서 소비 함수로 가는 경로와 Action 근거 경로가 6회 호출자 이동 또는 64회 전방 이동에서 끊겼다. 이미 열어 둔 함수 수를 순환 방지 경계로 사용한다. 길이가 긴 실제 경로가 임의 숫자 때문에 부재로 판정되지 않게 한 변경이며, 그래프 간선의 의미가 실제 바이트 흐름이라는 증명은 아니다.
3. Action 분석이 끝났는데 하나도 나오지 않으면 `동작 없음`으로 오인할 수 있었다. 활성 경로에서는 이를 미해결 의무로 기록하고 원시 입력 후보를 계속 남긴다. 내부 조건문을 후보로 되살려 빈칸을 채우지 않는다.
4. 원본 시험의 순서를 memcached의 `CMD_SET`, `CMD_GET` 문자열로 바꾸는 전용 규칙이 일반화 경로에 남아 있었다. 이를 제거하고 Entry별 시험 기회를 균등하게 배치한다. 특정 선행 요청이 필요하면 State Dependency의 근거와 원본 실행으로 확립해야 한다.
5. 계획기의 기본 최대 8요청은 유효한 선행 요청열 길이에 대한 근거가 없었다. 기본 고정 깊이를 제거했다. 명시적 깊이 한도와 별도 탐색 상태 한도에 걸리면 미해결로 남겨야 하며, 자원 한도가 시나리오의 부재 증명이 될 수 없다.
6. 엄격 검증에서 GDB breakpoint 순서만 고른 경우, 코드상 요청 귀속이 성립하지 않아 결국 모든 원본 시험이 미검증으로 끝난다. [GDB 공식 문서](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Thread_002dSpecific-Breakpoints.html)는 일반 breakpoint가 모든 스레드에 적용됨을 명시한다. 현재 관찰 값에는 요청·연결 식별자가 없으므로 이 설정으로 전체 워크플로우를 시작하면 **정적 분석·LLM 호출 전에 오류를 낸다**. 개별 원본 실행 검증에서는 원본 프로세스를 반복해서 시작하지 않고 `UNPROVEN`으로 종료한다. 실제 요청별 추적이 있는 실행만 엄격 증명 대상으로 삼고, 탐색용 실행은 별도로 미검증 상태로 기록한다.

**아직 해결되지 않은 판정 경계:** 현재 원본 검증기는 성공 응답 문자열과 요청별 handler 귀속을 요구한다. 응답 없는 입력 스트림은 원본 프로그램이 정상 종료하거나 GDB에서 함수가 보였다는 사실만으로 `PROVEN_RUNTIME`이 되지 않는다. GDB의 시간상 breakpoint 순서는 해당 요청의 바이트가 해당 처리에 도달했다는 인과관계가 아니다. 요청별 계측 또는 다른 독립 증거를 추가하고 실제 데몬에서 시험하기 전에는 이 경로의 하네스를 적격이라고 선언하지 않는다. 또한 기본 시나리오 후보 수·탐색 상태 수는 여전히 **작업 자원 한도**이며, 모든 동작을 발견했다는 보장은 없다.

변경 직후의 회귀 검사에서는 Action·입력 후보·상태 계획·원본 추적·오케스트레이터 관련 **108건 통과, 4건 건너뜀**을 확인했다. 소켓을 직접 여는 검사 1건은 이 실행 환경에서 소켓 생성이 `Operation not permitted`로 차단되어 검증 대상에서 제외했다. 이 결과는 활성 경로의 계약 회귀 검사이며, 여러 실제 데몬에서 적격 하네스가 생성된다는 성능 증거는 아니다.

## 2026-10-30: 분기 가정 재검사와 일반화 실측

### 구현에서 확인한 추가 판정 오류

1. 모델이 최초 입력 획득 함수에서 `context_complete=true`, `actions=[]`를 반환하면, 실제 입력 버퍼가 **직접 함수 인자로 전달되는 다음 함수**가 있어도 해당 Action 세션이 종료될 수 있었다. 또한 첫 Action을 찾은 뒤에는 다른 직접 입력 소비 함수가 남아도 멈출 수 있었다. 직접 인자 흐름으로 소스 위치가 확인되는 소비 함수가 남았다면 **발견한 Action 수와 관계없이** 다음 함수 원문을 한 턴에 하나씩 더 연다. 이 경로는 `if/case` 수집에 의존하지 않는다. 직접 소비 함수가 남아 있으면 미검사 함수 ID도 기록한다. 이것은 직접 인자에 대한 **탐색 보완**이며 모든 입력 경로의 완결성 증명이 아니다.
   - 직접 인자 흐름이 없고 Action도 없다면, 소스 호출 위치가 있는 **유일한 호출자**를 반환 경로의 탐색 후보로 연다. 호출자가 여러 명이면 임의로 선택하지 않고 목록을 미해결로 남긴다. 반환 경로로 찾은 Action은 구조체 버퍼의 실제 값 흐름을 별도로 증명하지 못하면 `POSSIBLE`로 유지한다. 직접 인자 흐름이 확인되지 않은 모든 비루트 Action에 같은 판정을 적용한다. 단순한 호출 순서를 입력 바이트의 인과관계로 승격하지 않는다.
2. 선행 요청 탐색이 상태 수 제한에 도달했는데 결과가 없으면, 차단 사유가 `no producer sequence satisfies`라고 적혔다. 탐색하지 못한 상태가 남은 경우에는 `producer sequence unresolved`라고 별도로 기록한다. 한도에 도달했다는 사실을 생산자 부재의 증거로 사용하지 않는다.
3. 정적 인덱스와 Fuzz Introspector 준비 단계가 `runs-*` 같은 결과 디렉터리까지 재귀 탐색한 후에야 제외했다. Python의 [공식 `os.walk` 문서](https://docs.python.org/3/library/os.html#os.walk)가 제공하는 상향식 이전의 디렉터리 가지치기로 바꿨다. memcached 작업 디렉터리에서 Fuzz Introspector 대상 소스는 변경 전후 **161개로 동일**했고 파일 목록 탐색 시간은 **23.0초 → 1.9초**였다. 이 수치는 파일 발견 단계만의 실측이며 전체 워크플로 시간 단축률이 아니다. 정적 인덱서가 놓쳤던 `.c++` 소스 확장자도 Fuzz Introspector 입력 목록과 일치시켰다.

추가로 결과물이 섞인 같은 디렉터리에서 정적 인덱스가 *모든 파일*마다 `Path.resolve()`를 호출하던 경로를 제거했다. 이 수정 전에는 `HC_C_AST_BUDGET_SECONDS=0` 조건의 전체 인덱스 실행을 90초가 지나 중단했고, 수정 후에는 함수 **2,438개를 15.6초**에 색인했다. 두 값은 동일한 완료 실행의 전후 비교가 아니므로 정식 속도 향상 비율로 사용하지 않는다. 15.6초에는 Clang AST 보강을 포함하지 않는다.

SVF의 비트코드 탐색도 같은 방식으로 결과 디렉터리를 재귀 방문하기 전에 제외한다. `build/`의 비트코드는 계속 포함하고 `runs-*` 아래의 과거 비트코드는 제외하는 회귀 검사를 추가했다. 이는 SVF의 간접 호출 분석이 빨라질 수 있는 파일 탐색 수정이지, 부족한 구조체 값 흐름을 SVF가 새로 증명한다는 뜻이 아니다.

## 2026-10-30: 실제 데몬의 중복 함수명과 콜백 탐색

원본 memcached에는 서버용 `memcached.c`와 테스트용 `testapp.c`에 각각 `tcp_read`가 정의되어 있다. 서버의 `conn_new`와 테스트 클라이언트의 `connect_server`가 각각 `c->read = tcp_read`로 등록한다. 기존 콜백 탐색은 인덱스 전체에서 함수명이 유일하지 않으면 **두 등록을 모두 버렸다**. 서버 `tcp_read`에서 `try_read_network`로 이동할 후보가 없었으므로, Entry를 찾고도 정상적인 입력 처리 쪽 문맥을 열지 못하는 실제 누락이었다.

[C 언어 N1570의 번역 단위·연결 규칙](https://www.sigbus.info/n1570)과 [Clang의 컴파일 데이터베이스 명세](https://clang.llvm.org/docs/JSONCompilationDatabase.html)는 소스 파일과 빌드 문맥을 구분해야 하는 근거다. 같은 파일에서 유일한 함수 정의가 있으면 해당 등록의 **탐색 대상**으로 우선 선택한다. 단, 이 소스 이름 매칭이 실제 포인터 객체·런타임 호출을 증명하는 것은 아니다. 결과는 호출 그래프의 확정 간선이 아니라 `lexical_callback_navigation_only`로 남는다.

빌드 대상 이름이 다른 함수를 모두 제거하는 방법도 시험했다. CMake의 `add_library(callbacks)`에서 콜백을 등록하고 `add_executable(server)`에서 호출하는 정상 fixture가 즉시 누락되었다. 따라서 빌드 대상의 일치 여부는 탐색 순서의 단서로만 기록하고, 서로 다른 대상의 후보도 보존한다. 링크 관계가 입증되지 않은 교차 대상 후보 역시 확정 간선으로 승격하지 않는다.

수정 후 실제 memcached 소스 인덱스에서 서버 `tcp_read`부터 `drive_machine → try_read_network`, 그리고 `drive_machine → try_read_command_ascii`의 **탐색 경로**를 얻었다. 빌드 대상 이름은 후보의 우선순위에만 쓰고, 다른 대상의 라이브러리가 서버에 연결될 가능성은 제거하지 않는다. 기존의 콜백 경로 기본 깊이 8·16과 방문 수 4096도 제거하고, 유한한 그래프를 한 번씩 오르내리는 탐색으로 바꿨다. 20단계 상승과 20단계 하강 fixture에서 42개 함수 경로를 찾았다. 실제 memcached의 서버 `tcp_read`→텍스트 파서 후보 경로 계산은 정적 인덱싱 이후 **0.39초**였다.

이 경로는 콜백 필드의 이름과 등록·호출 위치를 잇는 후보이며, `c->rbuf`의 바이트가 파서에 전달되었다는 값 흐름 증명이 아니다. 그 증명과 원본 실행 귀속은 여전히 별도로 필요하다. 관련 회귀 검사는 **130건 통과, 4건 건너뜀**이다.

### 후보가 발견되어도 Action Agent가 열지 않던 종료 조건

그래프가 위 콜백 후보를 반환하더라도, Input Action Agent는 `tcp_read`에서 모델이 `actions=[]`, `context_complete=true`라고 답하면 다음 함수를 열지 않았다. 직접 인자 추적도 `tcp_read`의 `buf`가 호출자의 `c->rbuf`에 대응한다는 것을 처리하지 못한다. 따라서 그래프 복구만으로는 실제 탐색 누락이 해결되지 않았다.

활성 Action 경로에 소스 위치가 있는 콜백 호출 후보를 **한 함수씩** 열도록 연결했다. 같은 빌드 대상 후보를 먼저 보고, 대상 이름이 다른 후보는 라이브러리 연결 가능성이 있으므로 Action이 아직 없을 때 이어서 본다. 남은 후보는 ID와 함께 미완료 의무로 기록한다. 이는 [FuzzingBrain V2의 함수별 분석과 호출 관계를 통한 문맥 탐색](https://arxiv.org/html/2605.21779)을 이 프로젝트의 콜백 탐색에 적용한 설계 선택이다. 논문이 이 콜백 규칙이나 하네스 생성 성공을 검증했다는 주장은 하지 않는다.

원본 memcached 소스를 색인하고 세 번의 빈 모델 응답을 넣은 재현에서 열린 함수는 `tcp_read → try_read_network → read_into_chunked_item`이었다. 명시한 세 턴 한도 뒤 `drive_machine` 등 남은 후보가 미완료로 기록되었다. 입력 바이트의 구조체 필드 이동은 여전히 정적 증명되지 않으며, 값 흐름 분석과 원본 실행 요청 귀속을 별도로 마련해야 한다. 관련 회귀 검사는 **131건 통과, 4건 건너뜀**이다.

## 2026-10-30: 포인터 반환 함수를 거치는 입력 버퍼 재검사

독립 데몬 Dropbear의 `packet.c:183`은 `read(ses.sock_in, buf_getptr(ses.readbuf, maxlen), maxlen)` 형태로 입력을 받는다. 기존 bootstrap 인덱서는 `buffer.c:180`의 `unsigned char* buf_getptr(...)` 정의를 색인하지 못했다. `char*`처럼 반환형과 `*`가 붙은 일반 C 선언을 놓친 것이다. [C11 초안 N1570의 함수 호출 규정](https://www.sigbus.info/n1570)은 함수 호출식의 결과형이 반환형이라는 근거를 제공하지만, 호출식의 결과 포인터가 **어느 메모리를 가리키는지**까지 증명하지 않는다. 이 차이를 유지해야 한다.

인덱서가 공백 없는 포인터 반환 선언도 찾도록 고쳤다. 활성 Action 경로에서는 획득 함수의 버퍼 인자가 포인터 반환 호출식이면 해당 helper 원문을 한 함수씩 열 수 있게 했다. 동시에 `buf_getptr(ses.readbuf, ...)` 안의 `readbuf` 식별자를 곧바로 `read`의 직접 기록 대상이라고 단정하던 lexical 추적을 막았다. helper 열기는 **탐색**이며, 버퍼 별칭이나 이후 consumer까지의 값 흐름은 여전히 미확정으로 남긴다. 이 변경은 특정 `buf_getptr` 이름이나 Dropbear 명령을 정적으로 지정하지 않고, 실제 소스의 호출식과 반환형을 검사한다.

적용 검증에서는 Dropbear 원본 소스를 다시 색인해 함수 **1,481개**, 간선 **4,382개**를 얻었다. `read_packet → buf_getptr` 간선이 잡혔고, 빈 모델 응답을 사용한 두 턴 시험에서도 두 함수 원문이 차례로 열렸다. 직접 기록 대상은 미확정으로, Action 부재도 미확정으로 기록됐다. 또한 한 함수에 획득 API 호출이 여러 개 있을 때 Entry 줄 번호와 일치하는 호출이 없으면 모든 호출을 입력 지점으로 취급하던 오류를 고쳤다. 이제 정확한 줄을 찾지 못하면 흐름을 미확정으로 둔다. 관련 회귀 검사는 **134건 통과, 4건 건너뜀**이다. 이 시험은 네트워크 요청을 실행하거나 Dropbear용 하네스의 빌드·도달·커버리지를 검증한 것이 아니다. 매크로, 간접 호출, 포인터 별칭을 포함한 전체 흐름은 별도 분석과 원본 실행 증거가 필요하다.

전체 테스트도 실행해 보았으나 이 샌드박스에서 LeakSanitizer가 `ptrace` 제한으로 치명 오류를 내는 네이티브 퍼저 실행 검사가 있어 `ASAN_OPTIONS=detect_leaks=0`을 지정해야 했다. 그 설정에서는 앞선 검사들이 통과했으나 뒤쪽 장시간 통합 검사에서 출력을 내지 않아 실행을 중단했다. 따라서 **전체 테스트 통과**로 보고하지 않는다. 이 환경에서 원본 데몬의 네트워크 실행 및 OSS-Fuzz 최종 적격 판정도 아직 확인하지 못했다.

환경 설정을 명시한 뒤 별도로 실행한 CMake 다중 대상 빌드 검사와 실제 Clang/libFuzzer 재생·짧은 퍼징 검사 **4건은 모두 통과**했다. 이 검사는 작은 독립 fixture의 빌드 경로를 검증한다. Dropbear나 memcached 새 하네스의 기능 도달과 크래시 판정까지 대신하지 않는다.

## 2026-10-30: 단발 입력의 원본 실행 판정 대칭성

`file`·`argv`·`env` 입력을 실행하는 경로에서, 후보 출력 표식이 일치하고 목표 함수가 관찰되면 `PROVEN_RUNTIME`으로 올릴 수 있었다. TCP/UDP 경로는 추가로 소스에 근거한 성공 판별 조건과 확립된 요청 바이트를 요구한다. 단발 경로의 차이 때문에 `model_input_hypothesis`처럼 아직 실험용인 바이트가 같은 출력을 만들기만 해도 증명된 정상 흐름으로 승격될 위험이 있었다. 이는 새 연구 기법을 도입한 것이 아니라, 이미 정한 **원본 실행 증명 계약을 모든 입력 통로에 동일하게 적용**하는 결함 수정이다.

[RESTler의 원본 연구](https://www.microsoft.com/en-us/research/wp-content/uploads/2021/03/RESTler.pdf)는 실제 서비스 응답을 다음 요청 순서의 검증 자료로 사용한다. 그러나 RESTler의 응답 판정은 API 명세와 HTTP 상태 코드라는 전제 위에 있다. 임의 C/C++ 데몬의 출력 바이트 일부가 같다는 사실만으로 성공이라고 옮겨 쓰면 안 된다. 우리 경로에서는 출력 표식의 소스 근거와 입력 바이트의 확립 여부를 별도로 요구하며, 둘 중 하나라도 없으면 실행은 기록하되 `UNPROVEN`으로 유지한다. 이 규칙으로도 요청별 함수 귀속과 출력 프레이밍의 완전성은 별도 검증 대상이다.

파일 입력 fixture에서 프로그램이 실제로 파일을 읽고 `OK`를 출력하며 목표 관찰기가 도달을 보고하도록 만들었다. 소스 성공 근거가 없거나 입력 출처가 실험용이면 이제 `PROVEN_RUNTIME`으로 올라가지 않는 것을 확인했다. 관련 시나리오·Action·입력 표면·인덱서의 집중 검사 **116건 통과, 4건 건너뜀**, 콜백·SVF·Fuzz Introspector 검사까지 포함한 확장 검사 **135건 통과, 4건 건너뜀**이다. 이는 단발 입력 판정의 회귀 검사이며, 실제 데몬에 대한 적격 하네스 생성률을 뜻하지 않는다.

## 2026-10-30: 목표 도달 검사 생략과 실제 요청 귀속

`ProjectSpec.scenario_require_target_reach=False`는 CLI에 공개되지 않은 저수준 테스트 옵션이지만, 기존 `_target_reached()`는 이를 `(entry_reached=True, target_reached=True)`로 변환했다. 따라서 검사하지 않은 것을 **관찰한 것**으로 바꾸어 `PROVEN_RUNTIME`이 될 수 있었다. 반환값을 미관찰 `(False, False)`로 수정했다. 명시적으로 주입한 테스트 관찰기는 별도 경로에서만 사용한다. 이 수정은 새로운 논문 기법의 채택이 아니라 증명 상태의 의미를 지키는 계약 수정이다.

기존 C 통합 fixture도 검사를 끈 채 하네스를 빌드하고 있었다. 이를 실제 입력 획득과 handler 실행에 같은 요청 ID·연결 ID를 기록하는 작은 계측 C 파일과 함께 빌드하도록 바꾸었다. 원본 입력 바이트의 SHA-256과 Entry/handler 함수 ID가 `RequestTraceJournal`에서 일치할 때만 정상 흐름을 증명한다. 이 fixture의 생성·sanitizer 빌드 검사가 통과했고, 검사 생략만으로는 증명되지 않는 별도 회귀 시험도 통과했다. 관련 요청 trace·시나리오·Action·인덱서 검사 **112건 통과, 4건 건너뜀**, 콜백·SVF·Fuzz Introspector 등까지 포함한 확장 검사 **141건 통과, 4건 건너뜀**이다.

[AFLNet](https://mboehme.github.io/paper/ICST20.AFLNet.pdf)은 응답 코드를 프로토콜 상태의 단서로 사용하고, [StateAFL](https://github.com/stateafl/stateafl)은 컴파일 계측과 장기 메모리 상태로 서버 상태를 추정한다. 두 방법 모두 임의의 GDB breakpoint 순서만으로 **한 요청의 바이트가 특정 handler에 전달되었다**고 증명하지 않는다. 현재 요청 trace는 프로그램이 협력해 이벤트를 내보내는 fixture에서는 작동하지만, 일반 데몬에 자동으로 삽입되는 계측 엔진은 아니다. 따라서 이 시험 결과를 대부분의 C/C++ 데몬에서 요청 귀속이나 적격 하네스가 자동 확보되었다는 근거로 사용할 수 없다.

## 2026-10-30: C++ 전역 범위 입력 호출 재현

C++ 독립 fixture의 멤버 함수 안에 `::recv(fd, data, ...)`를 두자 함수 정의는 색인됐지만 `recv` 호출은 `external_calls`에서 빠졌다. 활성 Entry Generator는 이 목록을 입력 API 후보 탐색에 사용하므로, C++의 전역 범위 지정 문법 때문에 실제 입력 지점을 놓치는 결함이었다. [C++ 작업 초안의 이름 조회 규정](https://www.eel.is/c++draft/basic.lookup)은 `::`가 범위를 지정하는 C++ 문법임을 뒷받침한다. 이를 데몬별 특별 규칙으로 넣지 않고, 일반 호출 추출에서 선행 `::`를 처리하도록 수정했다. 같은 이름의 멤버 `recv`가 있는 경우에는 `::recv`를 그 멤버의 직접 호출로 연결하지 않고 외부 호출 후보로 남긴다. 이 보수적 처리로 전역 함수가 **프로젝트 안에 실제 정의된 경우**에도 직접 간선이 누락될 수 있다. C++ AST가 제공하는 범위 정보 없이 임의의 전역 호출 대상을 확정하지 않겠다는 선택이며, 함수 호출 대상의 완전한 해결이 아니다. 멤버 함수와 동명 멤버가 있는 독립 fixture 회귀 검사까지 포함한 확장 검사 전체는 **155건 통과, 5건 건너뜀**이었다. C++ 템플릿·가상 호출·별칭까지 색인한다는 증거는 아니다.

## 2026-10-30: 입력 형식 분석의 시작 함수와 소비 함수

`InputSurfaceAgent`는 `recv`·`fread` 같은 라이브러리 함수 자체가 아니라 **그 함수를 호출해 바이트를 받는 프로젝트 함수**에서 시작한다. 이 함수에 요청 형식이 모두 있다고 가정하면, 단순 읽기 wrapper 뒤 parser나 콜백 소비 함수에 있는 형식을 놓친다. 실제 Dropbear의 `read(..., buf_getptr(...), ...)` 사례와 memcached의 연결 버퍼·상태 머신 사례에서 입력 획득 위치만으로 후속 형식을 설명할 수 없음을 확인했다. [NetLifter 연구](https://arxiv.org/abs/2305.11781)는 네트워크 구현의 입력 처리 코드에서 형식 제약을 복원하지만, 특정 읽기 함수 하나만으로 형식을 얻는다고 주장하지 않는다. [FuzzingBrain V2](https://arxiv.org/html/2605.21779)의 반복적인 함수 문맥 확장도 소스 탐색의 근거로 참고할 수 있으나, 그 연구는 임의 데몬의 요청 바이트를 생성하는 이 단계의 성공률을 입증하지 않는다.

이에 따라 Entry Verifier가 **실제로 열어 본 함수 ID**로 넘긴 `consumer_hints`가 남아 있다면, 모델이 입력 획득 함수에서 `context_complete=true`라고 해도 그 후보 원문을 한 턴에 하나씩 더 열도록 했다. 모델이 존재하지 않는 함수를 요청한 경우 그 오류를 기록하고, 이미 알려진 소비 후보가 있다면 그 후보 분석을 계속한다. 함수 ID는 탐색 지시일 뿐 값 흐름, 정상 요청, 런타임 도달의 증명이 아니다. 모델이 제시한 바이트도 계속 `model_input_hypothesis`로 남는다. 이 변경은 특정 프로토콜 문자열이나 `if/case`를 Action으로 추가하지 않는다. 후보가 많으면 시간과 LLM 문맥 비용이 늘고, 검증기가 소비 후보 자체를 누락하면 여전히 형식을 놓칠 수 있다. 모든 소비 함수를 열거했다는 주장은 하지 않는다.

입력 획득 함수에서 모델이 조기 완료를 선언하거나 잘못된 다음 함수명을 요청하고, 소비 후보 함수에 바이트 형식 단서가 있는 fixture를 추가했다. 소비 함수를 실제로 연 뒤에야 탐색이 끝나는 회귀 검사를 포함한 확장 검사 **157건 통과, 5건 건너뜀**을 확인했다. 이는 누락 경로의 수정 결과이며 다수 실제 데몬의 하네스 생성 성능은 아직 측정하지 않았다.

## 2026-10-30: C++ 호출 대상에 대한 컴파일러 근거

기존 정적 보강은 `.c` 번역 단위만 Clang AST로 읽었다. C++는 정규식 기반의 `external_calls`와 이름 매칭에 의존했기 때문에 `::recv`와 동명 멤버 `recv`의 관계, 매크로를 통해 확장된 입력 호출을 안정적으로 구분하지 못했다. [Clang의 AST 소개](https://clang.llvm.org/docs/IntroductionToTheClangAST.html)는 C++ 소스의 구문·이름 조회 결과를 AST에서 확인하는 방법을 제공한다. [컴파일 데이터베이스 명세](https://clang.llvm.org/docs/JSONCompilationDatabase.html)는 동일 파일도 빌드 대상에 따라 여러 명령으로 컴파일될 수 있음을 명시한다. 따라서 파일명이나 정규식 결과만으로 프로젝트 전역의 호출 관계를 확정하면 안 된다.

`clang++`로 실제 소스를 파싱하는 C++ 보강 경로를 추가했다. AST의 참조 ID가 같은 번역 단위의 정의와 일치하면 호출 후보를 기록하고, 컴파일 데이터베이스의 빌드 플래그가 확인될 때만 `direct` 간선으로 올린다. 플래그가 없는 파싱 결과는 `source_candidate` 탐색 근거로만 쓴다. AST가 전역 `::recv`를 가리킬 때는 동명 프로젝트 멤버로 연결된 bootstrap 간선을 제거하고 외부 호출로 남긴다. 매크로가 `recv`로 확장되는 사례에서도 AST가 외부 호출 이름을 확인한다. C++ fixture 네 종류와 기존 관련 검사 **168건 통과, 5건 건너뜀**을 확인했다. 그중 Entry Generator까지 이어지는 검사에서 전역 `::recv` 호출만 Entry 후보로 남고 동명 멤버 호출은 후보가 되지 않았다.

**당시 전이 한계:** Clang AST는 정확한 전처리·빌드 옵션이 있을 때 가장 유용하다. 컴파일 데이터베이스가 없거나 번역 단위 파싱이 실패한 경우에는 새 간선을 실행 근거로 승격하지 않는다. 같은 C++ 파일에 서로 다른 빌드 설정이 있으면 임의의 설정을 선택하지 않는다. 당시에는 매크로 호출이 `external_calls`에만 나타나고 Entry 후보 위치로 이어지지 않았다. 아래 변경에서 이 위치 누락을 보완했다. C++ AST 보강은 입력 바이트의 별칭·구조체 이동, 스레드 사이 전달, 원본 요청별 handler 귀속을 증명하지 않는다. 전체 테스트 묶음은 기존 `test_boundary_rebuild.py`의 한 C fixture에서 `harnesses_generated=0`으로 실패했다. `HC_CPP_AST_BUDGET_SECONDS=0`으로 새 C++ 보강을 끄고 같은 검사를 다시 실행해도 실패하므로, 이 실패를 새 AST 경로의 효과로 분류하지 않는다. 위 168건은 관련 경로의 집중 검사이지 전체 패키지 통과가 아니다.

전체 검사에서 추가로 드러난 CMake 빌드 fixture의 빈 입력 크래시는 이 샌드박스에서 `ASAN_OPTIONS=detect_leaks=0`으로 재실행하면 통과했다. 이것은 빌드 증명도, 누수 부재의 증거도 아니다. C++ 보강을 비활성화한 상태에서도 원래 실패한 실행 환경 의존 검사로 분리해 기록한다.

활성 Action 경로는 `semantic_action_mode=True`로 실행된다. 한 Entry에서 처음 입력을 받는 **프로젝트 함수**를 열고, 입력을 받은 값이 전달된 함수와 소스상 연결된 콜백·호출자를 한 번에 하나씩 확인한다. `if/case`는 열린 소스 안에서 입력의 분기 조건을 설명하는 위치 근거로만 쓴다. 분기 하나당 Action 하나를 만들거나 분기별 LLM 작업을 예약하는 과거 경로는 오케스트레이터가 호출하지 않는다. 분기가 전혀 없는 입력 처리 함수, 앞선 `if` 검사 뒤의 소비 함수, 내부 `if`가 30개인 dispatcher를 별도 회귀 검사로 다뤘다. 이 검사는 활성 경로의 분기 작업 수를 확인하며 실제 데몬의 Action 목록이 완전하다는 증명은 아니다.

Clang이 매크로 안의 `recv`를 파싱해도 기존 Entry Generator는 함수 원문에 `recv(`라는 글자가 없으면 후보를 만들지 않았다. C와 C++ 인덱서가 `spellingLoc`와 `expansionLoc`를 함께 보존하도록 하고, Entry Generator가 **확장 위치**를 후보의 줄 번호로 사용하도록 연결했다. C++에서 동명 멤버 호출이 매크로에 숨겨진 경우는 외부 `recv`로 취급하지 않는 반례 검사도 추가했다. 컴파일 데이터베이스가 없으면 전처리 결과가 제품 빌드와 같다는 근거가 없으므로 Verifier의 `VERIFIED`와 `REJECTED` 응답 모두 `UNRESOLVED`로 내린다. 이것은 Clang이 제공하는 위치 정보에 대한 국소적인 누락 수정이며, 새 요청 형식이나 Action을 추측해 추가한 변경이 아니다.

### 입력 버퍼 전달 근거의 재검토

매크로 안의 입력 호출을 Entry로 찾더라도 Action 탐색은 원문에서 `recv(...)`의 목적지 인자를 다시 찾았기 때문에 매크로 호출 뒤의 `parse(data)`를 연결하지 못했다. [Clang AST 문서](https://clang.llvm.org/docs/IntroductionToTheClangAST.html)의 호출식 자식 노드에서 **현재 함수 안에 선언된 변수·매개변수의 직접 인자**가 확인된 경우에만 그 식별자를 Action 탐색으로 넘긴다. 구조체 필드, 전역 변수, 포인터 계산, 함수가 반환한 주소, 같은 줄의 여러 확장 호출은 이 방법으로 확인되지 않으므로 미해결로 둔다. C/C++ 매크로 픽스처로 직접 변수 전달을 확인했고, 필드·전역 목적지는 연결하지 않는 반례도 검사했다. 이는 FuzzGen의 인자 전달 분석을 데몬 전체에 복사한 것이 아니라, 현재 Clang AST가 직접 보여 주는 한 인자의 위치만 사용하는 수정이다.

반대로 기존 원문 분석은 `read(fd, a->buf, n)`에서 목적지를 단순 이름 `buf`로 저장했다. 그러면 뒤의 `parse(b->buf)`도 같은 이름이라는 이유로 입력 흐름으로 판단할 수 있었다. [LLVM Alias Analysis 문서](https://llvm.org/docs/AliasAnalysis.html)는 포인터 관계에 `Must/May/No Alias` 구분이 필요하다고 설명한다. 따라서 필드 이름 일치만으로는 객체 동일성이 성립하지 않으므로 직접 입력 흐름 증명에서 제외했다. `try_read_udp`의 `c->rbuf`처럼 실제로 중요한 필드 전달도 이제 별도 객체·콜백 근거가 없으면 미해결이다. 이 변경은 가짜 증명을 줄이지만 Action 누락을 자동 해결하지 않는다. 필드 전달을 증명하려면 같은 객체가 쓰기부터 소비까지 유지되고 중간에 다른 쓰기가 없는지 분석하거나, 원본 실행에서 요청별 경로를 관찰해야 한다. [LLVM MemorySSA 문서](https://llvm.org/docs/MemorySSA.html)도 메모리 쓰기·읽기 관계는 별칭 분석과 함께 해석해야 하고 정밀도에 한계가 있다고 명시한다.

입력 형식 탐색도 Entry 함수 하나에서 끝내지 않도록 연결했다. `read(fd, data, n) → parse(data)`처럼 **직접 인자 전달이 소스에 있고 아직 시험 바이트가 하나도 없는 경우**, Input Surface Agent가 모델의 조기 완료 응답 뒤에도 `parse` 원문을 연다. 이미 바이트 가설이 있으면 다른 단계에서 원본 실행으로 시험하고, 이 단계가 모든 직접 소비 함수를 자동으로 여는 비용은 피한다. 이때 나온 입력 바이트는 계속 시험 가설로 저장하며, 파서가 받는 정상 요청이라는 판정으로 바꾸지 않는다. [FuzzGen](https://www.usenix.org/system/files/sec20-ispoglou.pdf)의 인자 의존성 추적은 이러한 소스 연결을 조사할 이유를 주지만, FuzzGen은 라이브러리 소비 코드를 대상으로 했으므로 데몬의 콜백·공유 필드·프로토콜 상태까지 자동으로 해결한다는 근거로 사용하지 않는다. 직접 인자가 아닌 경로의 누락, 장시간 원문 탐색, 모델의 요청 형식 오류는 여전히 별도 검증 과제다.

공개 구현도 대조했다. FuzzGen의 `src/backward.cpp`는 호출 결과에서 인자로 무조건 뛰어넘지 않고 `findAlloca`·`findStores`로 저장 위치를 추적하며, 두 흐름이 같은 구조 요소에 접근하는지 비교한다. 따라서 단순 필드 이름 일치만 남긴 기존 구현은 이 근거보다 약했다. RESTler의 `docs/user-guide/ImprovingCoverage.md`는 선행 자원 생성이 빠졌을 때 실행 로그·커버리지 보고서·명세의 링크나 주석을 확인하도록 안내한다. 이 절차는 **이미 요청 종류를 아는 API**에 유효하므로, 우리 시스템에서 아직 복원되지 않은 데몬 요청을 `if/case`에서 만들어내는 근거로 쓰지 않았다.

호출 인자도 단순 토큰 포함 여부로 연결하지 않도록 수정했다. 예를 들어 `read(fd, data, ...)` 뒤 `parse(other->data)`는 문자열 `data`가 같아도 직접 전달이 아니다. 현재의 직접 전달 탐색은 `parse(data)`와 `parse(&data)`처럼 인자가 그 식별자 자체이거나 그 주소인 경우만 인정한다. 이는 [LLVM Alias Analysis](https://llvm.org/docs/AliasAnalysis.html)의 객체 관계 구분을 현재 증거 수준에 적용한 보수적인 경계다. 이 제한은 `parse(data + offset)`처럼 실제로 연결된 경로도 놓칠 수 있으므로 완전성보다 잘못된 직접 증명 방지를 우선한다. 독립 반례와 `fread(&byte) → dispatch(&byte)` 통합 경로를 함께 검사했다.

검증은 관련 소스·오케스트레이터·콜백·큐 검사 164건 통과, 1건 건너뜀이다. 추가로 실제 C 데몬 TCP·UDP 요청 실행 검사가 통과했다. 소켓 실행 검사는 기본 샌드박스에서 소켓 생성 권한이 없어 실패했으며, 로컬 소켓을 허용한 별도 실행에서 TCP와 UDP 모두 통과했다. 이 결과는 입력 전달의 일부 회귀를 확인한 것이다. 실제 memcached 하네스의 생성, 빌드, 목표 handler 도달, 오탐 없는 크래시 여부는 이 검사로 판정되지 않았다.

**남은 경계:** 컴파일 데이터베이스가 있어도 해당 명령이 실제 퍼징 대상 제품 빌드인지 별도 확인이 필요하다. 매크로가 소스의 여러 위치에서 확장되거나 같은 줄에 둘 이상 등장하면 현재 후보 ID가 합쳐질 수 있다. C/C++ AST 파싱 실패, 구조체 필드·별칭·비동기 큐를 통한 값 전달, 모델이 소비 함수를 선택하지 못하는 경우의 누락도 해결되지 않았다. 현재 자료와 회귀 검사는 이 부분에 대한 일반적 성공률을 보장하지 않는다.

### 구조체 필드 입력 이후의 콜백 탐색

실제 memcached의 `try_read_udp`는 `recvfrom`으로 `c->rbuf`에 기록하고 호출자 `drive_machine`으로 돌아간다. 호출자는 이후 같은 `c`에 있는 함수 포인터를 호출한다. 기존에는 Entry 함수의 직접 호출 인자만 따라가므로 이 콜백 본문을 모델이 요청하지 않으면 탐색이 끝날 수 있었다. [FuzzGen](https://www.usenix.org/system/files/sec20-ispoglou.pdf)은 라이브러리 사용 코드의 인자·호출 순서를 분석할 이유를 보여 주지만, 이 데몬 콜백 경로를 복원하는 알고리즘을 제공하지 않는다. [LLVM Alias Analysis](https://llvm.org/docs/AliasAnalysis.html)도 이름 일치만으로 동일 객체를 주장할 수 없음을 보여 준다. 따라서 우리 코드에서는 **소스에서 읽기 함수 호출과 콜백 호출이 같은 수신자 변수에 있고, 콜백 대상 본문이 읽기 목적지 필드를 참조할 때** 그 콜백을 다음에 열 *후보*로 추가했다. 이것은 현재 워크플로우의 누락을 줄이기 위한 제한적 탐색 규칙이며 두 연구의 결과를 그대로 이식한 것이 아니다. 함수 하나를 연 뒤 다음 후보를 선택하는 기존 방식 안에서만 동작하며, `if/case` 하나당 새 작업을 만들지 않는다. 읽기와 콜백 사이의 실제 제어 흐름, 포인터 별칭, 다른 쓰기의 개입은 이 검사로 증명되지 않으므로 Action의 `PROVEN_STATIC` 근거로 사용하지 않는다.

독립 C fixture에서 `acquire(c) → drive(c) → c->handler(c)`는 탐색했고, `acquire(c) → other->handler(other)`는 같은 수신자 경로로 취급하지 않았다. 콜백 본문을 읽어 Action 후보가 나와도 상태는 `POSSIBLE`이며, 사용자가 설정한 작업 상한에 걸려 콜백을 열지 못하면 해당 함수 ID를 미확인 항목에 남긴다. 실제 memcached 소스 인덱스 2,474함수·11,858간선에서는 이 탐색이 `try_read_command_udp`를 포함한 **네 콜백 후보**를 찾았다. 이 중 어느 콜백이 UDP 요청에서 실행되는지는 등록 조건과 원본 실행을 더 확인해야 한다. 이 네 후보를 모두 UDP 기능으로 간주하거나 memcached 하네스가 완성됐다고 해석하면 안 된다. 필드 복사·다른 이름의 별칭·C++ 가상 호출·비동기 큐의 경로는 이 국소 검사 범위 밖에 남는다.

### 2026-10-30: 여러 호출자와 다른 데몬의 반례

읽기 함수에 직접 호출자가 둘 이상이면 기존 탐색은 전부 미해결로 멈췄다. 이제 각 호출자에서 읽기 함수의 인자와 이후 콜백 호출의 수신자가 같고, 콜백 대상이 읽기 목적지 필드를 참조하는지 독립적으로 확인한다. 그 근거가 있는 호출자만 한 함수씩 열고 나머지 호출자는 미해결로 남긴다. 목적지 주소를 돌려주는 보조 함수를 먼저 열어도 **원래 읽기 함수의 호출자**를 잃지 않도록 별도 대기열에 유지한다. 이것은 [FuzzGen의 호출 순서·인자 의존성 분석](https://www.usenix.org/system/files/sec20-ispoglou.pdf)에서 조사해야 할 관계를 참고한 것이지만, 그 논문은 라이브러리 API를 대상으로 하므로 여기의 같은 변수·필드 검사가 동일한 정밀도를 갖는다는 주장은 하지 않는다. [LLVM MemorySSA](https://llvm.org/docs/MemorySSA.html) 문서처럼 필드 쓰기와 읽기 사이에는 별칭과 중간 쓰기 문제가 남는다. 따라서 이 대기열은 소스 탐색에만 쓰며 Action 증명에 쓰지 않는다.

독립 반례에서는 `acquire(c)`의 두 호출자 가운데 `c->handler(c)`를 쓰는 쪽만 자동 탐색하고, `other->handler(other)`를 쓰는 쪽은 미해결로 남겼다. 실제 Dropbear 소스 1,481함수·4,384간선을 색인해 `read_packet_init::read`에서 모델이 매번 즉시 탐색 완료를 선언하도록 시험했다. 수정 전에는 `read_packet_init → buf_getwriteptr → cli_remoteclosed → svr_remoteclosed → read_packet → session_loop`를 열었다. 수정 후에는 **`read_packet_init → buf_getwriteptr → read_packet → session_loop`**를 열었다. 앞의 두 종료 콜백은 입력 획득 함수를 호출하는 경로가 아니라 획득 함수가 오류 처리에 호출하는 대상이다. 이제 모델의 선택 후보에는 남지만 자동 탐색 대상에서는 제외한다.

이 시험은 Dropbear의 실제 입력 처리 완료를 보여 주지 않는다. `read_packet`은 복호화 후 `ses.readbuf`에서 `ses.payload`로 상태를 옮기며, `session_loop`는 `ses.payload`가 있을 때 `process_packet`을 호출한다. 앞선 직접 인자·동일 수신자 탐색만으로는 이 변환을 연결하지 못했다.

### 2026-10-30: 공유 필드 전달을 탐색 후보로 연결

[FuzzGen](https://www.usenix.org/system/files/sec20-ispoglou.pdf)은 사용 코드에서 API 호출 간 저장 관계와 순서를 추적한다. 그러나 대상이 라이브러리 API이므로 그 결과를 데몬의 전역 상태와 소켓 입력에 대한 증명으로 가져올 수 없다. [LLVM MemorySSA](https://llvm.org/docs/MemorySSA.html)는 쓰기와 읽기의 관계를 분석할 수 있는 틀을 제공하지만 함수 내부 분석이며, [별칭 분석](https://llvm.org/docs/AliasAnalysis.html)의 정밀도와 중간 쓰기 확인이 필요하다. 현재 인덱스의 이름 검색은 그 분석을 구현하지 않는다.

그래서 다음 규칙을 **함수 원문을 열 순서를 정할 때만** 적용했다. 실제 Entry 호출의 목적지 식에서 `ses.readbuf` 같은 필드 경로를 얻고, 열린 호출자의 Entry 호출 **이후**에 소스상 호출되는 함수가 그 필드를 참조하면 한 함수씩 연다. 열린 함수의 실제 대입 오른쪽이 추적 필드를 참조하면 왼쪽 필드를 다음 검색 키로 추가한다. 예를 들어 `ses.payload = ses.readbuf`를 연 다음에만 `ses.payload`를 참조하는 후속 함수를 후보로 삼는다. 같은 줄에 여러 호출이 있는 경우에도 줄 번호와 호출 위치를 함께 비교한다. 호출 관계의 위치가 없거나 호출 순서를 소스에서 확인하지 못하면 자동으로 연결하지 않는다.

이는 별칭, 객체 동일성, 분기 실행 가능성, 복호화·압축 해제 결과의 바이트 동일성, 중간 쓰기 부재를 증명하지 않는다. 주석·매크로·동명 지역 변수 때문에 원문 검색 후보가 잘못 포함될 수 있으며, 다른 이름의 별칭과 비동기 전달은 놓칠 수 있다. 따라서 후보를 연 사실만으로 Action을 `PROVEN_STATIC`으로 올리지 않으며, 원본 실행 및 요청별 경로 검증은 계속 필요하다. 외부 자료에서 가져온 것은 **조사해야 할 저장 관계**이고, 이 이름·위치 기반 규칙 자체는 그 관계를 놓치지 않기 위한 현 구현의 제한적 탐색 방법이다.

독립 C fixture에서 `ses.readbuf`를 읽고 `ses.payload = ses.readbuf`를 거쳐 파서를 호출하는 경로를 열었다. `ses.payload = other.readbuf`인 반례에서는 파서를 공유 필드 전달 후보로 만들지 않았다. 실제 Dropbear 소스 1,481함수·4,384간선을 다시 색인해, 모델이 모든 턴에 즉시 완료를 선언해도 `read_packet_init → buf_getwriteptr → read_packet → session_loop → decrypt_packet → process_packet` 순서로 열리는 것을 확인했다. 관련 회귀 검사 **170건 통과, 1건 건너뜀**이다. 이 시험에서 의미 Action은 0개였고, 원본 요청의 성공이나 하네스 생성·빌드는 시험하지 않았다. 따라서 현재 확인한 성과는 **탐색 누락 하나의 해소**이며 정상 흐름 하네스 완성이 아니다.

### Input Surface 단계의 같은 전달 경로 재검사

Action 탐색에서 위 경로를 열어도 그보다 앞선 Input Surface Agent가 입력 형식 가설을 만들지 못하면 원본 프로그램에 보낼 요청 자체가 없다. 기존 Input Surface는 Entry Verifier의 힌트와 직접 인자 소비자만 자동 탐색했다. 그래서 같은 Dropbear 경로에서 모델이 조기 완료를 선언하면 입력 획득 함수 하나를 읽고 끝났다. 이는 뒤 단계에 Action 후보가 존재하는지와 별개인 실제 누락이었다.

이 단계에도 앞서 검증한 저장 관계 탐색을 연결했다. Entry의 공유 필드가 있는 경우, 원문에서 확인되는 호출자를 따라 읽기 함수의 반환 이후를 살핀다. 호출자가 하나뿐이면 그 함수를 열 수 있고, 그 뒤에는 호출 이후 같은 저장 객체가 사용되거나 이미 열린 대입에서 새 필드가 파생된 함수만 후보로 연다. 호출자가 여러 개이고 연결 근거가 없으면 임의로 고르지 않고 다음에 살펴볼 함수 ID들을 미해결 기록에 남긴다. 입력 형식 가설을 한 개 확보한 뒤에는 이 자동 확장을 계속 강제하지 않는다. 이 선택은 [FuzzGen의 사용 코드 저장·호출 관계 분석](https://www.usenix.org/system/files/sec20-ispoglou.pdf)에서 **조사 대상**만 가져온 것이며, 구현의 이름·호출 위치 검색이 논문의 정밀한 흐름 분석과 같다는 뜻이 아니다.

독립 C fixture에서는 모델이 매번 완료를 선언해도 `acquire → read_packet → session_loop → decrypt → parse`를 읽고 마지막 단계에서 제시한 바이트를 **가설**로 저장했다. 호출자가 둘인 반례는 첫 함수에서 멈추고 두 호출자 ID를 이어서 분석할 미해결 후보로 저장했다. C++ 소스 fixture에서도 같은 저장·호출 경로를 열었다. 실제 Dropbear 원본에서는 `read_packet_init → read_packet → session_loop → decrypt_packet → process_packet`까지 열었으나, 모델이 바이트를 제시하지 않은 시험이므로 입력 가설은 0개다. 관련 회귀 검사 **173건 통과, 1건 건너뜀**이다. 파서를 읽었다는 사실만으로 정상 SSH 패킷을 생성하거나 원본 실행이 성공했다는 주장은 하지 않는다. 동일한 전역 이름을 다른 객체가 가리는 경우와 간접·비동기 호출은 계속 누락·오탐 위험이다.

### 전체 회귀와 요청별 실행 증명의 경계

전체 회귀를 다시 수행해 `521 passed, 4 skipped, 37 subtests passed`를 확인했다. 로컬 소켓을 쓰는 검사는 샌드박스 밖의 로컬 실행 권한으로 수행했고, CMake 퍼저 실행에는 이 환경에서 `ASAN_OPTIONS=detect_leaks=0`을 사용했다. 이 설정으로 통과한 결과를 메모리 누수 부재의 근거로 쓰지 않는다. 기존 `test_boundary_rebuild.py`의 가짜 LLM 응답 목록은 Input Surface가 소비 함수 한 개를 추가로 열게 된 호출 순서를 반영하지 못해 하네스 코드 응답을 문맥 턴에 소모하고 있었다. 응답 순서를 맞춘 뒤 해당 C 하네스 생성·빌드 통합 검사가 통과했다. 이것은 테스트 fixture의 순서 수정이며 제품의 빌드 성공률 개선으로 계산하지 않는다.

또 다른 테스트는 엄격 모드의 GDB 경로에서 실행 관찰 기록이 있다고 가정했다. 현재 실행 검증기는 GDB 중단점의 **시간순 히트**만으로 요청과 목표 handler를 연결할 수 없으면, 원본 프로그램을 띄우기 전에 `UNPROVEN`으로 반환한다. [GDB의 스레드별 중단점 문서](https://www.sourceware.org/gdb/current/onlinedocs/gdb.html/Thread_002dSpecific-Breakpoints.html)는 스레드 지정을 하지 않은 중단점이 모든 스레드에 적용된다고 설명한다. 여기에 우리 시스템의 요청 ID가 없다는 사실을 합치면 시간순 히트는 입력별 인과관계 증명이 되지 않는다. 따라서 테스트를 무관찰·`UNPROVEN` 판정에 맞춰 수정했다. 이 부분은 하네스 생성보다 뒤의 **자격 판정 한계**로 남는다. 실제 대부분의 C/C++ 데몬에서 `QUALIFIED`를 얻으려면, 사용자가 만든 fixture처럼 수동으로 이벤트를 내는 방식에 기대지 않고 원본 요청과 handler를 연결하는 검증 방법을 별도로 구현·검증해야 한다.

### 원본 입력 시험이 실행되지 않던 문제와 분기 기준 재확인

기본 Action 경로는 이미 Entry에서 입력이 소비되는 함수를 하나씩 열며 **외부 주체가 입력으로 요청할 수 있는 의미 동작**을 찾는다. `if`·`switch/case`·명령어 문자열은 탐색 단서이며 Action의 개수나 작업 단위가 아니다. 같은 분기 안에 여러 동작이 있거나 여러 분기가 한 동작에 속할 수 있다. 옛 분기별 worker 구현은 명시적인 legacy 경로로만 남아 있고, 현재 orchestrator는 `semantic_action_mode=True`를 사용한다. 따라서 분기 필터를 더 늘리는 것은 현재의 누락이나 초기 원본 시험 실패에 대한 해결책이 아니다.

실제 누락은 **초기 원본 입력 시험에 엄격한 GDB 검증 설정을 그대로 적용한 것**이었다. 엄격 검증기는 요청별 handler 귀속이 없으면 프로세스 시작 전에 종료한다. 이 판정은 최종 자격에는 옳지만, 입력 바이트 가설에 대한 원본 응답을 얻는 첫 시험까지 막았다. [RESTler 원문](https://arxiv.org/abs/1806.09739)은 실제 응답을 이용해 요청열 가설을 시험한다. [RESTler 공식 가이드](https://github.com/microsoft/restler-fuzzer/blob/main/docs/user-guide/ImprovingCoverage.md)는 실패 응답과 요청 의존성을 실행 기록에서 분석한다. 다만 RESTler는 API 명세와 알려진 요청 종류가 있으므로, 그 도구의 요청 생성이나 성공 판정을 C/C++ 데몬에 그대로 적용할 수 없다. [AFLNet 공식 사용법](https://github.com/aflnet/aflnet/blob/master/README.md)도 실제 클라이언트 통신을 입력 시드로 요구한다. 따라서 출처 없는 명령 문자열·헤더·시드를 자동으로 채우는 방식은 근거로 삼지 않았다.

현재 변경은 **원본에 바이트를 보내고 응답을 기록하는 진단 시험**에만 별도의 탐색 설정 사본을 사용한다. Action 분석에는 그 Entry의 시험 바이트와 응답 원문, 실패 상세, `handler/성공 미증명` 경계를 전달한다. 모델은 그 관찰을 다음 소스 확인 질문에 사용할 수 있지만, 응답만으로 Action·handler·성공을 증명할 수 없다. 원래 프로젝트 설정과 최종 자격 판정은 바꾸지 않았다. 원시 입력을 Action 전용 자료형으로 옮기는 호환 어댑터는 dispatcher와 handler에 **같은 Entry 함수 ID**를 넣는다. 이전의 source draft 판정은 이 ID 일치와 Entry 근거만 보고 이를 의미 Action으로 착각할 수 있었다. 이제 내부 `UNCLASSIFIED_INPUT` 표식이 있는 원시 사례는 source-backed 의미 Action 초안 자격에서 제외했다. 사용자가 명시적으로 탐색 초안을 허용한 경우의 실행 관찰은 계속 별도 상태로 남는다. [GDB 공식 문서](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Thread_002dSpecific-Breakpoints.html)상 일반 중단점은 모든 스레드에 적용되므로, 여기서 관찰한 함수 순서는 요청별 원인 증명이 아니다.

독립 C stdin fixture에서는 명령어·분기 후보 목록 없이 원본에 `ABCD`를 보내 `ACCEPT` 응답을 관찰했고, 상태는 `PROVEN_RUNTIME`으로 올라가지 않았다. Action Agent가 이 관찰을 받되 의미 Action을 자동으로 만들지 않는 검사도 추가했다. 같은 Entry 세션의 첫 턴에만 원본 응답 원문을 넣고, 이후 함수 턴에는 중복 전송하지 않는 것도 검사했다. 전체 회귀는 **522건 통과, 4건 건너뜀, 하위 검사 37건 통과**다. 이 결과는 첫 시험의 실행과 피드백 전달 및 기존 기능의 회귀만 확인한다. 응답이 없는 데몬, 여러 요청이 섞인 서버, 파일·IPC 환경, 입력 형식을 복원하지 못한 경우, 요청별 handler 귀속과 최종 하네스 자격은 여전히 미해결이다. [LLVM SanitizerCoverage](https://clang.llvm.org/docs/SanitizerCoverage.html)는 함수·간선 실행을 계측할 수 있지만 요청 원인을 기록하지 않고, [DataFlowSanitizer](https://clang.llvm.org/docs/DataFlowSanitizer.html)는 별도 라벨링과 계측이 필요하므로 둘 중 하나를 켜는 것만으로 이 미해결 부분이 증명되지는 않는다.

### C/C++ 이외의 프로젝트 테스트·클라이언트에서 입력 가설 찾기

다른 데몬을 대조하면서 입력 예시가 제품의 C/C++ 함수 인덱스에만 있지 않다는 누락을 확인했다. Dropbear의 프로젝트 테스트는 Python 파일이고, memcached에는 Perl `.t` 테스트가 있다. 기존 `discover_usage_artifacts`는 자동 발견된 C/C++ 함수 파일만 올려 두므로 이 파일들의 요청 구성 코드를 Input Surface Agent가 열 수 없었다. [AFLNet 공식 사용법](https://github.com/aflnet/aflnet/blob/master/README.md)은 실제 클라이언트 통신을 시드로 수집한다. 이는 **프로젝트 사용 예시를 조사할 이유**는 주지만, 테스트 소스에서 추측한 바이트가 실제 통신 캡처와 같다는 주장은 뒷받침하지 않는다. [RESTler 공식 가이드](https://github.com/microsoft/restler-fuzzer/blob/main/docs/user-guide/ImprovingCoverage.md)도 API 예시가 필요한 상수를 채우는 데 도움을 줄 수 있다고 설명하지만, RESTler에는 API 명세가 있으므로 데몬 테스트 파일만으로 정상 요청을 확정할 수 없다.

현재는 Git 추적 대상인 테스트·클라이언트·예시의 텍스트 소스 파일을 별도의 `UsageArtifact`로 찾는다. 추적 여부는 생성된 실험 출력 대신 프로젝트 소스를 우선하기 위한 **소유권 단서**이며 유효한 요청이라는 증거가 아니다. Git 없는 소스 트리에서는 경로 기반 탐색을 사용한다. 자동 탐색은 코드·문서 확장자만 허용해 `.pem` 같은 키 파일과 임의 코퍼스 파일을 모델 문맥에 넣지 않는다. Input Surface Agent는 경로 목록을 같은 Entry 세션의 첫 턴에 받고, 선택한 파일 하나의 원문만 다음 턴에 연다. 파일을 여는 직전에는 인벤토리의 SHA-256과 현재 바이트가 같은지 확인한다. 제시된 바이트는 여전히 `model_input_hypothesis`이며, 사례에는 열어본 사용 예시 경로를 남긴다. 기존 함수 원문도 계속 한 턴에 하나씩 연다.

실제 두 소스 트리의 Git 추적 파일을 별도 인벤토리로 검사한 결과 Dropbear Python 테스트 9개와 memcached Perl `.t` 테스트 114개가 후보가 되었고, memcached의 `client_key.pem`은 제외되었다. 독립 C 제품과 Python 클라이언트 fixture에서는 모델이 `test/client.py`를 한 턴에 열어 `PING\n`을 **가설**로 기록했다. 이는 원본 데몬이 수락한 입력이나 하네스 성공을 입증하지 않는다. Python·Perl 테스트가 라이브러리 클라이언트를 호출할 뿐 실제 전송 바이트를 직접 만들지 않으면 여전히 요청 형식을 복원할 수 없다. 당시 구현에는 큰 파일을 통째로 모델에 넣는 문제와 사용 예시 인벤토리를 2048개에서 자르는 문제가 남아 있었다.

이 변경 뒤 전체 회귀는 **523건 통과, 4건 건너뜀, 하위 검사 37건 통과**다. 전체 회귀는 사용 예시 경로를 하나씩 여는 새 경로와 기존 단계의 내부 계약을 확인한 것이며, Dropbear·memcached의 입력 패킷 생성이나 하네스 자격을 판정한 것은 아니다.

### 사용 예시 탐색의 숨은 누락과 문맥 폭증 방지

[FuzzGen 원문](https://www.usenix.org/system/files/sec20-ispoglou.pdf)은 실제 소비 프로그램의 호출 순서와 공유 인자를 조사해야 잘못 초기화한 하네스의 가짜 크래시를 줄일 수 있다고 설명한다. 이 주장은 **사용 예시를 열어볼 이유**를 뒷받침하지만, 데몬의 Python·Perl 테스트 원문이 그대로 전송 바이트이거나 모든 요청을 망라한다는 뜻은 아니다. [FuzzingBrain V2 원문](https://arxiv.org/html/2605.21779)은 복잡한 함수 간 의존성을 좁은 문맥에서 점진적으로 분석할 필요를 제시하지만, 파일 128개 또는 16000자라는 숫자를 정하지 않는다. 아래 숫자는 모델 요청의 크기를 조절하는 전송 단위이며, 분석 완료 기준으로 쓰지 않는다.

이전 코드에는 프로젝트 사용 예시가 2048개를 넘으면 뒤 파일을 **알림 없이 버리는** 기본 상한이 있었다. 기본 상한을 없애고, 명시적으로 양의 `max_artifacts`를 넣은 호출만 작업 예산을 적용하도록 했다. 별도로 한 Entry에 모든 경로를 한꺼번에 넣던 방식은 한 번에 최대 128경로, 긴 경로가 많으면 더 적은 경로를 보여 주는 페이지로 바꿨다. 모델이 다음 페이지를 요청하면 같은 Entry 세션에서 열고, 요청하지 않아 남은 페이지는 `continuations.json`에 경로 인벤토리 위치와 함께 남긴다. 자동으로 모든 페이지를 순회하지 않는다. 그렇지 않으면 파일이 많은 프로젝트에서 Entry 수만큼 LLM 호출이 폭증할 수 있기 때문이다. 선택된 파일 원문도 16000자 페이지로 전달한다. 다음 부분이 필요하면 모델이 같은 경로를 다시 요청하고, 선택한 파일에 읽지 않은 부분이 남으면 문맥 완료로 인정하지 않는다. 미열람 파일은 다음 문자 위치도 기록한다. 파일 해시 검사는 매번 유지된다. 이 기록은 이어서 분석할 위치를 보존하지만, 별도의 재개 실행 기능을 구현했다는 뜻은 아니다.

이 수정은 **전송과 기록 방식**에 한정된다. 어떤 페이지에 관련 파일이 있는지, 사용 예시가 실제 전송 바이트를 포함하는지, 생성한 입력이 원본 프로그램에서 정상 처리되는지는 아직 증명하지 못한다. 뒤 페이지를 요청하지 않은 모델이 유용한 입력을 놓칠 수도 있다. 따라서 현재 사례의 `model_input_hypothesis` 지위와 원본 실행 검증 요구는 그대로다. 회귀 검사에서는 2049개 파일이 기본 인벤토리에 모두 남는지, 129번째 경로를 명시적으로 연 뒤 가설을 만들 수 있는지, 큰 파일의 두 번째 페이지를 읽을 수 있는지, 모델이 멈춘 경우 미열람 페이지가 이어서 볼 항목으로 남는지를 확인했다. 이 검사는 파일 탐색의 누락·폭증 경로만 다루며 최종 하네스 품질의 증거가 아니다.

프로젝트 가상환경에서 전체 회귀를 실행했다. 일반 샌드박스 실행의 소켓 통합 검사 한 건은 `PermissionError`로 막혔으며, 로컬 소켓을 허용한 재실행에서는 통과했다. 이 결과는 내부 계약의 회귀 여부만 확인한다. 실제 여러 데몬에서 입력 누락률·분석 시간·정상 흐름 복원·하네스 자격 판정이 개선되었는지는 독립 실행 자료가 필요하다.

후속 점검에서 원본 실행의 탐색 후보 수를 제한하는 `max_scenario_candidates`는 여전히 기본 256건이라는 **자원 예산**임을 확인했다. 이 숫자에 완결성을 부여할 연구 근거는 없다. 엄격 시나리오 탐색은 이미 누락된 대상 Action을 의무로 남겼지만, 탐색용 시나리오 경로는 예산 소진 뒤 남은 대상 Action을 조용히 건너뛰었다. 이 경로에도 생략된 Action ID를 `planner.obligations`로 기록하도록 수정했다. 한 Action의 변형 후보 수나 후속 요청 후보 수가 작업 예산에 닿았을 때에도 더 많은 요청열이 있을 수 있다는 의무를 남긴다. 예산을 무제한으로 바꿔 조합 탐색을 폭증시키는 변경은 하지 않았다. 따라서 256건 안에서 나온 결과를 전체 Action의 검증 완료로 읽어서는 안 된다. 모든 수정 뒤 전체 회귀를 다시 실행해 **531건 통과, 4건 건너뜀, 하위 검사 37건 통과**를 확인했다.

### 2026-10-30: Entry 전체 탐색 완료와 개별 Action 증거 분리

**관찰한 결함:** 활성 `InputActionAgent`는 한 Entry의 다른 소비 경로를 아직 열지 못하면, 이미 열린 입력 형식·dispatcher·handler·성공 결과의 소스 근거가 있는 Action도 전부 `POSSIBLE`로 내렸다. 반대로 Entry 탐색이 끝났다는 모델의 응답은 개별 Action의 누락 근거를 채우지 못한다. 이 판단은 분기 수와 무관하지만 중요한 Action을 계획 단계에서 빼는 결과를 만든다.

**연구 근거와 적용 범위:** [Weiser의 Program Slicing](https://faculty.cc.gatech.edu/~harrold/6340/cs6340_fall2009/Readings/Weiser.Slicing.TSE.pdf)은 분석 대상을 관찰하려는 특정 값과 위치로 정하고 데이터·제어 의존성을 추적한다. 여기서 가져온 것은 **전체 프로그램 탐색의 완료와 특정 동작에 대한 근거를 구별해야 한다는 분석 기준**이다. 우리 코드의 소스 위치 검사와 제한적인 직접 인자 추적은 논문의 완전한 프로그램 슬라이싱 구현이 아니며, 이 논문은 C/C++ 데몬 하네스의 정확도를 보장하지 않는다. [FuzzGen](https://www.usenix.org/system/files/sec20-ispoglou.pdf)의 호출 순서·인자 의존성 문제는 성공 경로와 필요한 상태를 별도로 확인해야 할 이유를 준다. 그러나 FuzzGen이 다루는 라이브러리 API 순서를 네트워크 요청 순서의 정답으로 옮기지 않는다. [OSS-Fuzz의 생성 하네스 평가](https://github.com/google/oss-fuzz/blob/master/docs/research/target_generation.md)는 잘못 호출한 API가 거짓 크래시를 만들 수 있음을 기록한다. 그래서 정적 Action 확정만으로 크래시나 하네스를 승인하지 않는다.

**적용:** 활성 의미 기반 응답에서 각 Action에 `action_context_complete`를 요구한다. 해당 Action의 외부 입력 형식, Entry에서 handler까지의 경로, 관찰 가능한 결과를 아직 조사 중이면 `false`다. `PROVEN_STATIC`은 이 값이 참이고 기존의 실제 열린 소스 근거·입력 예시·경로·성공 근거·미해결 조건 검사를 모두 통과한 Action에만 붙인다. Entry의 `context_complete`는 그 Entry에서 다른 Action이 남았는지를 표현하며, 미완료 경로는 `inventory_obligations`에 남는다. 이 필드는 모델의 자기평가이므로 독립 증거가 아니며, 단독으로 상태를 올리지 않는다. 기존 scripted 제공자가 새 필드를 생략한 경우에만 과거의 Entry 완료 값을 사용해 호환성을 유지한다.

**예상 효과와 위험:** 한 Entry의 다른 분기를 조사하느라 근거가 확보된 Action까지 막히는 누락은 줄어든다. 반면 모델이 한 Action의 근거를 과신하거나 직접 인자 추적이 구조체·별칭·비동기 전달을 놓치는 위험은 그대로 있다. 그 경우 실제 원본 요청 귀속 및 정상 실행이 입증되기 전에는 `PROVEN_RUNTIME`과 `QUALIFIED`가 되지 않는다. 따라서 이 변경의 성공 기준은 후보 회복과 거짓 정적 확정의 회귀 검사이며, 실제 다수 데몬의 하네스 생성률 향상이나 크래시 무오탐은 아직 입증하지 않았다.
## 2026-10-30: 입력 예시와 소비 경로를 혼동하지 않는 탐색 (아래 적용 범위 재검토에서 수정)

원본 C 코드에서 획득 버퍼를 두 함수에 전달하는 경우를 만들었다. 모델이 첫 함수의 입력 예시를 제안하면서 `context_complete=true`를 반환하면, 기존 Input Surface 경로는 아직 열지 않은 두 번째 함수를 건너뛰었다. **한 개의 바이트 가설은 그 바이트가 통하는 소비 함수 전체의 목록도, 각 함수의 형식도 증명하지 않는다.**

[NetLifter의 소스 기반 프로토콜 형식 복원](https://qingkaishi.github.io/public_pdfs/CCS23.pdf)은 입력 형식의 근거를 실제 파서 쪽에서 찾는 이유를 제공한다. 그러나 그 분석은 우리 인덱스의 모든 별칭·콜백·스레드 전달을 복구해 주지 않는다. 이 프로젝트에 적용한 범위는 **획득 버퍼가 직접 인자로 전달되는 소스 연결**뿐이다. 이미 예시 바이트가 있어도 이 연결의 미열람 소비 함수를 한 번에 하나씩 연다. 제안된 바이트는 계속 시험 가설이며, 그 함수를 연 사실만으로 정상 입력·실행 경로·기능 성공을 확정하지 않는다. 모델의 조기 완료와 별개로 `parse_alpha(data)`와 `parse_beta(data)`가 모두 열리는 C 소스 회귀 검사를 추가했다. 필드 별칭, 간접 호출, 다른 쓰기의 개입은 그대로 미해결로 기록한다.

### 요청별 자동 계측 후보의 적용 가능성 시험

[Clang DataFlowSanitizer 공식 문서](https://clang.llvm.org/docs/DataFlowSanitizer.html)는 입력에 사용자가 라벨을 붙여야 하고, 계측되지 않은 라이브러리는 ABI 목록으로 명시하거나 함께 계측해야 한다고 설명한다. 함수 도달 콜백도 실험 기능이며, 최대 기본 라벨은 8개다. [StateAFL 공개 구현](https://github.com/stateafl/stateafl)은 컴파일 시 네트워크 I/O와 메모리 할당을 계측해 상태를 관찰하지만, 그 상태 해시는 특정 요청의 handler 실행과 성공 결과를 증명하지 않는다.

이를 범용 요청 귀속의 완성된 해법으로 곧바로 도입하지 않고, 원본 소스에서 분리한 memcached HEAD 복사본에서 적용 전제를 시험했다. 기존 OSS-Fuzz 빌더의 Clang으로 memcached만 DFSan 계측하자 비계측 libevent의 `event_init.dfsan` 미정의로 configure가 중단됐다. 별도 libevent 계측의 첫 실패는 링크용 `-no-pie`를 빠뜨린 시험 설정 오류였고, 두 번째 실패는 비계측 libc `arc4random_buf`의 ABI 처리 누락이었다. 두 설정을 바로잡아 DFSan libevent과 memcached 서버를 빌드했다. 격리된 UDP `stats` 요청에서 `recvfrom` 직후의 바이트에 실험적으로 라벨 1을 붙였고, 같은 요청에 대한 서버 응답과 `try_read_udp` → `try_read_command_udp` → `process_request`의 라벨 도달을 관찰했다. `process_command_ascii`에서는 라벨이 붙은 명령 버퍼를 직접 확인했지만 함수 도달 콜백은 발생하지 않았다. [Clang 문서](https://clang.llvm.org/docs/DataFlowSanitizer.html)가 설명하듯 이 콜백은 함수 내 스택·레지스터에 **tainted value가 도달하는 조건**에 관한 실험 기능이지 모든 실행 함수의 추적기가 아니다. 따라서 콜백 부재를 handler 미실행으로 해석할 수 없다.

독립된 Dropbear HEAD 복사본도 DFSan 빌드 후 실제 SSH 배너와 클라이언트 버전 문자열 교환에 성공했다. 다만 시험 컨테이너에는 zlib 개발 라이브러리가 없어 `--disable-zlib`로 빌드했으므로 원래 설정과의 동등성은 입증하지 못했다. memcached의 라벨은 임시 복사본의 특정 UDP 획득 지점에 수동으로 붙인 것이다. 다른 read 계열 호출, 여러 요청의 고유 식별, TLS 경계, 결과의 의미적 성공, 크래시의 원본 재현은 자동으로 확보되지 않았다. 두 데몬의 빌드·기본 실행을 일반 C/C++ 데몬의 자동 요청 귀속 성공률로 해석하지 않는다.

따라서 DFSan은 현재 검증기와 `PROVEN_RUNTIME` 승격 경로에 넣지 않았다. **먼저 필요한 검증**은 독립된 실제 데몬 두 개 이상에서 원본과 동일한 빌드 구성이 계측 후에도 동작하고, 특정 요청의 바이트가 작업자/콜백을 지나 목표 함수에 귀속되며, 다른 동시 요청과 배경 작업을 잘못 귀속하지 않는 반례 시험이다. 그 뒤에도 함수 도달은 기능 성공과 별개의 관찰이므로 원본의 응답·상태·완료 조건 근거가 필요하다. 현재 일반 C/C++ 데몬의 요청별 자동 계측은 미완료다.

### 사용자가 지적한 가정별 실제 상태

이 표의 조치는 발견률이나 하네스 품질의 실험적 보증이 아니다. 설정된 시나리오 후보/상태 탐색의 유한 자원 한도는 **인식론적 완료 기준이 아니라 실행 중단 기준**이며, 미시험 후보·미해결 요청열을 결과에 남겨야 한다. 둘을 혼동해 `QUALIFIED`를 주장하는 경로는 허용하지 않는다.

### 원본 결과가 서로 모순될 때의 판정

실제 컴파일한 stdin 서버가 `OK`를 출력하면서 같은 요청의 계측 결과를 `failure`로 남기게 하자, 기존 검증기는 성공 응답 표식만 보고 `PROVEN_RUNTIME`으로 올렸다. 이 반례를 재현한 뒤, 요청별 원본 실패 결과가 있으면 성공 표식과 관계없이 정상 완료를 거부하도록 수정했다. [RESTler 원문](https://2019.icse-conferences.org/details/icse-2019-Technical-Papers/6/REST-ler-Stateful-REST-API-Fuzzing)은 실제 응답으로 요청열을 검증하지만, 여기의 실패 이벤트는 REST 응답 코드가 아니라 **별도로 계측한 원본 코드의 결과**다. 따라서 RESTler의 판정을 복사한 것이 아니라 상충하는 두 관찰을 확정 증거로 합치지 않도록 기존 계약을 고친 것이다. [FuzzGen 원문](https://www.usenix.org/system/files/sec20-ispoglou.pdf)의 잘못된 호출 순서와 거짓 크래시 문제는 이 보수적 경계의 목적을 뒷받침한다. 아직 원본 결과의 자동 계측이 없으므로 임의 데몬 전체에 이 보호가 적용됐다고 말할 수 없다.

### 입력 후보 단계의 전체 소비 함수 순회 재검토

직전의 `입력 예시와 소비 경로를 혼동하지 않는 탐색` 변경은 **한 바이트 가설이 모든 소비 경로를 대표하지 않는다**는 지적에는 맞았다. 그러나 그 이유로 입력 후보 담당 Agent까지 모든 직접 소비 함수를 열게 한 것은 적용 범위를 잘못 잡았다. 이 Agent의 산출물은 원본에 보낼 바이트 **가설** 한 건 이상이며, 모든 Action의 목록이 아니다. Input Action Agent가 같은 Entry에서 별도로 직접 소비 함수와 콜백 단서를 한 함수씩 여는 구조이므로, 두 Agent가 같은 소비 함수를 전부 여는 비용이 중복됐다.

| 외부 자료의 실제 범위 | 이 워크플로우에 적용한 부분 | 적용하면 안 되는 부분과 위험 |
|---|---|---|
| [NetLifter](https://qingkaishi.github.io/public_pdfs/CCS23.pdf)는 C 프로토콜 파서의 소스에서 입력 형식을 복원한다. | 바이트가 만들어지지 않을 때 획득 호출의 **소비 함수**를 열어 형식 근거를 찾는다. | NetLifter의 파서 전제나 형식 복원 정확도를 임의 데몬·C++·콜백 경로에 이식하지 않는다. |
| [Weiser의 Program Slicing](https://faculty.cc.gatech.edu/~harrold/6340/cs6340_fall2009/Readings/Weiser.Slicing.TSE.pdf)은 관찰 대상의 값·위치에 맞는 의존 코드를 분석한다. | `시험 가능한 바이트`와 `가능한 모든 동작`을 서로 다른 분석 목표로 취급한다. | 현재 직접 인자 추적을 완전한 프로그램 슬라이스라고 주장하지 않는다. |
| [RESTler](https://2019.icse-conferences.org/details/icse-2019-Technical-Papers/6/REST-ler-Stateful-REST-API-Fuzzing)은 명세로 만든 요청열을 원본 서비스 응답으로 시험한다. | 입력 바이트 가설이 생기면 원본 실행 시험을 먼저 할 수 있게 한다. | API 명세·응답 코드가 없는 데몬에 RESTler의 수락 판정을 복사하지 않는다. GDB 관찰도 요청별 handler 증거가 아니다. |
| [FuzzGen](https://www.usenix.org/system/files/sec20-ispoglou.pdf)은 상태와 호출 순서를 갖춘 라이브러리 퍼저 생성 문제를 다룬다. | Action과 후속 상태 계약은 별도 단계에서 계속 검증한다. | 라이브러리 API의 호출 순서를 네트워크 요청 순서의 정답으로 쓰지 않는다. |

**수정한 판정:** 바이트 가설이 없으면 Input Surface는 소스에 연결된 소비 함수를 계속 열 수 있다. 가설이 있고 모델이 더 열 함수를 요청하지 않으면 원본 시험으로 넘긴다. 그때 미열람 직접 소비 함수, Entry Verifier가 제시한 소비 함수, 사용 예시 페이지는 `continuations.json`과 의무 항목에 남긴다. 이는 입력 형식이나 Action 목록이 완성되었다는 판정이 아니다. 활성 Input Action 경로는 여전히 미열람 직접 소비 경로를 한 함수씩 열며, `if/case`를 별도 Action 작업으로 만들지 않는다. 여러 Entry의 초기 시험 순서는 한 Entry의 후보가 전부 앞서지 않도록 번갈아 배치할 뿐이며 기본 시험 건수 제한은 0이다. 원본 시험에 GDB를 사용한 경우 관찰 기록만 남기고 `PROVEN_RUNTIME`으로 승격하지 않는다.

**반례와 남은 위험:** `read_record`가 `parse_alpha`와 `parse_beta`를 직접 호출하는 C 픽스처에서 첫 턴에 바이트 가설이 나오면 Input Surface는 한 번만 모델을 호출하고 두 함수 ID를 미확인 항목에 남긴다. 이미 목록에 보였지만 열지 않은 사용 예시 파일도 경로를 남긴다. 별도 Input Action 회귀 검사는 첫 Action을 찾은 뒤에도 다른 직접 소비 함수를 열어 두 번째 후보를 찾는다. 반대로 바이트가 없으면 Input Surface가 파서를 계속 열어 형식 근거를 찾는 검사도 유지한다. 관련 검사 **55건 통과·1건 건너뜀**, 변경된 원본 실행 통합 검사 통과. 전체 회귀는 사용 가능한 로컬 소켓 환경에서 변경 직후 **543건 통과·4건 건너뜀·하위 검사 37건 통과**였고, 마지막 사용 예시 기록 수정 후 관련 검사를 다시 통과했다. 원본 시험에서 바이트가 거절된 뒤 해당 미확인 항목을 자동으로 다시 여는 피드백 루프, 간접 호출·필드 별칭·스레드 전달의 완전한 탐색, 요청별 자동 계측은 여전히 구현·검증되지 않았다. 따라서 이 변경은 중복 LLM 호출을 줄이는 **국소 수정**이며, 실제 데몬의 하네스 생성률이나 무오탐성을 입증하지 않는다.
