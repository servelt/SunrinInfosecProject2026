# ELF 빌드 대상에 따른 분석 순서: 근거와 검증

## 확인한 문제

한 소스 트리에 서버와 클라이언트 실행 파일이 함께 있으면, Entry 생성기가 둘 다 읽는 데 시간이 든다. Dropbear 서버를 분석할 때 `cli-*` 함수까지 후보로 섞였던 것이 실제 사례다. [Clang의 컴파일 데이터베이스 규격](https://clang.llvm.org/docs/JSONCompilationDatabase.html)은 각 번역 단위의 컴파일 명령을 정의한다. 그 파일만으로 어떤 목적 파일이 **서버 실행 파일에 링크되었는지**는 알 수 없다. 이를 근거로 클라이언트 소스를 제거하면 누락될 수 있다.

## 외부 규격을 이 워크플로우에 적용한 범위

[ELF 심볼 테이블 규격](https://gabi.xinuos.com/elf/05-symtab.html)의 `STT_FILE`은 심볼이 속한 소스 파일 이름을 기록할 수 있다. 디버그 정보가 없는 ELF에도 일반 심볼 테이블이 남아 있다면, 파일 이름을 **분석 순서의 양성 단서**로 사용할 수 있다. 이 규격은 현재 체크아웃의 파일 내용이나 빌드 리비전을 증명하지 않는다. 따라서 다음 조건만 채택했다.

1. DWARF 컴파일 단위가 있고 소스 내용이 일치하면 기존의 바이트 동일성 검사를 우선한다.
2. DWARF 컴파일 단위가 전혀 없을 때만 ELF `SHT_SYMTAB`의 `STT_FILE` 이름을 읽는다. 인덱싱된 파일 중 기본 이름이 유일할 때만 우선순위 단서로 쓴다.
3. 이름이 겹치거나 `.symtab`이 없으면 우선순위를 매기지 않는다. **단서가 없는 함수도 Entry 후보에서 제거하지 않는다.**
4. DWARF가 존재하나 현재 체크아웃과 내용이 맞지 않으면 같은 이름의 ELF 심볼로 그 불일치를 덮지 않는다.

이는 링크 대상의 완전한 복원이나 함수의 실행 가능성 증명이 아니다. 심볼의 부재를 소스의 부재로 해석하지 않으므로 stripped 바이너리, LTO, 인라인 함수, 생성 소스에도 결론을 강요하지 않는다. 이름이 유일하더라도 바이너리가 다른 리비전이면 순서가 틀릴 수 있다. 그 경우 영향은 읽는 순서이며 검증 결과나 후보 삭제가 아니다.

## 실제 다른 데몬에서 확인한 결과

Dropbear 커밋 `59870ad`의 복사본을 `--disable-zlib --disable-harden --disable-shadow`로 설정하고 `make -j4 dropbear`로 서버 실행 파일을 만들었다. 이 실험 바이너리에는 소스 DWARF 일치가 0개였다. 전체 C 소스 732개 중 ELF 파일 심볼을 통해 210개가 **읽기 우선순위**에 올랐고, 그중 서버 전용 `src/svr-*` 파일 16개가 포함됐다. `src/svr-main.c`는 포함되고 `src/cli-main.c` 및 `src/cli-*` 파일은 포함되지 않았다. 기본 이름이 중복된 심볼 3개는 선택하지 않았다. 실제 링크 명령에도 `svr-main.o`가 있었고 `cli-main.o`는 없었다. 이 비교는 이번 Dropbear 빌드에서 우선순위의 방향이 맞았다는 증거이며, 다른 빌드나 모든 데몬에서 같은 결과를 보장하지 않는다.

실제 코드의 출력은 `analysis/binary-source-priority.json`에 `matched_files`, `symbol_file_hints`, `ambiguous_symbol_files`를 분리해 기록한다. C 언어 두 파일을 링크하고 다른 클라이언트 파일을 제외한 반례, 같은 기본 이름이 두 곳에 있는 반례, DWARF와 현재 체크아웃 내용이 다른 반례를 테스트했다. 모두 소스 제외 없이 순서만 변경되는지 확인했다.

## 남은 검증

`STT_FILE`이 없는 실행 파일에서는 빌드 시스템이 제공하는 **실제 링크 대상과 목적 파일의 관계**가 필요하다. [CMake 파일 API](https://cmake.org/cmake/help/latest/manual/cmake-file-api.7.html)는 대상별 구조와 소스 정보를 제공하지만, Make/Autotools의 모든 링크 형태에 그대로 적용되지 않는다. 또 이 순서 변경은 Entry 발견 시간만 줄일 수 있고 입력 형식 복원, 요청별 handler 귀속, 정상 선행 상태, 하네스 적격을 해결하지 않는다. 그런 결과는 각 데몬에서 별도로 측정해야 한다.
